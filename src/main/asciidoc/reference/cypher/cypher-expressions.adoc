[[cypher-expressions]]
==== Expressions and Functions

This section describes the expressions and functions available in ArcadeDB's OpenCypher implementation.

===== Literals

[%header,cols="2,3,3"]
|===
| Type | Syntax | Example
| Integer | `123`, `-456` | `RETURN 42`
| Float | `3.14`, `-2.5` | `RETURN 3.14159`
| String | `'text'`, `"text"` | `RETURN 'Hello'`
| Boolean | `true`, `false` | `RETURN true`
| Null | `null` | `RETURN null`
| List | `[1, 2, 3]` | `RETURN [1, 'a', true]`
| Map | `{key: value}` | `RETURN {name: 'Alice', age: 30}`
|===

===== Property Access

Access properties using dot notation:

[source,cypher]
----
MATCH (p:Person)
RETURN p.name, p.age, p.address.city
----

A property can also be read with the subscript form `p['name']`, through `properties(p)` (`properties(p).name`, `properties(p)['name']`), and across a `LINK` property (`a.link.name`, `a.link['name']`). _(Since v26.10.2)_ `a.link['name']` on a `LINK` property reads through the link like `a.link.name`; before, it returned `null`.

[[cypher-declared-string-comparison]]
*Comparing a property declared in the schema:*

_(Since v26.10.2)_ A value written into a declared property is converted to the declared type, and the declaration also decides how a text is read. A property declared `STRING` stores the text of what is written into it (writing `1` stores `'1'`), and a property declared with any other scalar type (`INTEGER`, `LONG`, `FLOAT`, `DOUBLE`, `DECIMAL`, `BOOLEAN`, `DATE`, `DATETIME`, ...) stores a text written into it as that type (writing `'5'` into an `INTEGER` stores `5`). To find it again, a pattern (`MATCH (n:Product {code: 1})`, `MERGE`) or a comparison against such a property compares by what the other operand would be stored as: `n.code = 1` finds the `'1'` that writing `1` stored, and `n.qty = '5'` finds the `5` that writing `'5'` stored, so a repeated `MERGE` does not create a duplicate. A property that is not declared keeps Cypher's strict typing, so `'1' = 1` is `false`.

Only the text form is converted: two values of the same kind keep Cypher's comparison, so `n.qty = 1.5` stays `false` for a stored `1`. A text the declared type cannot read (`'abc'` or `'5.7'` for an `INTEGER`) matches nothing.

The comparison applies to every spelling of the same property read: `n.code`, `n['code']`, `properties(n).code`, `properties(n)['code']`, a chained read across a link (`a.link.code`, `a.link['code']`), `IN` (`n.code IN [1, 2]`) and the simple `CASE n.code WHEN 1 THEN ... END`. A value projected first is a plain value and keeps Cypher's strict typing:

[source,cypher]
----
// Product.code is declared STRING, Product.qty is declared INTEGER
CREATE (:Product {code: 1, qty: '5'})                              // stores '1' and 5

MATCH (n:Product {qty: '5'}) RETURN n                              // found

MATCH (n:Product) WHERE n['code'] = 1 RETURN n                     // found
MATCH (n:Product) WHERE n.code IN [1, 2] RETURN n                  // found
MATCH (n:Product) WITH n, n.code AS code WHERE code = 1 RETURN n   // not found: '1' = 1 is false
----

===== CASE Expression

Conditional logic in expressions.

*Simple CASE:*

[source,cypher]
----
MATCH (p:Person)
RETURN p.name,
       CASE
         WHEN p.age < 18 THEN 'minor'
         WHEN p.age < 65 THEN 'adult'
         ELSE 'senior'
       END AS ageGroup
----

*Extended CASE:*

[source,cypher]
----
MATCH (p:Person)
RETURN p.name,
       CASE p.status
         WHEN 'A' THEN 'Active'
         WHEN 'I' THEN 'Inactive'
         ELSE 'Unknown'
       END AS statusName
----

A `WHEN` can hold several comma-separated values, a list or map literal, or a comparison applied to the tested value:

[source,cypher]
----
RETURN CASE x WHEN 1, 2 THEN 'low' WHEN > 5 THEN 'high' WHEN IS NULL THEN 'none' ELSE 'mid' END
RETURN CASE n.tags WHEN [] THEN 'empty' WHEN ['a'] THEN 'just a' ELSE 'other' END
----

===== Arithmetic Expressions

Perform arithmetic operations on numeric values.

[%header,cols="2,2,3"]
|===
| Operator | Description | Example
| `+` | Addition | `RETURN 5 + 3` (returns 8)
| `-` | Subtraction | `RETURN 10 - 4` (returns 6)
| `*` | Multiplication | `RETURN 6 * 7` (returns 42)
| `/` | Division | `RETURN 15 / 3` (returns 5.0)
| `%` | Modulo | `RETURN 17 % 5` (returns 2)
| `^` | Power | `RETURN 2 ^ 8` (returns 256.0)
|===

*Examples with properties:*

[source,cypher]
----
// Double a person's age
MATCH (p:Person)
RETURN p.name, p.age * 2 AS doubleAge

// Calculate monthly salary
MATCH (p:Person)
RETURN p.name, p.salary / 12 AS monthlySalary

// Complex expression
MATCH (p:Person)
RETURN p.name, (p.age * 2) + 10 AS result
----

NOTE: The `+` operator also works for string concatenation: `RETURN 'Hello' + ' ' + 'World'` returns `'Hello World'`. A number, a boolean or a date/time value is converted to text, eg `'n:' + 1` returns `'n:1'`. Concatenating a string with a node, a relationship, a path, a map or a point raises a type error (`Type mismatch: expected Float, Integer, String or List<T> but was Node`), on either side of `+`: concatenate a property instead, eg `'x:' + n.name`.

===== Map Literals

Create inline map (object) structures.

*Syntax:* `{key1: value1, key2: value2, ...}`

[source,cypher]
----
// Simple map literal
RETURN {name: 'Alice', age: 30}

// Empty map
RETURN {}

// Map with expressions
MATCH (p:Person)
WHERE p.name = 'Alice'
RETURN {
  personName: p.name,
  doubled: p.age * 2,
  nextYearAge: p.age + 1
} AS info
----

===== List Comprehensions

Transform and filter lists using comprehension syntax.

*Syntax:* `[variable IN list WHERE condition | expression]`

* `variable` - iteration variable
* `list` - source list or range
* `WHERE condition` - optional filter (elements that don't match are excluded)
* `| expression` - optional mapping expression (transforms each element)

*Basic transformation:*

[source,cypher]
----
// Double each number
RETURN [x IN [1, 2, 3] | x * 2]
// Returns [2, 4, 6]

// Square numbers using range
RETURN [x IN range(1, 5) | x * x]
// Returns [1, 4, 9, 16, 25]
----

*With filter:*

[source,cypher]
----
// Filter and transform
RETURN [x IN [1, 2, 3, 4, 5] WHERE x > 2 | x * 10]
// Returns [30, 40, 50]

// Filter only (no transformation)
RETURN [x IN [1, 2, 3, 4, 5] WHERE x > 3]
// Returns [4, 5]
----

===== Map Projections

Extract specific properties from nodes or maps into a new map structure.

*Syntax:* `variable{.property1, .property2, key: expression, .*}`

* `.property` - include this property from the source
* `key: expression` - add a computed value with the given key
* `.*` - include all properties from the source

*Property selection:*

[source,cypher]
----
// Select specific properties
MATCH (p:Person)
WHERE p.name = 'Alice'
RETURN p{.name, .age} AS person
// Returns {name: 'Alice', age: 30}
----

*With computed values:*

[source,cypher]
----
// Add computed properties
MATCH (p:Person)
WHERE p.name = 'Alice'
RETURN p{.name, doubleAge: p.age * 2} AS person
// Returns {name: 'Alice', doubleAge: 60}
----

*All properties:*

[source,cypher]
----
// Include all properties
MATCH (p:Person)
WHERE p.name = 'Alice'
RETURN p{.*} AS person
// Returns {name: 'Alice', age: 30, salary: 50000}
----

*With aggregates:* a map projection that contains an aggregate groups by its own variable, one row per value of it.

[source,cypher]
----
MATCH (p:Person)-[:KNOWS]->(f)
RETURN p{.name, friends: count(f)} AS person
// Returns one row per p, e.g. {name: 'Alice', friends: 2} and {name: 'Bob', friends: 1}
----

RETURN sum(p.salary)

MATCH (p:Person)
RETURN avg(p.age)
----

[[cypher-max]]
====== max()

Returns the maximum value.

[source,cypher]

====== collect()

Collects values into a list.

====== toString()

Converts a value to string.

[source,cypher]
----
RETURN toString(123)      // Returns '123'
RETURN toString(3.14)     // Returns '3.14'
RETURN toString(true)     // Returns 'true'
----

_(Since v26.12.1.)_ A `localtime()`, `time()`, `localdatetime()` or `datetime()` is written as Neo4j 5 writes it: the seconds are always printed, and the fraction of a second has its trailing zeros removed (up to 9 digits). A date, an offset, a zone name and a duration are written as before.

[source,cypher]
----
RETURN toString(localtime('10:00'))                        // Returns '10:00:00'
RETURN toString(time('10:00Z'))                            // Returns '10:00:00Z'
RETURN toString(localdatetime('2020-01-01T10:00'))         // Returns '2020-01-01T10:00:00'
RETURN toString(datetime('2020-01-01T10:00:00.500Z'))      // Returns '2020-01-01T10:00:00.5Z'
----

Only the text made by `toString()` (and `toStringOrNull()`, `toStringList()` and `convert.toString()`) follows this rule. A temporal value that a query returns is still serialized as before, for example `"10:00"` for `localtime('10:00')` over HTTP.

_(Since v26.12.1.)_ A `BINARY` value (a byte array, such as a `BINARY` property or a bytes parameter) has no text form: `toString()` refuses it with `TypeError: InvalidArgumentValue - toString() cannot convert byte[]`, as it does for a list or a node, `toStringOrNull()` answers `null`, and `toStringList()` answers `null` for such an element. Before, they answered Java's identity text of the array (`[B@e044818`), which differs from run to run (issue #12780).

[[cypher-round]]
====== round()

Rounds to nearest integer, or to a number of decimal places with `round(value, precision [, mode])`. A value exactly half-way between two integers rounds toward positive infinity, and `round(x, 0)` answers the same as `round(x)`. A tie at a precision of one or more decimals rounds away from zero. The optional mode is one of `UP`, `DOWN`, `CEILING`, `FLOOR`, `HALF_UP`, `HALF_DOWN`, `HALF_EVEN` or `UNNECESSARY`, and always wins over the default. `UNNECESSARY` returns the value when no rounding is needed and raises `Rounding necessary` otherwise.

[source,cypher]
----
RETURN round(2.5)      // Returns 3.0
RETURN round(2.4)      // Returns 2.0
RETURN round(-2.5)     // Returns -2.0
RETURN round(-2.5, 0)  // Returns -2.0
RETURN round(-2.25, 1) // Returns -2.3
RETURN round(1.0, 0, 'UNNECESSARY')  // Returns 1.0
----

[[cypher-rand]]
====== rand()

Returns random float between 0 and 1.

[source,cypher]
----
RETURN rand()  // Returns e.g. 0.7324...
----

In an inline property map, `rand()` is drawn once per input row, and that one value both finds the node and checks it:
`UNWIND range(1, 2000) AS j MATCH (a:N {k: toInteger(rand() * 10)})` over keys 0 to 9 matches one node per row. In
`WHERE a.k = toInteger(rand() * 10)` the expression is drawn again for every candidate node, as the predicate is
written, so an index on `k` is not used to answer it. _(Since v26.12.1, issue #12179: a value drawn to look the node up
was drawn again to check it, so the match kept about one row in ten.)_

[[cypher-node-functions]]
===== Node and Relationship Functions

[[cypher-id]]
====== id()

Returns the internal ID of a node or relationship as a numeric (`Long`) value, matching the Neo4j semantics where `id()` returns an `INTEGER`. The two
components of an ArcadeDB RID (`bucketId`, `position`) are packed into a single non-negative number so it can be used in numeric predicates such as
`WHERE id(n) >= 0`.

[source,cypher]
----
MATCH (p:Person)
RETURN id(p)  // Returns e.g. 786432
----

The packing uses 63 of the 64 bits of the `Long` (the sign bit is kept clear so the value is never negative): the upper bits hold the `bucketId` and the lower
bits the record `position`. The split is controlled by the global setting `arcadedb.opencypher.idBucketBits` (see <<arcadedb-settings,Settings>>). The default of `16`
reserves 16 bits for the bucketId (up to 65536 buckets) and 47 bits for the position (~1.4e14 records per bucket), which covers the vast majority of use cases:

* Increase it (e.g. `20`) for databases that allocate a very large number of buckets across many types.
* Decrease it for buckets that hold an extremely high number of records.

[source,shell]
----
# Reserve 20 bits for the bucketId (up to ~1M buckets)
java ... -Darcadedb.opencypher.idBucketBits=20
----

To put the position field in perspective with the default `16`: it reserves 47 bits, enough to address `2^47` ≈ 1.4e14 positions per bucket. A single bucket is
internally limited to ~2.1 billion pages (the page index is a 32-bit integer), so with a standard 64KB page holding on average ~500 records that is about
`2.1e9 × 500` ≈ *1 trillion records (~137 TB) in one bucket* - and the 47-bit position field covers that roughly 30x over. In other words, the numeric `id()`
never runs out of range before the bucket is physically full, so for almost every database the only setting worth tuning is the bucketId width (the bucket
*count*), not the position width.

[NOTE]
====
`id()` fails with an error if a RID cannot be packed with the configured split (for example a `bucketId` beyond the reserved bits), so an out-of-range value is
reported instead of silently colliding with another id. Because the value is computed from the split, changing `arcadedb.opencypher.idBucketBits` alters the
numeric output: encode and decode must use the same setting. For a stable, opaque identifier that does not depend on this setting, use `elementId()` instead.

`id()` of a lightweight edge is `null`: a lightweight edge has no record, so there is no position to pack (_since v26.10.2_; earlier versions raised an error). Use `elementId()` instead, which names the edge (_since v26.12.1_, see <<lightweight-edges,Lightweight Edges>>).
====

From SQL, the numeric id can be resolved back to a record in O(1) with the `cypherRID()` function, e.g. `SELECT FROM cypherRID(:id)` (the inverse of `id()` / `.asCypherRID()`).

A RID written as text compares with a number as the id it encodes: `1 = '#0:1'` is `true`, and the same reading applies to `IN` and to `<`, `<=`, `>`, `>=`. It is an ArcadeDB extension that keeps the legacy `WHERE id(n) = '#1:0'` form working (Neo4j answers `false` for a number against a text). Only a text that spells a RID is read this way, so `5 = '5'` stays `false`. A decimal number is compared as it is, without being truncated first: `1.0 = '#0:1'` is `true` and `1.5 = '#0:1'` is `false`.

On a numeric property the answer is the same whether or not an index serves the predicate: with `P.id` a `LONG` property holding `1` on one vertex, `MATCH (p:P) WHERE p.id = '#0:1' RETURN p` and `WHERE p.id IN ['#0:1', '#0:2']` find that vertex with or without an index on `P.id`, and so does a `WHERE` equality on an indexed relationship property. An index on a `STRING` property still looks up the text as written. A property map in a pattern matched once per input row (after a leading `WITH` or `UNWIND`, as in `UNWIND ['#0:1'] AS r MATCH (p:P {id: r})`) still reads the text as a text and finds no vertex in a numeric property. _(Since v26.12.1: before, an index lookup answered no row where the same statement without the index answered the vertex, and `1.5 = '#0:1'` was `true`.)_

[[cypher-labels]]
====== labels()

Returns the labels of a node as a list. A node created with no label at all (`CREATE (n {name: 'x'})`) returns an empty list, exactly like Neo4j — including when the label a node carries happens to be literally `V` or `Vertex`, which are ordinary, writable labels like any other and are not treated specially.

[source,cypher]
----
MATCH (p:Person)
RETURN labels(p)  // Returns ['Person']

CREATE (n {name: 'x'})
RETURN labels(n)  // Returns []

CREATE (n:V {name: 'y'})
RETURN labels(n)  // Returns ['V']
----

[NOTE]
====
A database written by an earlier version can hold unlabelled nodes under the type name `V` (or `Vertex`), which that version used internally for "no labels". Those vertices report `labels(n)` as `['V']`/`['Vertex']` instead of `[]`.

There is no automatic per-record migration, because the two cases are indistinguishable in such a database: an existing `V`-typed vertex may be one that was genuinely created unlabelled, or one that was deliberately labeled `:V`. If a database's entire `V` (or `Vertex`) type was only ever used for unlabelled nodes, its schema type can be renamed so that the whole type reports no labels again; consult ArcadeDB support before doing this on a database where the distinction is not already known.
====

[[cypher-type]]
====== type()

Returns the type of a relationship. Calling it on a node is always an error.

[source,cypher]
----

[NOTE]
====
This check (and the equivalent one for `labels()`, `size()` and `length()`) is applied more precisely
when the same variable name is reused later in the query with `WITH`. A query that called `type()` on a node and
relied on a later `WITH` clause to mask the mistake now correctly reports the error instead of silently passing.

[[cypher-path-functions]]
===== Path Functions

The path functions read any path: one bound by a `MATCH` pattern or `shortestPath()`, the `path` a procedure yields (see
<<graph-algo-path-value>>), or one a `path.*` function returns. `null` returns `null`, and any other value is a type
error rather than an empty answer (`length()` also accepts a string, and returns its length in Unicode characters).

====== length()

Returns the length of a path (number of relationships).

[source,cypher]
----
MATCH path = (a:Person)-[:KNOWS*]->(b:Person)
RETURN length(path)
----

`length()` also accepts a string and counts it as `size()` and `char_length()` do: in Unicode characters, so a character outside
the Basic Multilingual Plane (an emoji, a mathematical letter such as `𝔸`) counts as one.

[source,cypher]
----
RETURN length('𝔸X')   // Returns 2
----

[NOTE]
====
Up to v26.10.2, `length()` of a string counted UTF-16 code units, so the example above answered 3 while `size('𝔸X')` answered 2.
From v26.11.1 the three agree. Strings made only of characters of the Basic Multilingual Plane (letters, digits and most scripts)
are not affected.
====

====== nodes()

Returns the nodes in a path as a list.

[source,cypher]
----
MATCH path = (a:Person)-[:KNOWS*]->(b:Person)
RETURN nodes(path)
----

====== relationships()

Returns the relationships in a path as a list.

[source,cypher]
----
MATCH path = (a:Person)-[:KNOWS*]->(b:Person)
RETURN relationships(path)
----

[[cypher-sql-bridge]]
===== SQL Function Bridge

ArcadeDB's OpenCypher implementation includes a bridge to the ArcadeDB SQL functions. This provides access to 100+ additional functions. Some of them (such as `sqrt()`, `date()` and `distance()`) can be called by their bare name; others (such as `pow()`, `uuid()`, `ifnull()` and `sysdate()`) are not found unless you prefix them with `sql.`, e.g. `sql.pow(2, 8)`. When in doubt, use the `sql.` prefix.

*Usage:*

Call SQL functions directly in Cypher expressions:

[source,cypher]
----
// Date functions
MATCH (p:Person)
RETURN p.name, date() AS today

// Math functions
RETURN sql.pow(2, 8) AS result  // Returns 256

// String functions
MATCH (p:Person)
RETURN normalize(p.name) AS normalizedName

// Geometric functions
RETURN distance(point(0, 0), point(3, 4)) AS dist  // Returns ~555811.94 (meters)
----

`point(0, 0)` creates a WGS-84 point, so `distance()` returns a geodesic distance in meters, not the cartesian distance of 5.0.

The Cypher `point()` function returns a map with the coordinates, the `crs` name and the `srid`, as Neo4j does:

[%header,cols="2,1,1"]
|===
|Call|crs|srid
|`point({x: 1, y: 2})`|cartesian|7203
|`point({x: 1, y: 2, z: 3})`|cartesian-3d|9157
|`point({longitude: 1, latitude: 2})`|wgs-84|4326
|`point({longitude: 1, latitude: 2, height: 3})`|wgs-84-3d|4979
|===

`crs` and `srid` can be given explicitly and are derived from each other. A `crs` name is accepted in any letter case and
returned in the spelling above. A pair that disagrees, or 2D/3D coordinates that do not match the `crs`/`srid`, raise an error.

`x`/`y` (and `z`) with a geographic `srid` or `crs` (4326, 4979, `wgs-84`, `wgs-84-3d`) build the same point as
`longitude`/`latitude` (and `height`): `point({x: 1, y: 2, srid: 4326}).longitude` is `1.0`. A map that has both `x`/`y`
and `longitude`/`latitude` is built from `x`/`y`, as in Neo4j, and `z` wins over `height`. A coordinate must be finite:
`Infinity` or `NaN` raises "Cannot create a point with non-finite coordinate values". A map with only one coordinate of
its pair, such as `point({x: 1})` or `point({latitude: 1})`, raises "A map with keys [x] is not describing a valid point",
while a coordinate given as `null` (`point({x: null, y: 2})`) still returns `null`. Unlike Neo4j, an unknown `crs` name
or `srid` is kept as given.

[NOTE]
====
Since v26.12.1. Before, `point({x: 1, y: 2, srid: 4326})` had a `null` `longitude` and `latitude`, a map with both
spellings built the WGS-84 point from `longitude`/`latitude`, non-finite coordinates were accepted and an incomplete map
returned `null` (issue #12276).
====

`ORDER BY`, `min()` and `max()` order points as Neo4j does: by coordinate reference system (srid 4326, 4979, 7203, 9157),
then by x (`longitude`), y (`latitude`) and z (`height`). A point sorts after an ordinary map. Points are not comparable
with `<` and `>` (the answer is `null`); `<=` and `>=` are `true` for two equal points and `null` otherwise.

[NOTE]
====
Since v26.12.1. Before, points were ordered as maps: a WGS-84 point by `latitude` first, a WGS-84-3D point by `height`
first, and points of different systems by their number of keys. `p <= p` and `p >= p` were `null` (issue #12274).
====

`point.distance(p1, p2)` returns the Euclidean distance between two Cartesian points and the distance in meters between two
WGS-84 points, on a sphere of radius 6,378,140 m as Neo4j does. For two WGS-84-3D points it includes the `height`: the surface
arc is taken at the mean height of the two points and the height difference is added as the other side of a right triangle,
so two points 1,000 m apart vertically are 1,000 m apart. `point.withinBBox(p, lowerLeft, upperRight)` also checks `z`
(`height`) when all three points are 3D. Both functions return `null` when a 2D point is mixed with a 3D point, or a
geographic point with a Cartesian one.

[NOTE]
====
Since v26.12.1. Before, both functions ignored the `height` of WGS-84-3D points and `point.withinBBox()` ignored `z` too, a
mix of 2D and 3D points gave a result instead of `null`, and `point.distance()` used an Earth radius of 6,371,000 m, so every
geographic distance is now about 0.11% longer. The SQL `geo.*` functions and the bare `distance()` shown above keep the
6,371 km radius (issue #12273).
====

[NOTE]
====
Up to 26.10.2 the `crs` names were `WGS-84`, `WGS-84-3D` and `cartesian-3D`. They are now the lower-case names Neo4j uses
(`wgs-84`, `wgs-84-3d`, `cartesian-3d`), so a test like `p.crs ENDS WITH '-3d'` works as it does on Neo4j. A point stored
in a property before the upgrade keeps the old spelling: `point.distance()`, `point.withinBBox()` and Bolt still recognise
it, but a case-sensitive comparison of its `crs` with a new point's does not match, so compare `toLower(p.crs)` or the
`srid` when old points can be involved.
====

For a complete list of available SQL functions, see the <<sql-functions,SQL Functions>> reference.

[[cypher-extended-functions]]
===== Extended Functions (APOC Compatible)

ArcadeDB provides a comprehensive set of extended functions that are fully compatible with Neo4j's APOC library. These functions work in both Cypher and SQL queries.

====== APOC Prefix Compatibility

ArcadeDB automatically supports the `apoc.` prefix. Your existing APOC queries work without modification:

[source,cypher]
----
// Neo4j/APOC style (works in ArcadeDB)
RETURN apoc.text.join(["a", "b", "c"], ",") AS result

// ArcadeDB native style (also works)
RETURN text.join(["a", "b", "c"], ",") AS result
----

====== Available Function Namespaces

[%header,cols="2,4"]
|===
| Namespace | Description
| `agg.*` | Aggregation functions (median, statistics, etc.)
| `convert.*` | Type conversion (toJson, fromJsonMap, etc.)
| `create.*` | Creation functions (uuid, virtual nodes/relationships)
| `date.*` | Date/time operations (format, parse, add, etc.)
| `map.*` | Map operations (merge, flatten, groupBy, etc.)
| `math.*` | Mathematical functions (sigmoid, tanh, etc.)
| `node.*` | Node operations (degree, labels, etc.)
| `path.*` | Path operations (create, combine, slice, expand)
| `rel.*` | Relationship operations (type, startNode, etc.)
| `text.*` | String manipulation (join, split, replace, camelCase, etc.)
| `util.*` | Utility functions (md5, sha256, compress, etc.)
| `vector.*` | Vector/embedding operations (similarity, distance, quantization, neighbors)
|===

====== Available Procedures

[%header,cols="2,4"]
|===
| Procedure | Description
| `merge.relationship` | Create or match relationships
| `merge.node` | Create or match nodes
| `algo.dijkstra` | Weighted shortest path
| `algo.astar` | A* pathfinding with heuristics
| `algo.allsimplepaths` | Find all simple paths
| `path.expand` | Expand paths from a node
| `path.subgraphnodes` | Get all reachable nodes
| `meta.graph` | Schema as virtual graph
| `meta.schema` | Detailed schema information
| `meta.stats` | Database statistics
|===

*Examples:*

[source,cypher]
----
// Text functions
RETURN text.camelCase("hello world") AS result
// Returns: "helloWorld"

// Map functions
RETURN map.merge({a: 1}, {b: 2, a: 3}) AS result
// Returns: {a: 3, b: 2}

// JSON conversion
RETURN convert.toJson({name: "Alice", age: 30}) AS json
// Returns: '{"name":"Alice","age":30}'

// Hashing
RETURN util.sha256("password") AS hash

// Statistics
RETURN agg.statistics([1, 2, 3, 4, 5]) AS stats
// Returns: {count: 5, min: 1.0, max: 5.0, sum: 15.0, mean: 3.0, ...}

// Graph algorithms
MATCH (a:City {name: 'NYC'}), (b:City {name: 'LA'})
CALL algo.dijkstra(a, b, 'ROAD', 'distance') YIELD path, weight
RETURN path, weight
----

For the complete function reference, see <<extended-functions>>.

[[cypher-operators]]
===== Operators

====== Comparison Operators

[%header,cols="2,3,3"]
|===
| Operator | Description | Example
| `=` | Equal | `WHERE n.age = 30`
| `<>` or `!=` | Not equal | `WHERE n.age <> 30`
| `<` | Less than | `WHERE n.age < 30`
| `>` | Greater than | `WHERE n.age > 30`
| `<=` | Less than or equal | `WHERE n.age <= 30`
| `>=` | Greater than or equal | `WHERE n.age >= 30`
|===

====== Logical Operators

[%header,cols="2,3,3"]
|===
| Operator | Description | Example
| `AND` | Logical AND | `WHERE n.age > 20 AND n.age < 40`
| `OR` | Logical OR | `WHERE n.city = 'NYC' OR n.city = 'LA'`
| `NOT` | Logical NOT | `WHERE NOT n.active = false`
|===

====== String Operators

[%header,cols="2,3,3"]
|===
| Operator | Description | Example
| `STARTS WITH` | String prefix match. Uses an ordered index on the property, except a case insensitive one | `WHERE n.name STARTS WITH 'A'`
| `ENDS WITH` | String suffix match | `WHERE n.email ENDS WITH '@gmail.com'`
| `CONTAINS` | Substring match | `WHERE n.name CONTAINS 'son'`
| `=~` | Regular expression | `WHERE n.phone =~ '[0-9]{3}-[0-9]{4}'`
|===

NOTE: `MATCH (n:Label) RETURN min(n.prop)` (and `max`) reads one end of the index when `prop` has an ordered index on `Label` and the query has no other clause. A `WHERE` that is only a range of the same property (`WHERE n.prop > 500000`, `<`, `>=`, `<=`) reads the first matching entry of the range instead of the whole range. SQL does the same for `SELECT min(prop) FROM Type WHERE prop > 500000`. A range bound that is `null` matches nothing, with or without an index.

====== List Operators

[%header,cols="2,3,3"]
|===
| Operator | Description | Example
| `IN` | Element in list | `WHERE n.name IN ['Alice', 'Bob']`
| `+` | List concatenation | `RETURN [1,2] + [3,4]` (returns [1,2,3,4])
|===

====== Null Operators

[%header,cols="2,3,3"]
|===
| Operator | Description | Example
| `IS NULL` | Check for null | `WHERE n.email IS NULL`
| `IS NOT NULL` | Check for not null | `WHERE n.email IS NOT NULL`
|===

[[cypher-parameters]]
===== Parameters

Parameters allow you to pass values into queries without string concatenation, providing security and performance benefits.

*Syntax:* `$parameterName`

[source,cypher]
----
MATCH (p:Person)
WHERE p.name = $name AND p.age >= $minAge
RETURN p
----

*Java Example:*

[source,java]
----
Map<String, Object> params = Map.of(
    "name", "Alice",
    "minAge", 25
);
ResultSet result = database.query("opencypher",
    "MATCH (p:Person) WHERE p.name = $name AND p.age >= $minAge RETURN p",
    params);
----

Parameters are particularly useful for:

* Preventing injection attacks
* Query plan caching (same plan reused for different parameter values)
* Handling special characters in values
