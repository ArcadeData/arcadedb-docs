[[materialized-views]]
==== Materialized Views

A materialized view is a schema-level object that stores the result of a SQL `SELECT` query as a backing document type.
Unlike regular views (which re-execute the query on every access), a materialized view holds a pre-computed snapshot of data that can be queried directly for fast reads.

A materialized view:

* Wraps a SQL `SELECT` query as its _defining query_
* Stores results in a backing `DocumentType` with standard buckets
* Supports three _refresh modes_: manual, incremental (post-commit), and periodic (scheduled)
* Persists its definition and metadata in `schema.json` alongside other schema objects
* Can be created, dropped, refreshed, and altered via SQL DDL statements or the Java Schema API

===== Refresh Modes

[[refresh-mode-manual]]
====== MANUAL

The view data is never automatically updated.
You must trigger a refresh explicitly via <<sql-refresh-materialized-view,`REFRESH MATERIALIZED VIEW`>> or the Java API.
Use this when you control refresh timing yourself or when source data changes infrequently.

[[refresh-mode-incremental]]
====== INCREMENTAL

After every committed transaction that modifies a source type, ArcadeDB automatically refreshes the view in a post-commit callback.
The refresh is:

* *Transactionally safe*: runs after the source transaction commits successfully; rolled-back transactions do not trigger a refresh
* *Batched per transaction*: multiple record changes in a single transaction result in one refresh, not one per record
* *Per record* for a view whose rows map one to one to source records (see below): only the rows of the source records the transaction changed are refreshed
* A *full refresh* for every other view (aggregates, `GROUP BY`, `ORDER BY`, and so on)

If the refresh fails, the view is marked `STALE` and a warning is logged.
A manual refresh can recover it.

[[refresh-mode-incremental-per-record]]
*Per-record views.* _(Since v26.12.1)_ A `REFRESH INCREMENTAL` view is maintained per record when its query reads a
single source type and has no `GROUP BY`, aggregate, `ORDER BY`, `LIMIT`, `SKIP`, `DISTINCT`, `LET`, `UNWIND`,
`FACETS`, `expand()` or subquery in `FROM`. Each row of such a view then carries a `_sourceRID` column (a LINK to its
source record, with a UNIQUE index), and a commit re-evaluates only the source records it created, updated or deleted:
their rows are updated, created or deleted, and the rest of the view is not touched. The cost of the refresh a commit
owes is proportional to the records it changed, not to the size of the view.

[source,sql]
----
CREATE MATERIALIZED VIEW UserStats
  AS SELECT id AS userId,
            out('HasUploaded').in('Likes').size() AS totalLikes,
            out('FriendOf').size() AS totalFriendships
     FROM User
  REFRESH INCREMENTAL;

SELECT userId, totalLikes, _sourceRID FROM UserStats;
----

* *Link and edge columns refresh only with their own row.* In the view above, a new `Likes` edge shows in
  `totalLikes` when that user's `User` record changes, or at the next `REFRESH MATERIALIZED VIEW`, not on every commit
  to `User` as before v26.12.1. If such a column must stay current, refresh the view on a schedule.
* *`_sourceRID` is visible to readers* (`SELECT *` returns it). A query that already projects a column named
  `_sourceRID`, or reads a type that declares a property with that name through `SELECT *`, keeps the full refresh.
  On a per-record view the name is reserved: a schemaless source record that carries an undeclared `_sourceRID`
  field, or a property of that name declared after the view was created, does not keep its value in the view. Under
  `SELECT *` the link to the source record always wins.
* *Large transactions.* When one transaction changes more source records than
  `arcadedb.materializedViewPerRecordMaxDelta` (default 10000), the pass rebuilds the whole view instead, on the
  committing thread, so the committer still reads its own write.
* *Failures.* A failed per-record pass marks the view `STALE`; the next commit to a source type hands a full rebuild to
  the background scheduler (`ArcadeDB-MV-Scheduler`), so no commit waits on it, and the view stays `STALE` until it
  succeeds. A per-record view that is not `VALID` when the database opens is rebuilt the same way, so it retries at
  every open until a rebuild succeeds.
* *Upgrading an existing view.* Views created before v26.12.1 keep the full refresh. Run
  `ALTER MATERIALIZED VIEW <name> REFRESH INCREMENTAL` to upgrade one that qualifies: it adds the `_sourceRID` column
  and its index and rewrites every row once, so the RIDs of the view rows change. The rewrite runs under the database
  write lock, so other writers wait for it. If it fails, the `ALTER` reports an error but the view stays switched, in
  `ERROR`, and the next source commit or a `REFRESH MATERIALIZED VIEW` rebuilds it.
* *Switching away and back.* `ALTER` to another refresh mode keeps the column, its index and the per-record flag. After
  switching back to `INCREMENTAL`, run `REFRESH MATERIALIZED VIEW`: the view was not maintained in between.

*Recovery after a crash or a leader change.* Changes a per-record view has not applied yet are held in memory and are
lost with the process. The view repairs itself with a full rebuild on the background scheduler, and reads `STALE`
until the rebuild ends:

* on a server outside a cluster, when the database opens after an unclean shutdown, every per-record view is rebuilt
  (after a clean shutdown only the views that are not `VALID`). A `READ_ONLY` open does not rebuild;
* in a highly available cluster, a node that becomes leader rebuilds the per-record views of every open database once
  it has applied all the entries committed before its term. The rebuild writes through the cluster, so the followers
  receive it.

[WARNING]
====
In a highly available cluster, a database that the new leader opens only after the election (for example after it was
closed for inactivity) does not get this rebuild yet: run `REFRESH MATERIALIZED VIEW` on its per-record views (tracked
in issue #11555).
====

*Which types are tracked.* An `INCREMENTAL` view is refreshed when a transaction changes a record of any type its query names, anywhere in the query: the top-level `FROM`, a subquery in `FROM`, and a subquery in `WHERE`, in the projection or in `LET`, at any depth. Each of these types is tracked together with all its subtypes, including subtypes created after the view. They are listed in the `sourceTypes` column of `schema:materializedViews`, and `DROP TYPE` on any of them is refused while the view exists.

*Sources that cannot be tracked.* `REFRESH INCREMENTAL` is refused with an error, on `CREATE MATERIALIZED VIEW` and on `ALTER MATERIALIZED VIEW ... REFRESH INCREMENTAL`, when the query reads a source that no type's record events report: a `TRAVERSE`, a `MATCH`, a function call in `FROM`, a bucket (`FROM bucket:...`), an index, schema metadata (`FROM schema:...`), record ids or parameters in `FROM`. Use `REFRESH MANUAL` or `REFRESH EVERY` for such a view.

Values reached by following a link or an edge from a tracked record (for example `address.city` or `out()`) are not tracked, since they cannot be detected from the query text: a change to the linked record does not refresh the view.

[NOTE]
====
This behavior changed in 26.11.1 (issue #10205). Before, only the type of the first `FROM` identifier was tracked, and only its own records, not those of its subtypes: a change to a type read by a subquery, or to a subtype, left the view out of date while its status stayed `VALID`. Existing views loaded from an older database have their source list completed from their query automatically on open, so they start refreshing on those changes and `DROP TYPE` of those types is refused. An existing `INCREMENTAL` view whose query reads one of the untrackable sources above keeps loading; creating a new one, or switching a view to `INCREMENTAL`, is refused.
====

[[refresh-mode-periodic]]
====== PERIODIC

A background scheduler thread runs a full refresh at the specified interval after each successful refresh completes.
Intervals are specified in seconds, minutes, or hours:

[source,sql]
----
REFRESH EVERY 30 SECOND
REFRESH EVERY 5 MINUTE
REFRESH EVERY 1 HOUR
----

The scheduler uses a single daemon thread (`ArcadeDB-MV-Scheduler`) shared across all periodic views.
If the database is closed, all scheduled tasks are cancelled automatically.

In a highly available cluster only the leader runs the periodic refresh, _since v26.11.1_: it rewrites the view's
records and replicates the rewrite, so the followers receive the refreshed view rather than recomputing it on their own
timer. A follower that is promoted to leader starts refreshing at its next interval.

===== View Status

Each view tracks a `status` field that reflects its current state:

[%header,cols=2]
|===
| Status | Meaning
| `VALID` | Data is up to date with the last refresh
| `STALE` | A refresh failed or was interrupted; data may be outdated
| `BUILDING` | A refresh is currently in progress
| `ERROR` | The last refresh encountered a fatal error
|===

If the database crashes while a view is `BUILDING`, the status is reset to `STALE` on the next startup to signal that the data may be incomplete.

===== Querying a Materialized View

Query a materialized view exactly like any other document type:

[source,sql]
----
SELECT * FROM ActiveUsers
SELECT name FROM ActiveUsers WHERE name LIKE 'A%'
SELECT count(*) FROM RecentOrders
----

===== Java API

*Creating a view*

[source,java]
----
database.transaction(() -> {
    database.getSchema().buildMaterializedView()
        .withName("ActiveUsers")
        .withQuery("SELECT name, email FROM User WHERE active = true")
        .withRefreshMode(MaterializedViewRefreshMode.MANUAL)
        .create();
});
----

Builder options:

[%header,cols=2]
|===
| Method | Description
| `withName(String)` | Name for the view (required)
| `withQuery(String)` | Defining SQL `SELECT` query (required)
| `withRefreshMode(MaterializedViewRefreshMode)` | `MANUAL`, `INCREMENTAL`, or `PERIODIC` (default: `MANUAL`)
| `withTotalBuckets(int)` | Number of buckets for the backing type
| `withPageSize(int)` | Page size for the backing type
| `withRefreshInterval(long)` | Interval in milliseconds for `PERIODIC` mode. Only `PERIODIC` accepts an interval: `create()` refuses one on a `MANUAL` or `INCREMENTAL` view, embedded and remote alike
| `withIgnoreIfExists(boolean)` | When `true`, returns existing view instead of throwing
|===

*Querying schema*

[source,java]
----
Schema schema = database.getSchema();

// Check existence
boolean exists = schema.existsMaterializedView("ActiveUsers");

// Get a specific view
MaterializedView view = schema.getMaterializedView("ActiveUsers");

// List all views
MaterializedView[] views = schema.getMaterializedViews();
----

*Refreshing and dropping*

[source,java]
----
// Programmatic refresh
database.getSchema().getMaterializedView("ActiveUsers").refresh();

// Drop via schema
database.getSchema().dropMaterializedView("ActiveUsers");

// Drop via the view itself
database.getSchema().getMaterializedView("ActiveUsers").drop();
----

*Changing the refresh mode*

[source,java]
----
// Refresh every 5 minutes; pass 0 as the interval for MANUAL or INCREMENTAL
database.getSchema().alterMaterializedView("ActiveUsers", MaterializedViewRefreshMode.PERIODIC, 300_000);
database.getSchema().alterMaterializedView("ActiveUsers", MaterializedViewRefreshMode.INCREMENTAL, 0);
----

`alterMaterializedView()` is the Java form of `ALTER MATERIALIZED VIEW ... REFRESH`. _(Since v26.10.2)_ it works on a
remote database too, where it is sent as that SQL statement, and the embedded and remote calls refuse the same
arguments: a `null` mode or a negative interval (`IllegalArgumentException`) and an interval on a `MANUAL` or
`INCREMENTAL` view (`SchemaException`). A remote `PERIODIC` interval must be a whole number of seconds, as in SQL. In
v26.10.1 and earlier the remote call threw `UnsupportedOperationException`, and the embedded one stored an interval on a
`MANUAL` or `INCREMENTAL` view, where nothing used it.

*Inspecting a view*

[source,java]
----
MaterializedView view = database.getSchema().getMaterializedView("HourlySummary");

view.getName();             // "HourlySummary"
view.getQuery();            // the defining SQL query
view.getRefreshMode();      // MaterializedViewRefreshMode.PERIODIC
view.getStatus();           // "VALID", "STALE", "BUILDING", or "ERROR"
view.getLastRefreshTime();  // epoch millis of last successful refresh
view.isSimpleQuery();       // true when the query has no aggregate, GROUP BY, or subquery or function in FROM
view.getSourceTypeNames();  // every type the query names, at any depth
view.getBackingType();      // the underlying DocumentType
----

===== Behavior and Constraints

* *Backing type protection*: You cannot `DROP TYPE` on a type that backs a materialized view. Drop the materialized view first.
* *The backing type is read-only*: only the refresh of the view writes its rows. `INSERT`, `UPDATE` and `DELETE` on the backing type, `TRUNCATE TYPE` on it (directly, or reaching it with `POLYMORPHIC` from a supertype), `TRUNCATE BUCKET` on one of its buckets and `ALTER TYPE <view> BUCKET -<bucket>` are refused, from SQL, the Java API and every protocol, with a message naming `REFRESH MATERIALIZED VIEW <view>` and `DROP MATERIALIZED VIEW <view>`. Change the source data instead, and refresh. A refused `TRUNCATE` deletes nothing. Reading the backing type and indexing it (`CREATE INDEX ON <view> ...`) are unaffected. _(Since v26.11.1, issue #11020. Before, a `TRUNCATE TYPE` of the backing type emptied the view while it kept reporting `VALID`, and a row inserted into it was answered beside the rows of the query until the next refresh.)_
* *The backing type cannot be extended*: `CREATE ... TYPE <type> EXTENDS <view>` and `ALTER TYPE <type> SUPERTYPE +<view>` are refused, as is a type below another one that extends the backing type, since `SELECT FROM <view>` also returns the rows of its subtypes, which no refresh computed. The backing type itself can still be given a supertype. A database where such a link already exists still opens, logs a warning, and the link can be removed with `ALTER TYPE <type> SUPERTYPE -<view>`. _(Since v26.11.1, issue #11204.)_ In such a database a `DROP TYPE` that would link a sub type directly under the backing type, or under a type below it (dropping `Mid` out of `+Deep -> Mid -> <view>+`), is refused before anything is changed, naming the link to take out first (`+ALTER TYPE `Deep` SUPERTYPE -`Mid`+`); after that the drop goes through. The same holds for the backing type of a continuous aggregate. _(Since v26.12.1, issue #11272. Before, the drop linked the sub type under the backing type.)_
* *Source type protection*: You cannot `DROP TYPE` on a type the defining query reads (any type listed in `sourceTypes`). Drop the materialized view first.
* *Renaming a type*: `ALTER TYPE <source> NAME <new>` on a source type of a view carries the view with it: the source type name the view stores and the `FROM` of its defining query are rewritten to the new name, and the change is saved with the schema. A continuous aggregate follows the rename of its source type the same way, and so does a trigger bound to the type. The rename is refused, before anything moves, when the type is the *backing* type of a view (a view is named after its backing type, so it cannot be renamed on its own) or when the query names the type in a form that cannot be re-pointed with certainty (for example a subquery that reads the same type again): drop the view, rename the type and create the view again. A view defined through an alias of the type keeps working without being rewritten, since the alias survives the rename. _(Since v26.11.1. Before, the rename left the view naming a type that no longer existed: its refresh failed, and `DROP TYPE` on the renamed type was let through. A database that already holds a view in that state is protected from the drop: `DROP TYPE` is refused, naming the view that is out of date, until that view is dropped.)_
* *Name uniqueness*: The view name must not match any existing type or materialized view.
* *Source type validation*: All types referenced by the query, including those in subqueries, must exist when the view is created.
* *Persistence*: View definitions are stored in `schema.json` under a `"materializedViews"` key and survive database restarts. Listener registration for `INCREMENTAL` views and scheduler tasks for `PERIODIC` views are re-established on startup.
* *Transaction safety*: The initial full refresh and all subsequent refreshes run inside their own transactions.
* *Query result columns*: Only non-internal properties (those not starting with `@`) are copied into the backing type during refresh.
* *No schema on backing type*: The backing document type is schema-less; property types are not enforced.

===== Error Handling

* If a post-commit refresh fails (`INCREMENTAL` mode), the view is marked `STALE` and a `WARNING` is logged. The source transaction is unaffected.
* If a periodic refresh fails, the view is marked `ERROR` and a `SEVERE` log entry is written. The scheduler continues running and will retry on the next interval.
* Callback errors in the transaction callback system are logged at `WARNING` level and do not affect the triggering transaction or other callbacks.

===== Limitations

* Only `REFRESH INCREMENTAL` views that qualify as <<refresh-mode-incremental-per-record,per-record>> refresh individual rows. Every other refresh (manual, periodic, or an incremental view with aggregates, `GROUP BY`, `ORDER BY` and so on) rebuilds the whole view.
* No support for cross-database queries in the defining query.
* Server replication: materialized view data lives in the local backing type and is replicated like any other document type in an HA cluster, but refresh triggering is local to the node that executes the write.

===== Example: Sales Dashboard

[source,sql]
----
-- Source type
CREATE DOCUMENT TYPE Sale;

-- A periodic summary refreshed every minute
CREATE MATERIALIZED VIEW SalesByProduct
  AS SELECT product, sum(amount) AS total, count(*) AS count
     FROM Sale
     GROUP BY product
  REFRESH EVERY 1 MINUTE;

-- An incremental view of recent activity (simple query)
CREATE MATERIALIZED VIEW RecentSales
  AS SELECT product, amount, date
     FROM Sale
     WHERE date >= '2026-01-01'
  REFRESH INCREMENTAL;

-- Query the views
SELECT * FROM SalesByProduct ORDER BY total DESC;
SELECT product, amount FROM RecentSales WHERE amount > 1000;

-- Manual refresh after a bulk import
REFRESH MATERIALIZED VIEW SalesByProduct;

-- Teardown
DROP MATERIALIZED VIEW SalesByProduct;
DROP MATERIALIZED VIEW RecentSales;
----
