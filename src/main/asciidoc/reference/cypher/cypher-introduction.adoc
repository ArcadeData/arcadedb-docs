[[cypher-introduction]]
==== Introduction

ArcadeDB provides native support for the https://opencypher.org/[Cypher] query language through a new, high-performance implementation built from the ground up.
This native OpenCypher module uses an ANTLR4-based parser with the official Cypher v25 grammar, providing excellent compatibility and performance.

NOTE: The query language identifiers `opencypher` and `cypher` are interchangeable: both run on the same native OpenCypher engine.

===== Key Features

The native OpenCypher implementation provides:

* **High Performance**: Native direct execution, comparable to native SQL
* **Full Read/Write Support**: MATCH, CREATE, MERGE, SET, DELETE with automatic transaction handling
* **Advanced Pattern Matching**: Variable-length paths with <<cypher-path-mode,path modes>> (WALK, TRAIL, ACYCLIC), OPTIONAL MATCH, multiple MATCH clauses
* **Query Composition**: UNION/UNION ALL for combining results, WITH for query chaining
* **Procedures and Profiling**: CALL for invoking built-in procedures and custom functions, PROFILE for performance analysis
* **Rich Function Library**: 23+ native Cypher functions plus bridge to 100+ ArcadeDB SQL functions
* **Cost-Based Optimizer**: Intelligent query planning with index selection and join ordering
* **100% Test Coverage**: Comprehensive test suite with 295+ passing tests

===== Using OpenCypher

To execute OpenCypher queries, use `opencypher` as the query language identifier.

**From Java API:**

[source,java]
----
ResultSet result = database.query("opencypher",
    "MATCH (p:Person) WHERE p.age >= $minAge RETURN p.name, p.age ORDER BY p.age",
    "minAge", 25);
----

**Through Neo4j BOLT Protocol:**

Connect using any Neo4j driver via the <<bolt-driver,BOLT protocol>>:

[source,java]
----
Driver driver = GraphDatabase.driver("bolt://localhost:7687", AuthTokens.basic("root", "password"));
Session session = driver.session(SessionConfig.forDatabase("mydatabase"));
Result result = session.run("MATCH (p:Person) WHERE p.age >= 25 RETURN p.name, p.age ORDER BY p.age");
----

**Through PostgreSQL Driver:**

Prefix your query with `{opencypher}`:

[source,sql]
----
"{opencypher} MATCH (p:Person) WHERE p.age >= 25 RETURN p.name, p.age ORDER BY p.age"
----

**Through HTTP/JSON API (GET - idempotent queries):**

[source,shell]
----
curl "http://localhost:2480/query/graph/opencypher/MATCH%20(p:Person)%20RETURN%20p"
----

**Through HTTP/JSON API (POST - updates):**

[source,shell]
----
curl -X POST "http://localhost:2480/command/graph" \
  -d "{'language': 'opencypher', 'command': 'CREATE (p:Person {name: \"Alice\", age: 30})'}"
----

===== Using Record IDs (RIDs)

You can use ArcadeDB's <<rid,RecordIDs (RID)>> in Cypher queries to start from a specific vertex.
RIDs in Cypher are always strings, so they must be contained between single or double quotes.

[source,cypher]
----
MATCH (m:Movie)<-[a:ACTED_IN]-(p:Person) WHERE id(m) = '#1:0' RETURN *
----

===== Parameters

OpenCypher supports parameterized queries using the `$paramName` syntax:

[source,cypher]
----
MATCH (p:Person) WHERE p.age >= $minAge AND p.city = $city RETURN p
----

Parameters are passed as key-value pairs after the query string:

[source,java]
----
ResultSet result = database.query("opencypher",
    "MATCH (p:Person) WHERE p.age >= $minAge RETURN p",
    "minAge", 25);
----

===== Automatic Transaction Handling

A write statement (CREATE, SET, DELETE, MERGE, REMOVE, FOREACH, a write procedure) automatically handles its transaction:

* If no transaction is active, the whole statement runs in one transaction, committed when the statement has run to its
  end, as over HTTP and as an implicit transaction in Neo4j. A statement that fails leaves nothing behind, and one that
  meets a concurrent conflict is run again from the committed state, up to `arcadedb.txRetries` times _(since v26.11.1;
  before, each write clause committed its own transaction row by row, so a failing statement kept the writes made before
  the error)_
* If a transaction is already active, the statement runs in it and leaves the commit or rollback to its owner
* A `CALL { ... } IN TRANSACTIONS` subquery still commits each batch on its own, so a statement using one is not run
  again on a conflict

[source,java]
----
// Automatic transaction - the whole statement commits once it completes
database.command("opencypher", "CREATE (n:Person {name: 'Alice'})");

// Manual transaction - you control commit/rollback
database.transaction(() -> {
    database.command("opencypher", "CREATE (a:Person {name: 'Alice'})");
    database.command("opencypher", "CREATE (b:Person {name: 'Bob'})");
    database.command("opencypher", "MATCH (a:Person {name: 'Alice'}), (b:Person {name: 'Bob'}) CREATE (a)-[:KNOWS]->(b)");
    // Commits when lambda completes successfully
});
----

===== Performance Considerations

The native OpenCypher implementation includes a cost-based query optimizer that:

* Automatically selects optimal indexes for node lookups. When several predicates on the same node can use an index
  (an equality, an `IN` list, an `OR` of equalities or a range), each one is costed and the cheapest drives the
  lookup, so a `UNIQUE` index resolved by its whole key is preferred over a non-unique one whatever the properties are
  called or which operator they use. Two candidates of the same cost are decided by the order the query writes them in
  _(since v26.11.1)_
* Uses range index scans for inequality predicates (`>`, `<`, `>=`, `<=`)
* Starts a pattern that has a node with no label from the index of a labelled node _(since v26.12.1)_. In
  `MATCH (p:Person)-[:KNOWS]->(q) WHERE p.id < 500` the unlabelled `q` is reached through the relationship and `p` is
  read by an index seek, an `IN` seek or a range scan, instead of walking every `Person`. Written from the other end,
  `(q)-[:KNOWS]->(p:Person)`, the pattern starts from `p` too. A pattern with no labelled node, a labelled node no index
  serves (the pattern would start from a scan of the whole label) or a variable-length hop into the unlabelled node is
  still planned step by step, as before. The index lookups of this plan ask the read permission of the type, and of its
  subtypes, each time the statement runs, so a user who may not read the type is refused whatever the index holds
* Starts a single fixed-length hop from its far end when the first node has no label and no condition and the far
  node is pinned on every column of a `UNIQUE` index of its label _(since v26.12.1)_, also in a statement planned step
  by step such as a `MATCH` after `UNWIND` or `WITH`. `UNWIND $keys AS k MATCH (x)-[:OF]->(:Doc {key: k})` finds each
  `Doc` through the index and walks its relationships backwards, instead of scanning every vertex of the database once
  per row. The pin can be an inline property map (literals, parameters or a variable bound by an earlier clause) or a
  `WHERE` equality or `IN` list. The written order is kept for an `OPTIONAL MATCH`, a path variable, a variable-length
  hop, a relationship with no type or of a `UNIDIRECTIONAL` type, a non-unique key and a first node that has a label or
  a condition. The rows of a `MATCH` without `ORDER BY` can come in a different order
* Drives a single-hop relationship pattern from the edge type's own index when the `WHERE` clause pins the
  relationship's indexed properties and neither endpoint is selective, e.g.
  `MATCH ()-[t:TRANSFER]->() WHERE t.transactionId IN ['A', 'B'] RETURN t`. An equality, an `IN` list or an
  `OR` of equalities on the same property all qualify, and a leading prefix of a composite index is enough:
  with an index on `(transactionId, date)`, filtering `transactionId` alone walks that prefix of the index
  instead of scanning every edge. The plan shows it as `MATCH EDGE BY INDEX`
* Scans the buckets of the relationship type, sub-types included, instead of walking the edge lists of every vertex,
  for a single-hop pattern whose `WHERE` clause or inline property map requires a property of the relationship to have
  a value _(since v26.12.1)_. `MATCH ()-[e:K]->() WHERE e.w = 3 RETURN count(e)` is answered the way
  `SELECT count(*) FROM K WHERE w = 3` is, and a directed pattern over one type runs in parallel. A comparison
  (`=`, `<>`, `<`, `<=`, `>`, `>=`), `IN`, `IS NOT NULL`, `STARTS WITH`, `ENDS WITH`, `CONTAINS`, `=~`, a bare property
  used as a boolean, an `OR` whose two sides each require a property, and an inline map such as `[e:K {w: 3}]` qualify.
  A statement that only aggregates properties of the relationship with `count`, `sum`, `avg`, `min`, `max`, `collect`,
  `stDev` or `stDevP` and has no grouping key takes the scan without a predicate: `MATCH ()-[e:K]->() RETURN count(e.w)`.
  The plan shows it as `MATCH EDGE BY TYPE SCAN`. The scan reads the records of the type, which
  <<lightweight-edges,lightweight edges>> do not have, so it is used only where no lightweight edge could be in the
  answer: `e.w IS NULL`, `coalesce(e.w, 3) = 3`, `RETURN e`, `RETURN e.w` and `count(*)` without such a predicate keep
  the walk. The walk is also kept for a statement that writes, bound endpoints, a path variable, a variable-length hop,
  an endpoint narrowed by its own properties or by a `WHERE` conjunct of its own, a far node pinned by a `UNIQUE` index
  and a labelled first node that is cheaper to walk, and an index on the relationship property is preferred when the
  `WHERE` clause pins it. The read permission of the relationship type and of the endpoint labels is asked each time the
  statement runs
* Asks the read permission of the type, and of its subtypes, before any index lookup _(since v26.12.1)_: the lookup of
  a labelled node (an equality, an `IN` list or a leading prefix of a composite index) asks it for the label, and
  `MATCH EDGE BY INDEX` asks it for the relationship type and for the labels written on both endpoints. A user who may
  not read one of them is refused whatever the index holds, as a scan of the type refuses him. Before 26.12.1 the node
  lookup was refused only when the index held the value (and answered no rows when it did not), and the relationship
  lookup returned the relationships that end in a type the user may not read
* Expands the second-to-last node of a chain of hops once, instead of once per path that reaches it, when the statement
  reads only the distinct far ends _(since v26.12.1)_. In
  `MATCH (p:Person {id: $id})-[:KNOWS]-(:Person)-[:KNOWS]-(:Person)-[:KNOWS]-(x:Person) RETURN count(DISTINCT x)` every
  friend of a friend is expanded once and every `x` comes once, with relationship uniqueness still enforced, so the
  answer is the one the full walk gives. It applies to one `MATCH` (not `OPTIONAL`) followed by `RETURN`, over a chain of
  two or more hops whose relationships and intermediate nodes have no variable and whose far end has one, when the
  `RETURN` is a `RETURN DISTINCT` without aggregations or aggregates only with `count`, `sum` or `avg` over `DISTINCT`
  arguments and with `min` or `max`. A path variable, `SKIP`, `LIMIT`, `WITH` or a function such as `rand()` keeps the
  full walk. The plan shows it as `ExpandToDistinctEnds`
* Optimizes join order based on cardinality estimation
* Detects bounded patterns for efficient relationship traversal
* Joins the parts of a pattern no relationship connects - `MATCH (a:Person), (c:City)`, or two `MATCH` clauses - on
  the `WHERE` conjuncts that relate them instead of crossing every row with every row. A conjunct
  that reads one part alone narrows that part before the join. Cypher does not fix the order conjuncts are evaluated
  in, so a conjunct that reads one part, like either side of a join key, is evaluated once per row of that part rather
  than per pair, and ahead of the conjuncts written before it: `rand()` there is drawn per row, and an expression that
  can fail, such as `1 / 0`, can fail on a row the written order would have skipped. A `c.property = expression`
  conjunct over an indexed
  property seeks the index once per row of the other part (`IndexNestedLoopJoin` in the plan), which holds nothing in
  memory; any other `left = right` conjunct is answered by a hash join (`ValueHashJoin`). Only parts nothing relates
  are crossed (`CartesianProduct`). The rows a join buffers count against
  <<settings-sql,`arcadedb.queryMaxHeapElementsAllowedPerOp`>> and reserve their heap from the budget all the running
  queries share, `arcadedb.queryMaxHeapRAM`, and past a few thousand rows a query that only reads, or
  only adds entities (`CREATE`, `MERGE` without `SET` actions), holds them by record identity rather than in full
  (`[compact buffer]` in the plan)

For best performance:

* Create indexes on frequently queried properties
* Use labeled nodes in MATCH patterns for faster type filtering
* Prefer specific property constraints over full scans
* Use parameters for queries executed multiple times (enables query plan caching). Since v26.10.2 queries that differ only in the literal values they embed share a cached plan too (see the `queryLiteralParameterization` setting), but parameters also keep values out of the query text
