[[sql-align-database]]
===== SQL - `ALIGN DATABASE`


Executes a distributed alignment of the database. It must be executed on the Leader server. The alignment computes a checksum of
each file and sends them to the replica nodes. Each replica node will compute the checksum on its own files. The files that are
mismatching are requested by the replica to the leader. In the future single pages could be transferred instead of the entire file.

NOTE: Align Database command is available only when the server is running with the <<howto-high-availability,HA module>> active.

*Syntax*

[source,sql]
----
ALIGN DATABASE
----

The command returns which page have been aligned on each server.

*Examples*

* Align the current database.

----
ArcadeDB> ALIGN DATABASE
----

[[sql-alter-database]]
===== SQL - `ALTER DATABASE`


Change a database setting. You can find the available settings in <<settings-sql,Settings>> appendix. The update is persistent.

*Syntax*

[source,sql]
----
ALTER DATABASE <setting-name> <setting-value>

----

* *`&lt;setting-name&gt;`* Check the available settings in <<settings-sql,Settings>> appendix. Since the setting name contains `.`
 characters, surround the setting name with ```.
* *`&lt;setting-value&gt;`* The new value to set

NOTE: Only *database* settings can be set this way. Since v26.10.1 a setting that belongs to the whole server or to the JVM
is refused, naming its scope: use `SET SERVER SETTING` for a server setting, or a `-D` JVM property for a JVM one. Before
v26.10.1 such a value was accepted and saved into the database configuration, where nothing would ever read it back.

NOTE: The value reported back is the one that took effect, which is not always the one you sent: a setting with a valid
range is corrected to fit. For example `arcadedb.maxPageRAM` is reduced when the page cache asked for is larger than the
heap can accommodate.

NOTE: On an HA cluster the changed setting is replicated to every node, which applies exactly that key. A node running
an older build cannot apply it, so during a rolling upgrade the statement is refused with HTTP `409` and the setting is put
back. See <<ha-database-settings,Database settings>> for path-valued settings and for what to do when the statement times
out. _(Since v26.10.2: the setting was written on the node that ran the statement only.)_

*Examples*

* Set the date time format to support milliseconds (the default is 'yyyy-MM-dd HH:mm:ss').

----
ArcadeDB> ALTER DATABASE `arcadedb.dateTimeFormat` 'yyyy-MM-dd HH:mm:ss.SSS'
----

* Set the default page size for buckets to 262,144 bytes. This is useful when importing database with records bigger than the
 default page.

----
ArcadeDB> ALTER DATABASE `arcadedb.bucketDefaultPageSize` 262144
----

[[sql-backup-database]]
===== SQL - `BACKUP DATABASE`


Executes a backup of the current database. The resulting file is a compressed archive using ZIP as algorithm. The archive contains
the database directory without the transaction logs. The backup is executed taking a snapshot of the database at the time the
command is executed. Any pending transaction will not be in the backup archive. ArcadeDB allows to execute a non-stop backup of a
database while it is used without blocking writes or affecting performance. A close requested while a backup is running waits for
the backup to complete, and the database keeps serving in the meantime: the archive is always complete, and the close goes ahead
right after.

[NOTE]
====
Since 26.10.1, one database runs one whole-database maintenance operation at a time: backup, restore, import, export and
`drop database`. A second one on the same database is refused immediately with an `operation in progress` error naming the one
already running, rather than proceeding alongside it - simply retry once the first has finished. Two exceptions: several exports
of one database may run together (they read only), and a `drop database` conflicts with everything, including another drop.

Previously a `drop database` issued during a backup, restore or import could delete the database directory while that operation
was still using it.
====

*Syntax*

[source,sql]
----
BACKUP DATABASE [ <backup-file-url> ]

----

* *`&lt;backup-file-url&gt;`* Optional, defines the name of the backup archive. If not specified, the backup file will
 be `backups/&lt;db-name&gt;/&lt;db-name&gt;-backup-&lt;timestamp&gt;.zip`, where the timestamp is expressed from the year to the millisecond.
 Example of backup file name `backups/TheMatrix/TheMatrix-backup-20210921-172750767.zip`.

[NOTE]
====
`&lt;backup-file-url&gt;` must be a bare file name (e.g. `mybackup.zip`), never a path or a `file://` URL that carries
one. `BACKUP DATABASE` always writes into the server's backup directory so the archive's location cannot be steered
elsewhere through SQL; a value with a directory component - `/`, `\`, or `..` in it - is rejected with `Backup file
cannot contain path change because the directory is specified`. Use the standalone `Backup` class or the embedded
API directly (not through SQL) if a full path is genuinely needed.
====

[NOTE]
====
Since 26.10.1 the backup directory is the one every other backup command uses - the running auto-backup plugin's
configuration, then `config/backup.json` even when the schedule is off, then `arcadedb.server.backupDirectory` - so
an archive written here is visible to `list backups` and reachable by `delete backup` and `restore backup`. See
<<backup-directory-resolution,Where an On-Demand Backup Goes>>.

Previously the statement read `arcadedb.server.backupDirectory` on its own, so with a `config/backup.json` naming a
different directory the archive landed out of reach of those commands and was never retention-pruned. One
consequence of the change: `BACKUP DATABASE` now fails if that configured directory is invalid (absolute, or
escaping the server root), which is the same refusal the other backup commands already gave.
====

[NOTE]
====
Since 26.10.2 the statement applies the retention policy after a successful backup, as `trigger backup` and the
auto-backup scheduler do. Retention works off the archives in `backups/<db-name>` rather than off the databases registered
with the scheduler, so a database that is not named in `config/backup.json` is pruned by the `defaults` retention
(`maxFiles`, or the tiered policy) instead of growing its directory without bound. The archive just written is always kept.

Only archives named `<db-name>-backup-<timestamp>.zip` are subject to retention. An archive you name yourself with
`BACKUP DATABASE 'before-the-upgrade.zip'` is never deleted by it. With the auto-backup scheduler disabled nothing is pruned,
which is the behavior of an on-demand backup without a scheduler.
====

*Examples*

* Execute the backup of the current database with the default filename.

----
ArcadeDB> BACKUP DATABASE
----

[[sql-check-database]]
===== SQL - `CHECK DATABASE`


Executes an integrity check and in case of a repair of the database. This command analyzes the following things:

* buckets: all the pages and records are scanned and checked if can be loaded (no physical corruption)
* vertices: all the vertices are loaded and all the connected edges are checked. In case some edges point to records that have been
 deleted they can be fixed automatically if the `FIX` option is enabled.
* edges: scan all the edges and check the incoming and outgoing links are consistent in the relative vertices. If not, the edges can
 be automatically removed if the `FIX` option is enabled.
* <<timeseries,TimeSeries>> types: every shard's mutable bucket, sealed store and shared tag dictionary is validated, including the
 CRC32 of every sealed block. See <<sql-check-database-timeseries,TimeSeries integrity>> below.
* <<indexes,indexes>>: the structure of each index is validated. A corrupted index is dropped and rebuilt if the `FIX` option is
 enabled, keeping its name and its configuration - a full-text index's analyzers and BM25 parameters, a geospatial index's
 precision, a vector index's dimensions.
* existence constraints: _since v26.10.1_, every record of a type that declares a `MANDATORY` or `NOTNULL` property is checked
 against it. See <<sql-check-database-constraints,Existence constraints>> below.
* cached record counters: _since v26.10.1_, the counter `count(*)` answers from is compared against the records the bucket scan
 actually found. See <<sql-check-database-record-counters,Cached record counters>> below.

NOTE: the index check is *structural*: it validates the index's own pages, not that every record of the type appears in the index.
An index that is intact but incomplete - for example one whose build was interrupted by a crash - is therefore reported as healthy.
If you suspect that, run <<sql-rebuild-index,`REBUILD INDEX`>> on it: rebuilding re-reads every record and also preserves the index
configuration.

When a vertex's edge list is unreadable (for example a lost or corrupted chunk of the adjacency linked list), the `FIX` mode does
not delete anything: every edge record stores its own endpoint identities, so the adjacency list is rebuilt from the surviving edge
records. After the rebuild, a full-scope `FIX` (no `TYPE`/`BUCKET` filter) also reclaims the orphaned edge-list segments the old,
unreachable chains left on disk.

The reverse shape is an *orphan edge record*: an edge record whose `@out` and `@in` are live vertices, but that no vertex's edge
list references, so no traversal reaches it. It is reported as `ORPHAN RECORD` and counted under `unreachableEdgeRecords`.
_Since v26.11.1_ a plain `FIX` relinks it: the edge goes back into the outgoing list of its `@out` vertex and, for a bidirectional
edge type, into the incoming list of its `@in` vertex. The relinked records are counted under `relinkedOrphanEdgeRecords`, and the
adjacency entries written under `reconnectedEdges`. `FIX DELETE ORPHANS` deletes them instead, and takes precedence when given.
Without `FIX` the warning suggests both: `CHECK DATABASE FIX` to relink the edge, or `CHECK DATABASE FIX DELETE ORPHANS` to remove
it. Before v26.11.1 a plain `FIX` left orphan edge records untouched, and `DELETE ORPHANS` was the only repair.
One run relinks a bounded number of orphans to cap its memory; what it leaves is counted under `orphanEdgeRecordsLeftToRelink`,
and the next `FIX` relinks it. A `GraphBatch` flush that failed inside a live process deletes the records it wrote, and logs
the RID of any it could not delete: delete those before a `FIX`, which would otherwise relink edges the caller was told were not
created.

The usual cause is a <<java-batch-importer,GraphBatch>> whose process died (`kill -9`, an OOM kill, a power loss) before `close()`:
the edge records its flushes committed are on disk, but the vertices' head-chunk pointers are only written at `close()`.
`CHECK DATABASE FIX` makes those committed edges traversable without reloading them.

A <<lightweight-edges,lightweight edge>> has no record to be rebuilt from. _Since v26.11.1_ the rebuild carries the lightweight
entries of the part of the dropped list it can still read over into the new one (`salvagedLightEdges`), and rebuilds the
lightweight edges of a bidirectional type stored in the unreadable part from their copy in the other endpoint's list
(`recoveredLightEdges`), as many times as that list holds them. That costs one more walk of the edge lists of every vertex, only
in `FIX` mode and only when a list is rebuilt. A lightweight edge of a unidirectional type is stored in its source's outgoing list
only: one stored in the unreadable part has no other copy and is lost, and the run counts the list under `unsalvageableEdgeLists`
with a warning naming the vertex and the direction. Before v26.11.1 a rebuild dropped every lightweight edge of the list.

The other shape is a *dangling reference*: an adjacency entry that points at a record which no longer exists, typically left behind
by a vertex deleted by an old release, before edge removal became strict. There is nothing to rebuild in that case - the record the
entry names is gone - so `FIX` drops the entry instead.

_Since v26.9.1_, an application that reaches such a record before the repair has run is told so plainly, and always in the same
way. Removing an entry from the edge list of a vertex whose own record is missing, adding one to it, and deleting that vertex
outright all raise `VertexNotFoundException`, a `RecordNotFoundException` (answered as HTTP `404`) that names the vertex and points
at `CHECK DATABASE FIX`. Creating an edge whose *endpoint* is such a record raises it too, naming the endpoint - which is not the
vertex the statement named. It is deliberately *not* a `NeedRetryException`: the record is gone rather than temporarily unreadable,
so a retry can only fail identically, and a job walking possibly-stale references can skip that entry instead of spending its retry
budget and rolling back the whole transaction. An unreadable *chunk* of a vertex that does exist keeps raising the retryable
`ConcurrentModificationException` described above - the two are told apart by which record the failure names.

A `DELETE VERTEX` refused this way is refused before it touches anything: the vertex's record is checked first, so the failure does
not cost a walk over an adjacency list that is about to be rolled back.

IMPORTANT: the same answer now covers the genuinely concurrent case. A vertex that *another* transaction deletes while this one is
removing its edges used to be reported as a retryable `ConcurrentModificationException`; it is a `VertexNotFoundException` like
every other "the vertex is not there", because the record is equally gone either way and a retry could only rediscover that on the
next attempt. An application that wraps its vertex deletes in its own `catch (ConcurrentModificationException)` retry loop no
longer catches that case: catch `RecordNotFoundException` alongside the conflict and treat it as already deleted, which is the
conclusion the loop would have reached after spending its retries.

That up-front check reads the vertex's record, so deleting a vertex needs the `readRecord` permission on its type as well as
`deleteRecord` (see <<groups,groups>>). This is not a new requirement in practice, since every way of obtaining the vertex in
order to delete it already reads it, but a group granting `deleteRecord` alone now fails at the first statement of the delete
rather than part of the way through it.

NOTE: the `RECORD` scope cannot repair a dangling reference. The RID in the message is the record that is missing, so there is no
edge list to rebuild there, and the entry to drop lives on the vertex at the *other* end. No index maps a vertex back to the lists
that reference it, so finding that vertex takes a scan - which is why the message names the database-wide form.

While the check runs, its progress (current step and percentage) is visible live in the <<console,console>>, in Studio, and
through the <<http-progress,HTTP progress endpoint>>. Run `FIX` in a maintenance window: like every repair, it assumes no
concurrent writers.

*Syntax*

[source,sql]
----
CHECK DATABASE [ TYPE <type-name>[,]* ] [ BUCKET <bucket-name>[,]* ] [ RECORD <rid>[,]* ]
              [ FIX ] [ DELETE ORPHANS ] [ DELETE INVALID RECORDS ] [ RECLAIM UNREFERENCED FILES ]
              [ DEEP ] [ COMPRESS ]
----

The optional clauses must appear in the order shown above.

* *`&lt;type-name&gt;`* Optional, if specified limit the check (and the fix) only to the specific types
* *`&lt;bucket-name&gt;`* Optional, if specified limit the check (and the fix) only to the specific buckets
* *`&lt;rid&gt;`* Optional, limits the check to the listed records instead of scanning whole types. Cannot be combined
 with `TYPE` or `BUCKET`. Useful when a single vertex's edge list is broken and a full scan is not worth its cost. The
 listed records must exist: repairing a reference that points at a *deleted* record is a database-wide `FIX`, not this
 scope
* *`FIX`* Optional, if used auto fix the issue found with the check
* *`DELETE ORPHANS`* Optional, requires `FIX`. Removes orphan edge records: edge records whose endpoints are valid
 vertices but which no vertex's edge list references. A clause of its own because the same shape is also produced by a
 vertex that merely lost its head-chunk pointer, whose edges are still recoverable. Without it a `FIX` relinks those
 records into their vertices' edge lists instead _(since v26.11.1; before, it left them untouched)_, and without `FIX`
 the finding is only reported, under `unreachableEdgeRecords`
* *`DELETE INVALID RECORDS`* Optional, requires `FIX`, _since v26.10.1_. Removes the records that do not satisfy their
 own type's existence constraints. A clause of its own because `ALTER PROPERTY ... MANDATORY TRUE` on a type that
 already holds records makes every one of them a finding while they hold real data - see
 <<sql-check-database-constraints,Existence constraints>>. Without it the finding is still reported, under
 `constraintViolatingRecords`
* *`RECLAIM UNREFERENCED FILES`* Optional, requires `FIX`. Deletes files this node holds that no schema component was
 ever built for. Without it the finding is still reported, under `unreferencedFiles`
* *`DEEP`* Optional, adds the checks that decode the stored data rather than reconciling what describes it. Today only
 the TimeSeries pass has a deeper tier - see <<sql-check-database-timeseries,TimeSeries integrity>>. Independent of
 `FIX`: nothing this tier finds is repairable
* *`COMPRESS`* Optional, if used compresses the database with the check, packing every page to reclaim the space a
 deleted or shrunk record left behind. Independent of `FIX`: while it runs, it also removes any record-table slot
 whose declared size cannot fit the page - a physical-corruption shape it walked past and left in place before
 `26.9.1` - so a database compressed with this release repairs that class of corruption even without `FIX`

[[sql-check-database-vector-ids]]
*Vector indexes*

_Since v26.10.1_ the check reads the pages of every `LSM_VECTOR` index and reports one that has two records on the same
vector id. The index appears under `corruptedIndexes`, and `warnings` carries how many records are affected and the
first few RIDs, each with the record that took its id.

Such an index never keeps its persisted graph. A graph build counts both records, while every load of the same pages
keeps only the one written last, so the graph holds more nodes than the load has live vectors and is rejected as stale
on the next load. Each search that finds it rejected waits for a full rebuild of the graph, and the rebuild produces
the same graph again. The record that lost its vector id is not returned by a vector search until its vector is indexed
again. A graph build now logs those records by RID and keeps one record per id, which ends the loop but does not
restore them.

While an index has records left out this way it does not compact, because a compaction would erase the shared ids from
the pages. The index keeps growing until it is rebuilt. `getStats()` exposes `compactionBlockedBySharedIds` and
`recordsLeftOutBySharedIds` so this can be monitored. The check reads every page of each vector index and holds that
index's read lock while it does, so writes to the index wait for the scan.

`CHECK DATABASE` alone only reports. `FIX` rebuilds the index from the records, which gives every record that holds an
embedding a vector id of its own. The rebuild reads every vector of the type, so on a large index it takes as long as
a `REBUILD INDEX`: run it off-peak. In a cluster the statement runs on the leader, wherever it is issued, and the
rebuilt index reaches the followers as replicated data like any other `FIX` of an index.

[[sql-check-database-constraints]]
*Existence constraints*

_Since v26.10.1_ the check also asks a schema question: does every record satisfy the `MANDATORY` and `NOTNULL`
constraints its own type declares? It is the one question nothing else in the database could answer, and a record that
fails it is not merely untidy - every later write to it fails, because the update path validates the whole document,
so the record reads as broken to the application long before anyone thinks to look at the schema.

A record can end up in that state three ways, and only the first is a fault:

* an openCypher `CREATE`/`MERGE` pattern commits the record before the `SET` that completes it has run - which is what
 makes the standard `MERGE (n:L {id: $id}) SET n.prop = $v` upsert work the way it does in Neo4j - and the process
 dies, or the connection is killed, before the end of the statement;
* a `RESTORE DOCUMENT`/`VERTEX`/`EDGE` run by a release older than `26.9.1`, which did not apply the schema contract;
* a schema change that no existing record was measured against: `ALTER PROPERTY ... MANDATORY TRUE` on a type that
 already holds records, which does not validate them, or renaming a `MANDATORY` property, which relabels the schema
 and leaves every record that predates it carrying the old name. Every one of them becomes a finding while holding
 data that is exactly as real as it was the day before the DDL ran.

Because the third is legitimate and the state it leaves is identical to the first, the *removal is a clause of its
own*: a `FIX` that deleted by default would answer a DDL by destroying the type's contents. Reporting is always on.

There are two repairs, and which one is right depends on whether the records hold data:

* complete the record with a **single** `UPDATE` supplying every missing property. It has to be a single statement -
 the write path validates the whole document, so supplying two missing mandatory properties in two statements fails on
 the first;
* remove the records with `CHECK DATABASE FIX DELETE INVALID RECORDS`.

The two are safe to use together, including at the same time: the repair re-reads and re-checks every record inside
the transaction that deletes it, so a record an `UPDATE` completed while the check was running is reported and left
in place rather than deleted. A removal a `beforeDelete` trigger refuses is reported too, and not counted as removed.
The removal is committed in batches sized by `arcadedb.checkDatabaseRepairBatchPages`, like every other
`CHECK DATABASE ... FIX` repair, so a bulk removal stays inside the replicated-entry limit under
<<howto-high-availability,HA>>.

The check costs nothing on a database whose types declare no such constraint: the types to check are resolved from the
schema before a record is read, so a database with none asks no question at all and its report simply says zero.
_Since v26.10.2_ a run that only reports asks the question while it decodes the content of each record, which every run
does anyway, so a constrained type is not read a second time and the run has no `Checking existence constraints` step.
`FIX DELETE INVALID RECORDS` keeps that step: its delete passes need a scan of their own.

[[sql-check-database-record-counters]]
*Cached record counters*

`SELECT count(*)` does not scan: every bucket keeps a record counter that each commit folds its delta into, and the
counter is what the query answers from. That counter is persisted in the database's `statistics.json` and restored
when the database is opened, so a counter that goes wrong stays wrong across restarts and nothing recomputes it until
something invalidates it.

_Since v26.10.1_ the bucket pass compares the two. It already reads every slot of every bucket, so the authoritative
number is in hand, and a disagreement is reported as an error naming the bucket, both numbers and the direction:

----
cached record count of bucket 'Order_0' is 10869 but the bucket holds 10906 records:
count(*) on this bucket under-reports by 37; run CHECK DATABASE FIX to recompute the counter
----

`FIX` recomputes it - the counter is invalidated, and the next `count(*)` rescans and republishes it. A read-only run
only reports, and the report carries `staleRecordCounters` and, under `FIX`, `staleRecordCountersFixed`. Both count
*buckets*, not records: one per bucket whose counter disagreed, whatever the size of the disagreement. They sit next to
record tallies such as `totalActiveRecords` in the same JSON, so the distinction is worth reading twice.

This is the symptom to look for when `count(*)` disagrees with a forced full scan such as
`SELECT count(*) FROM <type> WHERE @rid IS NOT NULL`, in *either* direction. On a replicated database the drift is
per node and per bucket, so the replicas disagree with each other while holding identical data, which looks exactly
like <<howto-high-availability,HA>> state divergence until a full scan rules it out.

NOTE: a bucket whose counter has never been computed is not reported - there is nothing to be wrong yet - and neither
is one the current transaction has pending changes on, nor one this same run has just repaired, since in those cases
the two sides of the comparison describe different moments. The same applies to a read-only check that another
transaction committed into while it was scanning, so running `CHECK DATABASE` on a live node under write load does not
raise a false alarm.

*Counters written by a release older than 26.10.1*

Releases up to and including `26.9.1` could fold a replicated transaction's record-count delta twice when a
<<howto-high-availability,Raft>> entry was replayed on a node that had been restarted *cleanly*, which includes every
rolling upgrade and every Kubernetes pod rotation. Nothing in `statistics.json` says which counters that happened to,
so `26.10.1` does not trust any of them: the file now carries a format version, counts written without one are
discarded when the database is opened, and each affected bucket recomputes on its next `count(*)`. That is one extra
bucket scan, once, and the marker is written back on the next clean close. A `WARNING` in the server log says how many
buckets it applied to, so the first `count(*)` that changes after an upgrade is not a mystery.

[[sql-check-database-timeseries]]
*TimeSeries integrity*

A TimeSeries type has neither record buckets nor indexes, so it is walked by a pass of its own that reads the three
on-disk formats it owns: the mutable bucket (`.tstb`), the shared tag dictionary (`.tstd`) and the sealed store
(`.ts.sealed`). The default tier reconciles every header and directory against the data it describes and verifies the
CRC32 of every sealed block - which means it reads the whole sealed file, the same cost class as the record scan the
check already runs over every bucket. A block is otherwise CRC-checked only on the first read that touches it, so a
block nothing queries is a block nothing verifies.

`DEEP` adds the checks that have to decompress. A CRC proves the bytes are the bytes that were written; it proves
nothing about whether they mean what the block claims. Three things every read path answers queries from, without ever
looking at a value, are verified only under `DEEP`:

* the block's timestamps are sorted -- the range iterator binary-searches them, so an unsorted block silently returns a
 subset of the rows that match
* the block's declared per-column min/max/sum are what its values actually add up to -- aggregation push-down answers
 `MIN`/`MAX`/`SUM`/`AVG` straight from them without decompressing
* the block's declared distinct tag values cover the values it holds -- block pruning skips a whole block whose
 declaration does not list the value being filtered on

Each of those, when wrong, produces a wrong answer rather than an error, so nothing else in the engine reports it.

`FIX` repairs only what is *derived* and never a sample: the mutable bucket's page-0 counters, the sealed header's
block count and global timestamp bounds, and the tail of an interrupted sealed append. Those matter beyond tidiness - a
wrong global bound is read straight out of the header when the file is opened, so a range query pruned against it
silently misses data the file holds, and a tail no reader can see also hides every block appended after it.

A sealed block that fails its CRC, or that `DEEP` finds inconsistent, is reported and left untouched. It is the only
copy of the samples in it, so discarding it is a decision for an operator, who under <<howto-high-availability,HA>> can also rebuild a
sealed store by recompacting from the replicated mutable pages.

*Examples*

* Execute the integrity check of the entire database without fixing any issue found.

----
ArcadeDB> CHECK DATABASE
----

* Execute the integrity check of the types 'Account' and 'Bill' without fixing any issue found.

----
ArcadeDB> CHECK DATABASE TYPE Account, Bill
----

* Execute the integrity check only on the bucket 'Account_Europe' without fixing any issue found.

----
ArcadeDB> CHECK DATABASE BUCKET Account_Europe
----

* Execute the integrity check of the entire database and auto fix any issues found.

----
ArcadeDB> CHECK DATABASE FIX
----

* Execute the deeper integrity check, which decodes the stored TimeSeries data instead of only reconciling what
describes it.

----
ArcadeDB> CHECK DATABASE DEEP
----

* Execute the deeper check on one TimeSeries type, repairing the derived counters it finds wrong.

----
ArcadeDB> CHECK DATABASE TYPE SensorReading FIX DEEP
----

[[sql-export-database]]
===== SQL - `EXPORT DATABASE`


Exports a database in the `exports` directory under the root directory where ArcadeDB is running.

*Syntax*

[source,sql]
----
EXPORT DATABASE [<url>] [WITH ( <setting-name> = <setting-value> [,] )* ]

----

* *`&lt;url&gt;`* Optional, defines the location of the file to export. Use:
 ** `file://` as prefix for files located on the same file system where ArcadeDB is running. For security reasons, it is not possible to provide an absolute or relative path to the file
 ** By default the file name is set to `exports/<db-name>-export-<timestamp>.<format>.tgz`.
* *`WITH`* Optional settings as comma-separated key/value pairs:
 ** *`format`* The format of the export. Default is `jsonl`.
  *** *`jsonl`* exports in https://jsonlines.org/[JSONL] format - a newline-delimited JSON variant
  *** *`graphml`* exports in the popular http://graphml.graphdrawing.org/[GraphML] format. GraphML is supported by all the major Graph DBMS. GraphML has no type for collections and many scalar types: ArcadeDB writes such values as text with an `arcadedb:type` attribute that its own GraphML import reads back (see the note below). Using `graphson` instead of `graphml` is recommended
  *** *`graphson`* exports in the https://tinkerpop.apache.org/docs/current/dev/io/#graphson[GraphSON] format supported by all the major Graph DBMS
+
`graphml` and `graphson` are provided by the optional `arcadedb-gremlin` module. Without it on the classpath the
export is refused, naming the format and the module. _(Since v26.10.1: a failed `graphml` lookup could fall through
to the GraphSON exporter and write a GraphSON archive into the file you named `.graphml`.)_
 ** *`overwrite`* Set to `true` to overwrite the export file if it already exists. Default is `false`.

[NOTE]
====
Since 26.10.1 an export claims its target file for its duration, so two exports that resolve to the same file no longer write
into it at the same time - the second one fails immediately with `Another export to '<file>' is already in progress` instead of
producing a corrupt archive. This applies with `overwrite = true` as well, which previously skipped the check altogether.

The claim is held in a sidecar file next to the target, so an export file name ending in `.exporting` is rejected as a reserved
name. A running export now also publishes its progress, so it is visible on the progress endpoint, in the console and in Studio.
====

[NOTE]
====
Since 26.9.1 the `jsonl` export includes TIMESERIES types: their definition (columns, shards, precision, retention,
compaction interval and downsampling tiers) and their samples, so a JSONL export is a complete backup of a
TIMESERIES type. Earlier versions wrote a file that could not be imported at all when the database contained one.

The same release also restores type-level `CUSTOM` metadata, type aliases and the bucket-selection strategy on
import, and stops writing each vertex's edge identifiers into the export - no importer ever read them, and on a
densely connected graph they were the bulk of the file. Edges are unaffected and are rebuilt as before.
====

[NOTE]
====
Since 26.10.1 importing a `jsonl` export also restores the parts of the schema that live outside the types:
triggers, materialized views, continuous aggregates, `DEFINE FUNCTION` libraries and module extensions. The export
has always contained them; earlier versions simply skipped them on import and still reported success.

They are restored after the records, so a restored trigger does not fire again for data the source database had
already processed. If one of them cannot be recreated - a trigger whose type no longer exists, for example - it is
counted as a warning and the rest of the restore still completes.

On an HA cluster these schema members are restored as one schema change, which holds the database write lock while it
runs and replicates to every node. _(Since v26.10.2: they reached only the leader's schema, so the followers, and a new
leader after a failover, had the imported types and records but no triggers, views, aggregates or functions.)_

Installing a `JAVASCRIPT` or `JAVA` trigger, or a `js` function library, from an imported file requires the same
`updateSecurity` permission that creating one by hand does, since either is code that runs inside the server.
====

[[sql-export-jsonl-value-fidelity]]
[NOTE]
====
Since 26.11.1 a `jsonl` export and import round trip keeps more of the database as it was (issue #10201):

* *Links to records that are not in the export.* A link whose target is not part of the export (the record was deleted before the export, or excluded by `includeTypes`, `excludeTypes` or `includeRecords`) is set to `null` on import. Inside a `LIST OF` or `MAP OF` property, which cannot hold `null`, the element or entry is dropped. The import counts them as `danglingLinks` in its result and logs a warning. If the property is `MANDATORY` or `NOT NULL` the record fails like any other record error. Before, such a link kept its old RID, which after the import named another record.
* *Values with no declaration keep their type.* Undeclared properties, elements of untyped `LIST` and `MAP` properties, and properties of embedded documents are restored with the type they had: a `DECIMAL` keeps its scale, `LONG`, `SHORT`, `BYTE` and `FLOAT` stay themselves, dates and datetimes keep their full precision, `BINARY` values and primitive arrays stay arrays, and undeclared links stay links and are remapped to the imported records. The export (format version 2, `exporterVersion` 2 in the `info` line) writes, beside a record's `p` properties, a sparse type tree under the key `y` (tokens such as `LONG`, `DATETIME`, `LINK`, `BINARY`, `ARRAY_OF_FLOATS`, `EMBEDDED`; an array of per-element types for a list; an object of per-entry types for a map). Before, these values came back as whatever JSON parsed them into (an `INTEGER` or `DOUBLE`, a string, a list). A map with a `t` key is no longer mistaken for an embedded document.
* *Bucket count.* Each type is recreated with the number of buckets it had in the export (`BUCKETS n`, including 0 for an abstract type). Before, it got the default bucket count.
* *Declared lists and maps (issue #10391).* A `LIST OF` or `MAP OF` property is restored for every element type. Before, a declared `LIST OF DATE`, `MAP OF DATE`, `LIST OF BINARY`, `MAP OF BINARY`, `LIST OF DATETIME_MICROS` / `DATETIME_NANOS`, `LIST OF ZONED_DATETIME`, `MAP OF DOUBLE` or `MAP OF FLOAT` (holding a `NaN` or an infinity) aborted the import of the whole database, and a `MAP OF DECIMAL` lost the scale of its values (`3.70` came back `3.7`). A declared `ZONED_DATETIME` property, and a `float[]` or `double[]` holding a `NaN` or an infinity, are restored as well, and so is a `MAP OF STRING` that has a `t` key. A `LIST OF` or `MAP OF` whose elements the declaration reads back exactly (`BOOLEAN`, the integer types, `FLOAT`, `DOUBLE`, `DECIMAL`, `STRING`, `DATETIME`, `LINK` and the like) is written as it was, with no type tree, so the export of a schema-full database does not grow; any other element type is written with the tree. A file exported by 26.10.x imports where its data allows: its `MAP OF DECIMAL` keeps the scale its text carried, and its `LIST OF DATE`, `MAP OF DATE`, `LIST OF BINARY` and `MAP OF BINARY` are read back from the declaration. A `NaN` or an infinity inside a map or a `float[]` / `double[]` was written as `null` by that export, and stays `null`.
* *Links to records exported later, edge constraints and extreme dates (issue #10483).* The export writes every vertex before every document, so a `LINK OF T`, `LIST OF T` or `MAP OF T` (T a record type) can point at a record the import has not reached yet. The record is saved with the check of the link's target type suspended, and the link is resolved and the whole record validated again once every record is in: a link to a record of the wrong type still fails the import. Before, the check ran on the identity the target had in the source database, which in the new one names a record of another type, and the import aborted. A `MAP OF LINK` with a `t` key has its links remapped like any other. An edge is created with its properties, so an edge type with a `MANDATORY` or `READONLY` property imports. A `LIST OF DATE` or `MAP OF DATE` holding a date beyond about 292 million years from 1970 (`LocalDate.MAX`, `LocalDate.MIN`) is exported as its ISO text; before, the export skipped the record and failed.

Files exported by older versions have no `y` key and import exactly as before.
====

[[sql-export-graph-formats-value-fidelity]]
[NOTE]
====
Since 26.11.1 the `graphson` and `graphml` exports write every property value (issue #10202):

* *GraphSON.* A `BYTE`, `SHORT`, `DECIMAL`, date or datetime property no longer makes the export of the whole database fail. Such values are written with TinkerPop's extended `gx:` types (`gx:Byte`, `gx:Int16`, `gx:BigDecimal`, `gx:LocalDate`, `gx:LocalDateTime`, ...), and `BINARY` values (`arcadedb:Binary`, base64), primitive arrays (`arcadedb:FloatArray`, ...) and Cypher durations with ArcadeDB's own `arcadedb:` types. `IMPORT DATABASE` reads them back with their types. A reader outside ArcadeDB needs TinkerPop's `GraphSONXModuleV3`, as for any GraphSON file with `gx:` types, and cannot read the `arcadedb:` types. Links are written as plain RID text.
* *GraphML.* The export is still standard GraphML in TinkerPop's layout (`labelV` / `labelE` keys), readable by TinkerPop and other GraphML tools. A key is declared with a GraphML type (`boolean`, `int`, `long`, `float`, `double`, `string`) only when all its values share it. A value GraphML has no type for (`BYTE`, `SHORT`, `DECIMAL`, dates, `BINARY` as base64, arrays, lists, and maps as JSON text) is written as text with an `arcadedb:type` attribute (namespace `https://arcadedb.com/xmlns/graphml`), which ArcadeDB's GraphML import reads back to the original type; other tools ignore the attribute and read the text. `BINARY` and `float[]` values are no longer written as Java identity strings (`[B@...`), and a key whose values have different types no longer aborts the import with a `NumberFormatException`. Links are written as plain RID text and imported as strings.
====

*Examples*

* Export the current database under the `exports/` directory with the default format and filename:

[source,sql]
----
EXPORT DATABASE
----

* Export the current database to a specific file:

[source,sql]
----
EXPORT DATABASE file://database.jsonl.tgz
----

* Export the current database in GraphSON format, overwriting any existing file:

[source,sql]
----
EXPORT DATABASE file://Movies.graphson.tgz WITH format = 'graphson', overwrite = true
----

* Export overwriting a previously exported file without specifying a URL:

[source,sql]
----
EXPORT DATABASE WITH overwrite = true
----

NOTE: A `jsonl` export of a <<timeseries,TimeSeries>> type records each column's compression codec, because it
cannot be worked out again from the column's data type alone. _(Since v26.10.1)_ importing such an export into a
remote database preserves that codec exactly, even if the default codec for that data type changed between the
two versions. Earlier versions could silently give the restored column the newer default instead.

[[sql-import-database]]
===== SQL - `IMPORT DATABASE`


Executes an import of the database into the current one. Usually an import database is executed on an empty database, but it is
possible to execute on any database. In case of conflict (unique index key already existent, etc.), the conflicting records will not
be imported. The importer automatically recognize the file between the following formats:

* *OrientDB* database export
* *Neo4J* database export
* *GraphML* database export. GraphML has no type for collections and many scalar types; values exported by ArcadeDB carry an `arcadedb:type` attribute that restores their type (see <<sql-export-graph-formats-value-fidelity,the note on graph formats>>). Using GraphSON instead of
 GraphML is recommended
* *GraphSON* database export
* *JSON* documents or responses
* *JSON Lines* documents or responses

*Syntax*

[source,sql]
----
IMPORT DATABASE <url> [WITH ( <setting-name> = <setting-value> [,] )* ]
----

* *`&lt;url&gt;`* Defines the location of the file to import. Use:
 ** `file://` as prefix for files located on the same file system where ArcadeDB is running. The path is resolved against the directory where ArcadeDB is running, so a file written by `EXPORT DATABASE` (which writes to `exports/`) is read back with `file://exports/<file-name>`.
 ** `https://` and `http://` as prefix for remote files.

*Examples*

* Import into the current database an export made with `EXPORT DATABASE file://mydb.jsonl.tgz`
[source,shell]
----
IMPORT DATABASE file://exports/mydb.jsonl.tgz
----

* Import the public OpenBeer database available as demo database for OrientDB and exported in TGZ file
[source,shell]
----
IMPORT DATABASE https://github.com/ArcadeData/arcadedb-datasets/raw/main/orientdb/OpenBeer.gz
----

* Import the Movie database used in Neo4j's examples:
[source,shell]
----
IMPORT DATABASE https://github.com/ArcadeData/arcadedb-datasets/raw/main/neo4j/movies.graphson.tgz
----

* Import a JSON response into document type `mytype`
[source,shell]
----
IMPORT DATABASE http://echo.jsontest.com/key/value/one/two WITH documentType = 'mytype'
----

* Test data source
[source,shell]
----
IMPORT DATABASE http://echo.jsontest.com/key/value/one/two WITH probeOnly = true
----

* Import a graph from CSV, with vertices in a `vertices.csv` which contains a column `Id`,
  and edges in a `edges.csv` which contains columns `From` and `To`,
  both placed in the ArcadeDB base folder:
[source,shell]
----
IMPORT DATABASE file://empty.csv WITH vertices="file://vertices.csv", verticesFileType=csv, typeIdProperty=Id, typeIdType=Long, edges="file://edges.csv", edgesFileType=csv, edgeFromField="From", edgeToField="To"
----

*Result*

The statement returns a single row with a `result` column: `OK` when the import completed, or `FAIL` when the
source or one of the settings could not be used, in which case a `reason` column explains why. Any other failure
raises an error.

_(Since v26.10.1: the `FAIL` answer was overwritten with `OK` before it reached the client, so an import of an
unusable source reported success with no rows and no statistics. Scripts that check `result` now detect these
failures.)_

See also <<importer,Importer>> for a description of the settings.
