[[upgrade]]
==== Upgrade ArcadeDB

ArcadeDB automatically upgrades a database to a newer on-disk format when a newer version of ArcadeDB opens it.
The migration is transparent and happens lazily on first open, so the only operator step is to point the new binaries at your existing data.

[[upgrade-breaking-changes]]
===== Breaking changes

This section lists behavior changes that may require action when upgrading.

[discrete]
====== 26.12.1 - A user name is checked when a user is created

Creating a user, by any route (Studio, `POST /api/v1/server/users`, the `create user` server command, the console, the Cypher `CREATE USER` statement, or a credential of `arcadedb.server.defaultDatabases` that carries a password), now refuses a name with leading or trailing whitespace, two whitespace characters in a row or a control character, with a message that says why. Any other name is accepted as before. A request that a replica relays to the leader under the name of the user who sent it needs a name made of printable ASCII characters, with no leading or trailing space and no two spaces in a row, and fails with `400` otherwise (see <<ha-security,HA Security>>).

*Impact:* a script that creates users from names it did not trim now fails on a name with a trailing space instead of creating a user under it. A user already stored under a name that creation would now refuse keeps working on the server that holds it. On a cluster, a user whose name has a character outside printable ASCII (an accented letter, for example) gets `400` on a request that a replica must relay to the leader.

*Action:* trim the names a provisioning script passes, and on a cluster name the users that send requests through a replica with printable ASCII characters. See <<users,Security - Users>>.

[discrete]
====== 26.12.1 - `ts.movingAvg()` refuses a window that is not a whole number of at least 1

`ts.movingAvg(value, window)` read a window of `0` or less, or an options map without `window` (`{}`), as a window of 1, so the "moving average" was the raw, unaveraged series, and truncated a fractional window such as `2.5` to 2 (issue #12755). It now refuses each of them, and `null`, with an error such as `ts.movingAvg() requires a <window_size> of at least 1, but received 0`. A whole window of 1 or more is unchanged, as a number, a numeric string (`'2'`) or `{window: n}`, and a window larger than the data still averages whatever rows there are.

*Impact:* a query whose window came out as `0` or negative (a parameter, or a ratio that rounds to 0), had a fraction, or used `{}`, now fails instead of returning the raw series or a window of another size.

*Action:* pass a whole number of rows, at least 1, as the window. The window is read once, from the first row of the aggregation.

[discrete]
====== 26.12.1 - openCypher `toString()` refuses a `BINARY` value and `convert.toJson()` writes it as an array

`toString()`, `toStringOrNull()` and `apoc.convert.toJson()` of a `BINARY` value (a byte array, such as a `BINARY` property or a bytes parameter) answered Java's identity text of the array, for example `[B@e044818`, which changes from row to row and from run to run (issue #12780). `toString()` now refuses it with `TypeError: InvalidArgumentValue - toString() cannot convert byte[]`, as it does for a list, `toStringOrNull()` answers `null`, and `toStringList()` answers `null` for such an element. `apoc.convert.toJson()` answers the JSON array of the signed bytes (`[1,-1]`), the text it already gave a byte array inside a map. Indexing into a `BINARY` value is still refused, and its message now says `byte[]` instead of `LIST<ANY>`.

*Impact:* a query that called `toString()` on a `BINARY` value now fails instead of returning the meaningless text, and a value stored from it keeps the old text.

*Action:* none for a query that did not rely on the identity text. To get text from a `BINARY` value, use `apoc.convert.toJson()` or encode it with the SQL function `encode(value, 'base64')`.

[discrete]
====== 26.12.1 - The `text.*` functions answer what APOC answers

Fifteen `text.*` functions, documented as APOC compatible, answered differently from APOC 5.26 on ordinary input and now answer the same (issue #12104; see <<ext-fns-text,Text Functions>>). The ones a query can notice:

* `text.replace()` and `text.split()` read the second argument as a Java regular expression, where it was literal text. `text.split()` drops the empty pieces at the end (`'a,'` is `['a']`) unless the new third argument `limit` is negative, and `text.split('a.b.c', '.')` is `[]`. The openCypher `replace()` and `split()` and the SQL `.replace()` and `.split()` are unchanged and literal.
* `text.charAt()` answers the code point (`'hello', 1` is `101`), not the one-character string, and `text.code()` takes a code point and answers the string (`65` is `'A'`), where it answered the code of the first character of its argument.
* `text.jaroWinklerDistance()` answers the distance, 1 minus the similarity: 0.0 for equal strings.
* `text.format()` takes its values as one list, `text.format('%s %d', ['a', 1])`, and an optional language for the separators of numbers.
* `text.snakeCase()` joins the words with `-` (`'fooBarBaz'` is `foo-bar-baz`), `text.slug()` keeps the case and the non-ASCII letters (`'Hello World'` is `Hello-World`), `text.join()` writes a `null` element as `null`, and `text.hexValue()` is upper case and zero-padded (`255` is `00FF`).
* `text.sorensenDiceSimilarity()` compares the bigrams of each word as a multiset (`'aa'` and `'aaaa'` is 0.5) and takes an optional language tag, `text.camelCase()` and `text.upperCamelCase()` no longer capitalize the first word after a leading separator, and `text.capitalizeAll()` and `text.decapitalizeAll()` split the words at spaces only and trim the result.

*Impact:* a query that used `text.replace()` or `text.split()` with a delimiter that is a regular expression operator (`.`, `|`, `(`, `[`, `$`) matches something else, or fails to compile the pattern. A filter such as `text.jaroWinklerDistance(a, b) > 0.85` now keeps the dissimilar strings. `text.format()` with the values as separate arguments reads the first as the one value and the second as the language, so a format with several specifiers fails. A stored or compared value made with `text.snakeCase()`, `text.slug()` or `text.hexValue()` changes.

*Action:* escape the regular-expression characters of the delimiter (`'\\.'` for a dot) or use the openCypher `split()` and `replace()`, write `text.jaroWinklerDistance(a, b) < 0.15` for `> 0.85`, pass the values of `text.format()` as a list, and regenerate the values made with the changed functions.

[discrete]
====== 26.12.1 - `create.vNode`, `create.vRelationship`, the `meta.*` procedures and `path.slice()` answer what APOC answers

These functions and procedures, documented as APOC compatible, now answer what APOC 5.26 answers (issue #12109):

* `create.vNode()` and the `nodes` and `relationships` of `meta.graph()` are virtual nodes and relationships, where they were maps with `_type`, `_id` and `_labels` keys. `labels()`, `type()`, `properties()` and `id()` work on them, and `id()` is negative. `create.vRelationship()` reads its arguments in the documented order `(startNode, type, properties, endNode)`, where it read `(startNode, type, endNode, properties)` and failed on the documented order. The `CALL create.vNode(...) YIELD node` and `CALL create.vRelationship(...) YIELD rel` forms answer the element instead of `null`.
* The third argument of `path.slice()` is a length, where it was an end index: `path.slice(p, 1, 1)` is the second relationship, `path.slice(p, 0, -1)` the whole path, and `path.slice(p)` is accepted.
* `meta.stats()` yields APOC's columns (`nodeCount`, `relCount`, `labels`, ...), and counts each node once, where a node of a type with supertypes was counted once per supertype. `meta.nodetypeproperties()` and `meta.reltypeproperties()` list the properties found in the data too, not only those declared in the schema, write `nodeType` and `relType` as ``:`Name` ``, and name the value types as APOC does (`Long` and `Double` instead of `Integer` and `Float`). `meta.graph()` answers one relationship per start label, type and end label.

*Impact:* a query that read the `_labels` or other keys of the old maps, called `create.vRelationship()` with the end node third, used `path.slice()` with an end index, or compared `nodeType` or `propertyTypes` with the old values answers differently or fails. `meta.stats()` and `meta.graph()` read every relationship record, so on a large graph they take longer than before.

*Action:* use `labels(n)` and `n.prop` on the virtual elements, pass the end node of `create.vRelationship()` last, pass the length (`end - start`) as the third argument of `path.slice()`, and update the comparisons with the new `nodeType` and `propertyTypes` values. `YIELD value` of `meta.stats()` still works. See <<ext-fns-schema-meta,Schema & Meta Procedures>>, <<create-v-node,create.vNode()>> and <<path-slice,path.slice()>>.

[discrete]
====== 26.12.1 - An openCypher shortest path from a node to itself answers only a minimum of zero

`shortestPath()` and `allShortestPaths()` whose start and end are the same node answered the zero-length path also when the pattern requires at least one hop: `[*]`, `[*1..]` or a relationship without a quantifier (issue #11913). That path is shorter than the pattern allows. Now only a written minimum of zero (`[*0..]`, `[*0..2]`) answers it; any other pattern has no row for that pair, and in the expression form `shortestPath(...)` returns `null` and `allShortestPaths(...)` an empty list.

*Impact:* a query such as `MATCH (a), (b) MATCH p = shortestPath((a)-[*]->(b))` no longer returns the rows where `a` and `b` are the same node, and a count or a minimum length over such rows changes.

*Action:* write `[*0..]` where the zero-length path of a node to itself is wanted. See <<cypher-compatibility,shortestPath() and Hop Bounds>>.

[discrete]
====== 26.12.1 - An openCypher pattern predicate over a null variable is false

A pattern predicate such as `WHERE (x)-->()`, `exists((b)-->(x))` or `WHERE NOT (x)-->()` that names a node or relationship variable an `OPTIONAL MATCH` left null treated that variable as any node, so it was true whenever the pattern held somewhere in the graph (issue #13124). It is now false, and its `NOT` true, as Neo4j answers. A variable not in scope at all still stands for any node, and `EXISTS { }` subqueries and pattern comprehensions are unchanged.

*Impact:* rows where the variable is null are no longer kept by the positive predicate and are now kept by `NOT` of it, so an anti-join written as `OPTIONAL MATCH ... WHERE NOT (n)-[:R]-()` returns the rows it used to drop.

*Action:* none, unless a query relied on the old answer.

[discrete]
====== 26.12.1 - An openCypher hop that ends at a null variable matches nothing

A hop whose end is a node variable an earlier `OPTIONAL MATCH` left null read that variable as unbound and bound a vertex to it (issue #12728): `MATCH (a:A) OPTIONAL MATCH (a)-[:NOPE]->(x) MATCH (a)-[:S]->(x)` returned the vertex `a` points to for `x`, and the same went for the undirected, variable-length, two-hop and quantified path forms, a later `OPTIONAL MATCH`, and `count(x)`. The hop now matches nothing, so a `MATCH` drops the row and an `OPTIONAL MATCH` keeps it with `x` null, as when the null variable is the start of the hop. See <<cypher-optional-match,OPTIONAL MATCH>>.

*Impact:* the rows and counts such a query used to return for a null variable are gone.

*Action:* none, unless a query relied on the old answer.

[discrete]
====== 26.12.1 - An openCypher hop that reuses a null relationship variable matches nothing

A hop that reuses a relationship variable an earlier `OPTIONAL MATCH` left null read that variable as unbound and matched any relationship (issue #12621): `OPTIONAL MATCH (a)-[r:NOPE]->(b) WITH r MATCH ()-[r]->() RETURN count(*)` counted every relationship of the graph. The same went for a later `OPTIONAL MATCH`, `EXISTS { }` and `COUNT { }`. The hop now matches nothing, as a relationship variable bound to an edge already matched only that edge. See <<cypher-optional-match,OPTIONAL MATCH>>.

*Impact:* the rows and counts such a query used to return for a null relationship variable are gone.

*Action:* none, unless a query relied on the old answer.

[discrete]
====== 26.12.1 - openCypher `toString()` of a time or a datetime prints the seconds and trims the fraction, as Neo4j 5 does

`toString()` of a `localtime()`, `time()`, `localdatetime()` or `datetime()` used Java's text, which leaves out zero seconds (`10:00`) and keeps the trailing zeros of the fraction (`.500`). It now prints the seconds always and removes the trailing zeros of the fraction: `10:00:00`, `2020-01-01T10:00:00.5Z` (issue #11912). `toStringOrNull()`, `toStringList()`, `convert.toString()` and `apoc.convert.toString()` print the same, and a `java.time` value bound as a parameter prints as the Cypher temporal it stands for.

*Impact:* a key, an id or a comparison built from `toString()` of a time or a datetime changes (`'10:00'` becomes `'10:00:00'`). A temporal value that a query returns, over HTTP or SQL, keeps its text, and string concatenation with a temporal is unchanged.

*Action:* regenerate or normalize stored text that was made with `toString()` of a time or a datetime.

[discrete]
====== 26.12.1 - An openCypher `CALL` of an unknown namespaced name no longer runs the SQL function of its last segment

A `CALL` of a namespaced name that is neither a procedure nor a function ran the SQL function named by the last segment of the name, whatever the namespace (issue #12110): `CALL apoc.atomic.concat(n, 'name', 'zz')` ran SQL `concat()`, returned no row and wrote nothing, and `CALL nosuch.max(1, 2)` returned 2. Such a call now fails as an unknown procedure, as in Neo4j. `CALL` of an SQL function by its full name (`CALL abs(-5)`, `CALL vector.neighbors(...)`) is unchanged.

*Impact:* a `CALL anything.max(...)` that relied on the last segment fails with `UnknownProcedureException` (`Neo.ClientError.Procedure.ProcedureNotFound` over Bolt).

*Action:* call the SQL function by its full name or with the `sql.` prefix: `CALL sql.max(1, 2)`. See <<cypher-call,CALL>>.

[discrete]
====== 26.12.1 - Naming an object that does not exist is the client's error on every protocol

A statement that names a type, an index, a bucket, a property, a trigger or a view that does not exist raises a `SchemaException`, a missing record a `RecordNotFoundException`, an unknown method an `UnknownFunctionException`, and a Cypher `CALL` of an unknown procedure an `UnknownProcedureException` (issue #11384). Many of these raised a plain `CommandExecutionException` before.

*Impact:* over PostgreSQL these answer `42P01` or `42883` instead of `XX000` (see <<postgres-missing-name,Naming an object that does not exist>>), over Bolt `Neo.ClientError.Statement.SemanticError` or `Neo.ClientError.Procedure.ProcedureNotFound` instead of `UnknownError`, and over HTTP `400` instead of `500`. Embedded Java code that caught `CommandExecutionException` for a missing type or index no longer catches it. `OPTIONAL CALL` of an unknown procedure now fails instead of returning a `null` row.

*Action:* catch `SchemaException` (or `ArcadeDBException`) for a missing schema object, and expect the new error codes in clients that keyed on the old ones.

The Java API follows the same rule (issue #11633). A missing edge type in `GraphBatch` or in the hybrid, full-text and vector search functions, a missing bucket behind a Gremlin label, and a missing embedded document type raise a `SchemaException`. A function or function library that does not exist (`Schema.getFunctionLibrary()`, `FunctionLibraryDefinition.getFunction()`) raises an `UnknownFunctionException`. All of these raised an `IllegalArgumentException` before. The batch endpoint (`/api/v1/batch`) still reports what it committed before such an error.

[discrete]
====== 26.12.1 - A write whose outcome is unknown over HTTP answers `504`, not `500`

A write that an HA replica forwarded to a leader which died or did not answer, and a write handed to the replication whose quorum was not confirmed, answered `500` before (the first with `exception: java.io.EOFException` or a connection reset), although the write may have been committed (issue #11887).

*Impact:* these answer `504` with `exception` `com.arcadedb.exception.TransactionOutcomeUnknownException`, on the leader and on the replica. A client that handled this case by its `500` status must now handle `504`; the Java remote client does not retry it.

*Action:* on a `504` from `/api/v1/command` or `/api/v1/commit`, check whether the write landed before sending it again. See <<ha-outcome-unknown-contract,Outcome-unknown response contract>>.

[discrete]
====== 26.12.1 - The line protocol write refuses an unknown `precision`

`POST /api/v1/ts/{database}/write` read a `precision` it did not recognize (`sec`, `seconds`, `h`, a typo) as nanoseconds and answered `204`, so a timestamp in seconds was stored in 1970 (issue #11875).

*Impact:* any value other than `ns`, `us`, `u`, `ms` or `s` (in any case) answers `400` with an `error` naming the accepted values, and nothing in the request is written. An absent or empty `precision` still means nanoseconds.

*Action:* send one of the accepted values. See <<timeseries-line-protocol-precision,Precision parameter>>.

[discrete]
====== 26.12.1 - A mistake in a SQL script's own values or order is a client error, not `500`

`SLEEP` of a value that is not a number, an unknown `CONSOLE` level, a `LOCK` after a modification or a second `LOCK`, a `COMMIT` with no transaction open inside a loop or an `IF`, a `BEGIN` in a loop past the nested-transaction limit, and `<`, `<=`, `>`, `>=` or `BETWEEN` between two records answered `500` before, with a `NullPointerException`, `ClassCastException`, `TransactionException` or `CommandExecutionException` (issue #11893).

*Impact:* over HTTP these answer `400`, with `TypeMismatchException` (`SLEEP`, comparison), `CommandSQLParsingException` (`CONSOLE`, `COMMIT`) or `CommandSemanticException` (`LOCK`, `BEGIN`), and over the other protocols the matching validation or parsing error. An unknown `CONSOLE` level is now refused when the script is parsed, so none of the statements before it runs. Embedded Java code that caught `TransactionException` around a script with `LOCK` or `BEGIN` must catch `CommandSemanticException` (or `ArcadeDBException`); `acquireLock()` and `begin()` called directly from Java still throw `TransactionException`.

*Action:* none for a script that ran. A client that retried or alerted on `500` for these cases stops doing so. See <<sql-script,SQL Script>>.

[discrete]
====== 26.12.1 - Eight SQL and openCypher caller mistakes answer `400`, not `500`

Eight statement shapes that are a mistake of the caller, or that the engine refuses on purpose, answered `500` before, some with only a bare Java exception or a dump of the whole record as the message (issue #12795):

* `UPDATE` and `MOVE VERTEX` with `ADD`, `PUT` or `INCREMENT`. The message now names the `SET` form that does the same: `SET tags = tags || 'x'`, `SET m.k2 = 2`, `SET n = n + 1`. See <<sql-update,UPDATE>>.
* a nested `distinct()`, as in `SELECT FROM P WHERE distinct(n) = 1`, and a `FROM` target the engine does not support.
* `SELECT FROM :p` and `TRAVERSE ... FROM :p` with a parameter bound to a value that cannot be a target (`1`, a map, a list of non-records). The message names the parameter, the value and the accepted kinds.
* `INSERT`, `UPDATE`, `CREATE EDGE` and `MOVE VERTEX` with `CONTENT :p` bound to a value that is not a map, a document or a list of them. The message names the statement; an `INSERT` said `UPDATE` before.
* `expand(@this)` and `expand(*)`. The message names the record by RID and type, not the whole record.
* `SEARCH_INDEX(@type, 'a')` and `SEARCH_FIELDS(@type, 'a')` answered a `NullPointerException`. An argument read from the record is now evaluated per record, so `SEARCH_INDEX(@type + '[name]', 'a')` finds the record, and `SEARCH_INDEX(@type, 'a')` answers `Index with name 'P' was not found`.
* openCypher `LOAD CSV FROM null`. The message names the expression that evaluated to `null`.

`SELECT FROM []` and `TRAVERSE ... FROM []` are unchanged: they answer no rows.

*Impact:* over HTTP these answer `400`, with `CommandSemanticException` (`ADD`, `PUT`, `INCREMENT`, a nested `distinct()`, an unsupported target), `TypeMismatchException` (the `:p` target, `CONTENT`, `expand`) or `InvalidArgumentException` (`LOAD CSV`), and over the other protocols the matching validation error. Embedded Java code that caught `CommandExecutionException`, `IllegalStateException` or `UnsupportedOperationException` for these cases must catch the new type (or `ArcadeDBException`).

*Action:* none for a statement that ran. A client that retried or alerted on `500` for these cases stops doing so.

[discrete]
====== 26.12.1 - `algo.maxFlow` follows the relationship direction

`algo.maxFlow` treated every relationship as an undirected pipe, so flow could run against a relationship and two opposite relationships added up (issue #11798). It now follows the relationships outgoing by default, and takes an optional fifth argument, `direction` (`OUT`, `IN` or `BOTH`). See <<algo-max-flow,algo.maxFlow>>.

*Action:* pass `'BOTH'` as the fifth argument to keep treating the relationships as undirected.

[discrete]
====== 26.12.1 - The second argument of `node.relationship.types()` is APOC's relationship pattern

`node.relationship.types(node, [relTypes], [direction])` (and `apoc.node.relationship.types`) takes APOC's relationship pattern as its second argument, as APOC does, and the direction moved to the third position (issue #12103). `(n, 'KNOWS>|<LIKES')` answers the types of that list the node has a relationship of, `(n, null, 'IN')` every incoming type. The same release makes `node.degree*`, `node.relationship.exists()`, `algo.dijkstra`, `algo.astar` and `algo.allsimplepaths` read the pattern too (see <<node-relationship-pattern,node functions>> and <<algo-relationship-pattern,the relationship pattern>>), and the fifth argument of `algo.dijkstra` is APOC's `defaultWeight` when it is a number. An edge type whose name contains `|`, `<` or `>` (or `,` in the `algo.*` procedures) can no longer be named in these arguments.

*Impact:* a call written for the old signature keeps its answer: a second argument that is a direction word (`IN`, `INCOMING`, `OUT`, `OUTGOING`, `BOTH`, in any case) with no third argument is still read as the direction. In a database with an edge type named exactly like that word (an edge type `OUT`), `(n, 'OUT')` is now the pattern naming that type and answers `['OUT']` or `[]`. A call that passed a type name, `(n, 'KNOWS')`, used to fail as an unknown direction and now answers.

*Action:* write the direction as the third argument, `(n, null, 'OUT')`, where an edge type has the name of a direction word.

[discrete]
====== 26.12.1 - `node.degree()` counts a self loop once in both directions, and `TYPE<` is an incoming marker

`node.degree()` (and `apoc.node.degree`) counted a self loop twice when the pattern follows both directions, once from the outgoing side and once from the incoming side, where APOC and `COUNT { (n)-[:T]-() }` count it once (issue #12674). It now counts it once. The count of one direction (`node.degree.in()`, `node.degree.out()`, `'T>'`, `'<T'`) is unchanged. The relationship pattern also reads a trailing `<` as incoming, as APOC does, so `'T<'` is `'<T'`; before, `'T<'` was looked up as an edge type named `T<`. See <<node-relationship-pattern,node functions>>.

*Impact:* a node with a self loop answers a degree one lower per self loop (and per repeated alternative) than before, and an edge type whose name ends in `<` can no longer be named in these arguments.

*Action:* none for the counts, they now match APOC. Rename an edge type whose name ends in `<`.

[discrete]
====== 26.12.1 - An undirected openCypher `MERGE` answers an existing self loop once

`MERGE (a)-[r:R]-(b)` over a relationship that already exists as a self loop (`a` and `b` are the same node) returned the loop twice, so `ON MATCH SET`, `SET`, `RETURN count(*)` and every later clause ran twice for it (issue #13117). It now returns the loop once, as `MATCH` and Neo4j do. Directed patterns and relationships between two different nodes are unchanged, and no relationship was ever created twice. See <<cypher-compatibility,Cypher compatibility>>.

*Impact:* a query that merges an undirected relationship between two bindings of the same node, typically a batched `UNWIND ... MERGE` with a row whose two ends are equal, answers one row per existing loop instead of two.

*Action:* none, the rows now match `MATCH`.

[discrete]
====== 26.12.1 - A `limit` of 0 of `vector.fuse` and `vector.boost` returns no row, and a negative `limit` is refused

The `limit` option of `vector.fuse()` and `vector.boost()` read `0` and any negative number as "no limit", so `{ limit: 0 }` returned every row (issue #13131). `0` now returns no row, as the `k` of `vector.neighbors()` does, and a negative `limit` is refused with an error naming the option. Leaving `limit` out, or passing `null`, still returns every row. The `k` option of `vector.mmr()` is read the same way: a negative `k` is refused, also when the candidate list is empty, where it used to return no row. See <<vector-fuse-ext,vector.fuse()>>.

*Impact:* a query that computes `limit` (a page size, or a budget minus what was used) and reaches `0` gets no row instead of the whole candidate set, and one that passes a negative `limit` (answered every row before) or a negative `k` of `vector.mmr()` (answered no row before) fails.

*Action:* omit `limit`, or pass `null`, where no cap is wanted.

[discrete]
====== 26.12.1 - `algo.kTruss` returns only the vertices of the k-truss when `k` is passed

`algo.kTruss(relTypes, k)` validated `k` and then ignored it, returning every vertex whatever `k` was (issue #12303). A call that passes `k` now returns only the vertices whose truss number is at least `k`, and a `k` below 2 is refused. A call without `k`, or with `null`, still returns every vertex with its truss number. See <<algo-k-truss,algo.kTruss>>.

*Action:* drop the `k` argument (or pass `null`) to keep receiving every vertex.

[discrete]
====== 26.12.1 - MongoDB wire filters match as mongod does

Filters over the MongoDB protocol (`find`, `count`, `update`, `delete` and the top-level `$match` stages of an aggregation) are evaluated by ArcadeDB's own matcher, which follows mongod's rules, instead of the one bundled with mongo-java-server (issue #12074). Several filters now answer differently: `{a: {}}` matches only an empty document, a regular expression matches only strings, `null` reached through an array, `$mod` on longs, `$gte`/`$lte` against `null`, comparisons of arrays and documents, NaN and `$elemMatch`. A filter with an unknown operator or a malformed operand is refused before any document is read, so an upsert with such a filter inserts nothing.

[discrete]
====== 26.12.1 - `arcadedb.server.defaultDatabases` decodes `%XX` in its credentials and refuses an ambiguous one

A user name, password or group of a `arcadedb.server.defaultDatabases` credential is percent-decoded, so a separator inside it can be written (`%3A` for `:`, `%2C` for `,`, `%3B` for `;`, `%5B` for `[`, `%5D` for `]`, `%25` for `%`), see issue #11269. A credential with more than three `:`-separated fields, an empty user name or an empty password is refused with a WARNING naming the user, and so is an entry with text after its `]` that opens no `{...}` command list.

*Impact:* a password written with a raw `:` used to be cut at it, the text after it becoming the user's group; that credential now creates no user and grants nothing. A password that contains `%` followed by two hexadecimal digits (`%41`) now reads as the decoded character: an existing user written that way is reported `already exists with a different password` and keeps its password, a new one is created with the decoded password.

*Action:* write a `%` that is followed by two hexadecimal digits as `%25`, and any `:`, `,`, `;`, `[` or `]` inside a field encoded as above. See <<settings-sql,`server.defaultDatabases`>>.

[discrete]
====== 26.12.1 - One property name cannot have two types in a type hierarchy

`CREATE PROPERTY` was refused when a super type already declared the name, but accepted when a sub type declared it with another type, and `ALTER TYPE ... SUPERTYPE +` only logged a warning, whatever the types were (issue #12732). An index on the super type's property then missed the records of the sub type (a lookup answered `0` rows where a scan found `1`), a `BINARY` against a `LONG` left an index file that could not be read, and a `BY KEY`, `BY ITEM` or `GEOSPATIAL` index over a property of another type answered `500` or refused every later insert. A name declared with the same type on a super type and a sub type is still accepted. A name declared with another type, or another `OF` type, anywhere in the hierarchy is now refused: by `CREATE PROPERTY` and `ALTER PROPERTY ... NAME` with an `AlreadyExistsException` (`409` over HTTP), and by `ALTER TYPE ... SUPERTYPE +` and the Java `Property.setOfType()` with a `SchemaException`. A refused statement changes nothing. See <<sql-create-property,`CREATE PROPERTY`>> and <<sql-alter-type,`ALTER TYPE`>>.

*Impact:* a schema script that declares a property on the sub type first and then declares the same name with another type on the super type, or links the two types with `SUPERTYPE +`, now fails; with the same type it works as before. The JSONL import of an export of a database that already holds such an overlap is refused at the linkage step. A database that already holds an overlap still opens, and the overlap is not repaired.

*Action:* declare the property with the same type in every type of the hierarchy, or give the sub type's property another name.

====== 26.12.1 - A schema change refused because of the data already stored is a `ValidationException`

`CREATE PROPERTY` and `ALTER PROPERTY` refused because a record already stored violates the constraint (`MANDATORY`, `NOTNULL`, `MIN`, `MAX`, `REGEXP`), and the same refusal over a sample already stored in a TIMESERIES type, raise a `ValidationException`, whose kind names the constraint where there is one. An update that would change the partition key of a type with `partitioned(...)` bucket selection raises a `ValidationException` too (issue #12037). Before, they raised a `CommandExecutionException` (the partition key an `IndexException`), and `MANDATORY`, `NOTNULL` and the partition key were answered over HTTP with `500`.

*Impact:* over HTTP these refusals answer `400`, with the constraint in `exceptionArgs`. Embedded Java code that caught `CommandExecutionException` or `IndexException` for these cases no longer catches them.

*Action:* catch `ValidationException` (or `ArcadeDBException`) for a schema change refused over the stored data. See <<sql-create-property,CREATE PROPERTY>>.

====== 26.12.1 - A schema change over PostgreSQL answers no result set, and a violated constraint has its own error code

Over the PostgreSQL protocol a schema change (`CREATE TYPE`, `CREATE PROPERTY`, `CREATE INDEX`, `ALTER TYPE`, `DROP TYPE`, `REBUILD INDEX`, ...) is answered as PostgreSQL answers `CREATE TABLE`: no result set and a command tag naming the statement, such as `CREATE DOCUMENT TYPE` (issue #11312). The command tag of every statement the server parses comes from the statement, not from its text, so a write with a leading comment reports its row count (issue #11313). A value refused by a constraint declared on its property raises a `ValidationException` that names the constraint (`ValidationException.getKind()`: `MANDATORY`, `NOT_NULL`, `MIN`, `MAX`, `MAX_LENGTH`, `REGEXP`, `READONLY`, `TYPE`, `ENCODING`), a number a property's type cannot hold raises a `ValueOutOfRangeException` (an `IllegalArgumentException`), and a call of a function that does not exist raises an `UnknownFunctionException` (a `CommandExecutionException`), see issue #11314.

*Impact:* over PostgreSQL, a client that read the row a schema change returned gets none (JDBC `execute()` returns `false` for it), and the refusals answer the SQLSTATEs listed in <<postgres-refused-value,A refused value and an unknown function>> instead of `22023` and `XX000`. Over HTTP a violated constraint and an unknown function answer `400` instead of `500`, with the constraint in `exceptionArgs`; over Bolt a violated constraint is `Neo.ClientError.Schema.ConstraintValidationFailed` and an unknown SQL function `Neo.ClientError.Statement.SyntaxError`; over MongoDB a violated constraint is `121` (`DocumentValidationFailure`); over gRPC an unknown function is `INVALID_ARGUMENT` instead of `INTERNAL`. The Java remote clients rebuild the `ValidationException` with its kind.

*Action:* read a schema change's outcome from the success of the statement rather than from a returned row. Clients that keyed on the old error codes should expect the new ones.

====== 26.12.1 - A database's directory settings must stay inside the server-level directory

====== 26.12.1 - TIMESERIES sealed files record the type they belong to, which older builds cannot read

Every TIMESERIES type created by 26.12.1 draws a random owner id, stored in the schema (`sealedOwner`) and written into the header of every `.ts.sealed` file of its shards, at sealed format version 4 (issue #11274). ====== 26.12.1 - A database opened read-write is refused by older builds, unless fixed-width float arrays are turned off

A build before 26.11.1 cannot read the fixed-width float and double arrays introduced in 26.11.1 (see <<upgrade-float-arrays-fixed-width,Float and double arrays are stored fixed-width>>), and 26.9.1 and 26.10.x did not refuse such a database: they read those arrays as `null`, left the records out of `vector.neighbors()`, and the first `UPDATE` of such a record erased its arrays (issue #12234). While `arcadedb.serializer.fixedWidthFloatArrays` is `true` (the default), 26.12.1 labels the dictionary file of a database with format version 2 (`dictionary.<id>.<pageSize>.v2.dict`, same content as version 1) when it creates the database, when it opens it read-write, and when the setting is turned on. Builds from 26.8.1 to 26.11.x refuse to open such a database with `Dictionary '...' was written with format version 2, which this version of ArcadeDB cannot read (latest known is 1)` instead of losing data. The label does not depend on the content: a database that holds no float or double array is labelled too. A database opened read-only is not labelled. If the label cannot be applied (an I/O error), a WARNING is logged and arrays are written in the old varint form until the next open.

*Impact:* once 26.12.1 has opened a database read-write, no released build opens it any more, 26.11.x included (it reads the fixed-width form but refuses the label). Builds before 26.8.1 do not check the label and still open it, with the data loss described above. In an HA cluster, a node still on an older build that has to install a full snapshot from an upgraded node refuses the dictionary until it is upgraded too.

*Action:* none to upgrade. To keep a rollback possible, set `arcadedb.serializer.fixedWidthFloatArrays` to `false` before the database is first opened read-write by 26.12.1, or take a backup before the upgrade: the label stays at version 1 and arrays are written in the varint form, which every build reads. Turning the setting off later does not remove the label. To go back to 26.11.x only, stop the server and rename `dictionary.<id>.<pageSize>.v2.dict` back to `dictionary.<id>.<pageSize>.v1.dict`. Never do that to open the database with 26.10.x or older when it may hold float or double arrays: export it with 26.12.1 and re-import it with the older version instead. See <<settings-sql,`serializer.fixedWidthFloatArrays`>>.

====== 26.12.1 - `DROP INDEX` refuses the bucket index of an index, and an index missing one is not used

An index that lacks the bucket index of one of the buckets it covers (left by an interrupted rebuild of an earlier version) is no longer used by any query planner: queries fall back to a scan. `database.lookupByKey()` on it raises an `IllegalArgumentException`, and Cypher `SHOW INDEXES` reports it with state `FAILED`.

====== 26.12.1 - An index on an undeclared property written by an older version finds its old list and number keys

An index on a property the schema does not declare keys each value by its text. 26.10.1 changed that text for a floating point or decimal number (`1.0` is keyed `1`, `-0.0` is keyed `0`, `1e300` by its full digits, where 26.9.1 wrote `1.0`, `-0.0` and `1.0E300`), and 26.12.1 for a list holding such a number (`[1.5, 2.0]` is keyed `[1.5, 2]`). Nothing re-keyed the entries an older version wrote, so after an upgrade a seek missed those records, `MERGE` created a second node, `IS UNIQUE` accepted a copy, a delete or an update left the old entry behind, and `CHECK DATABASE` reported errors (issues #12160, #12233). Such an index now also reads, removes and checks the old spelling of a list or number key, and a `STRING` spelled like an old key (`'1.0'`, `'[1.5, 2.0]'`) is still a different value. An old entry is found by the text it was written with: `1.0` finds the entry 26.9.1 wrote for `1.0`, and `1` finds it only after a rebuild.

*Impact:* every `LSM_TREE` index created before 26.12.1 is treated as possibly holding old keys. On an undeclared property, its seeks, removals and unique checks of a floating point number or of a list holding one pay an extra read, a seek of a `STRING` that reads as a number or a list (`1.0`, `2.500`, `[1.5, 2.0]`) loads the record behind each entry it finds, and a unique `STRING` key that reads as a number or a list (`12345`, `2.5`) loads one record at commit. Any other text pays nothing, and so does an index created by 26.12.1.

*Action:* run `REBUILD INDEX <name>` (or `REBUILD INDEX *`) once after upgrading: it writes every entry under its current key and removes the extra cost. See <<sql-rebuild-index,`REBUILD INDEX`>>.

====== 26.12.1 - A materialized view keeps the brackets of its query, and `@cat` is a reserved name

A materialized view or a continuous aggregate stores its `SELECT` as text. Earlier versions dropped brackets from that text: `a = 1 AND (b = 2 OR c = 3)` was stored as `a = 1 AND b = 2 OR c = 3`, and `NOT (x AND y)` lost its brackets too, so the view held rows its query does not return (issue #11299). A back-ticked `` `@cat` `` was stored without its back-ticks, and the view could not be created (issue #11308). The stored text now means what was written. `@cat` is now a token of its own like `@rid` and `@type`, so it can be written without back-ticks.

*Impact:* a view created by an earlier version keeps the text it stored, and keeps answering the wrong rows.

*Action:* drop and recreate any materialized view or continuous aggregate whose query has a bracketed `OR` or a `NOT (...)`. See <<sql-create-materialized-view,`CREATE MATERIALIZED VIEW`>>.

====== 26.12.1 - The gRPC Java client returns record rows and record columns as records

A row that returns a record, such as Cypher `MATCH (n) RETURN n`, now reaches a `RemoteGrpcDatabase` caller as that vertex or edge with its own properties, and a column that holds a record (`RETURN a, r, b`, SQL `SELECT @rid, @type, @this`, the records of `collect(n)`) as a `Document`, `Vertex` or `Edge`, as the embedded API returns them (issue #12196). Before, `RETURN n` gave a vertex whose only property was `n`, `SELECT @rid, @type, @this` a record whose only property was `@this`, and the other record columns raw maps. A projection row with a `@type` column, such as `SELECT @type, name FROM P`, is now a projection row with both columns; before, it reached the client as a record of type `P` without the `@type` column (issue #12519).

*Impact:* code that read the properties through the alias (`vertex.get("n")`) or cast a record column to `Map` no longer works. A map a query builds with a valid `@rid` and the name of an existing type as `@type` is also returned as a record. The columns of a projection keep the order of the query. In an HA cluster, a command a follower forwards to the leader still answers a row that has a `@type` column as a record of that type.

*Action:* read the properties from the record itself (`result.getVertex().get().get("name")`), and treat a record column as a `Document`, `Vertex` or `Edge`. See <<java-api-grpc,Java API (gRPC)>>.

====== 26.12.1 - The HTTP Java client returns record columns as records

A column of a projection row that holds a record, such as Cypher `MATCH (a)-[r]->(b) RETURN a, r, b`, SQL `SELECT @this AS me, name` or `SELECT first(out('Knows')) AS friend`, reached a `RemoteDatabase` caller as a list of RIDs, with every property lost: a vertex as `[#1:0]`, an edge as `[edge rid, in rid, out rid]`. It now arrives as a `Document`, `Vertex` or `Edge` with its properties, as the embedded API returns it, and so do the records held in a list, a map or a path of a column (`collect(a)`, `{who: a}`) (issue #12184). A row that is itself a record (`RETURN a`) was not affected.

*Impact:* code that read such a column as a `List` of RIDs no longer works. A map a query builds with a `@cat` of `d`, `v` or `e` and a `@type` is also returned as a record. The change is in the client alone and works with any server version.

*Action:* treat a record column as a `Document`, `Vertex` or `Edge`, and call `getIdentity()` on it where only the RID is needed. See <<java-api-remote,Java Remote API>>.

====== 26.12.1 - A vector index whose definition in `schema.json` is invalid is left out at open, alone

*Impact:* such a definition, typically from a hand-edited or restored `schema.json`, used to be accepted as is, or, for a value already checked at open (an unknown similarity, a negative `rerankOversample`), to stop the schema load half way: the database opened without every index loaded after it, UNIQUE ones included. ====== 26.12.1 - A `READ_COMMITTED` commit is refused when it read stale records from a page it had written

Once a `READ_COMMITTED` transaction has written a bucket page, it reads that page from its own copy, taken at its first write, which does not show what other transactions committed there afterwards. The commit-time merge (`txPageSlotMerge`, and `arcadedb.graph.edgeAppendMerge` for edge lists) used to re-apply the transaction's writes on the newer page and the commit succeeded, so a statement decided on those stale reads was committed: an `UPDATE` or `DELETE` that matched none of the rows committed before it ran, a Cypher `MERGE` that created a second node, a relationship `DELETE` that found nothing (issue #11590). Now such a commit fails with a retryable `ConcurrentModificationException`. A page whose records the transaction read still hold the same content on the committed page keeps merging, and so do blind inserts and updates.

*Impact:* a transaction that writes a page and then reads records of the same page that another transaction changed meanwhile can now be refused where it used to commit, and so can a transaction that adds a relationship to a vertex and then traverses or counts that vertex's relationships in the same direction while another transaction adds one there too. `database.transaction(...)` and the other retrying APIs retry it, and the retry reads the committed records. `REPEATABLE_READ` is unchanged.

*Action:* none, beyond retrying on `ConcurrentModificationException`, which every concurrent writer already has to. See <<isolation,Isolation>>.

====== 26.12.1 - A delete of a record changed since it was read is refused

Under `READ_COMMITTED` a delete removed whatever sat at the record's RID when it got there, with no check that it was still the record read (issue #12472). If another transaction deleted the record and an insert reused its RID, the delete removed the unrelated new record and committed without an error; a SQL `DELETE ... WHERE` racing an `UPDATE` removed a record the update had made stop matching. A record deleted by its RID without being loaded first is deleted as it is found.

*Impact:* under contention more deletes are retried. `database.transaction(...)` and a single-request command over HTTP retry them; a transaction spanning several HTTP requests now receives the exception at the delete instead of a silent wrong delete.

*Action:* none, beyond retrying on `ConcurrentModificationException`, which every concurrent writer already has to. See <<isolation,Isolation>>.

====== 26.11.1 - Float and double arrays are stored fixed-width, which older builds cannot read

An `ARRAY_OF_FLOATS` or `ARRAY_OF_DOUBLES` value (a vector embedding, for example) is now written as its element count followed by the raw little-endian IEEE-754 elements, 4 bytes per float and 8 per double, where each element used to be a zigzag varint of 5 bytes per float and 9 to 10 per double (issue #10856). A record holding a 1536-dimension float embedding shrinks from about 7,695 to about 6,150 bytes, about 22% less disk and page cache. Records written before keep the old form and are still read; an update rewrites the value in the new form. In an HA cluster no node writes the new form until every peer advertises the `fixed-width-float-arrays` capability, so a rolling upgrade keeps writing the old form until the last node is upgraded.

*Impact:* once a database holds records in the new form, a build older than 26.11.1 cannot read them.

*Action:* none to upgrade, and no migration is needed. To go back to an older build afterwards, export the database with 26.11.1 and re-import it with the older version. See <<datatypes-float-array-storage,Data Types>>.

====== 26.11.1 - `pow()` and `sqrt()` answer the value, not the width of the argument

`pow()` answered null for every negative base and narrowed its result into the type of the base (`pow(2, 31)` returned `2147483647`, `pow(s, 3)` on a SHORT holding 300 returned `-832`), and read a fractional exponent as a whole one (`pow(2, 2.5)` returned 4). `sqrt()` rounded the root of an integral argument down into its type (`sqrt(2)` returned `1`). Both now answer the value (issue #11047): an exact integral power widens to a Long and then to an exact Decimal, a fractional exponent and a negative exponent of an integral base answer a Double, a negative base is accepted, and the root of an integral or Float argument is a Double. A power no type can hold raises an arithmetic error instead of a saturated number.

*Impact:* `sqrt(4)` returns `2.0` (a Double) where it returned `2`, and `pow()` of an INTEGER base can return a Long or a Decimal.

*Action:* none, unless code relied on the type of the result; cast it with `.asInteger()` or `.asLong()` where an integral value is needed. See <<pow,pow()>> and <<sqrt,sqrt()>>.

====== 26.11.1 - SQL refuses positional values that do not match the placeholders

A list spread into several values for one `IN ?` answered fewer rows than the caller meant. The values are now counted against the placeholders before the statement runs, and a mismatch is refused with a `CommandSQLParsingException` (HTTP 400) that names both counts (issue #10721). Values bound by name (a map) are not counted.

*Impact:* code that passed a surplus value, or relied on a missing value being bound to `null`, fails where it used to answer.

*Action:* pass one value per placeholder, `null` included, and a list meant for one `IN ?` as one value (a `List` or a Java array). See <<http-positional-params,positional parameters over HTTP>>.

====== 26.11.1 - A plain `CHECK DATABASE FIX` relinks orphan edge records

A plain `CHECK DATABASE FIX` left it untouched, and only `FIX DELETE ORPHANS` repaired it, by deleting it. ====== 26.11.1 - `count(*)` repeats inside a `REPEATABLE_READ` transaction

Under `REPEATABLE_READ` the committed counter of each bucket is now read at the first count of the transaction and kept, plus the transaction's own inserts and deletes (issue #10712). `READ_COMMITTED` is unchanged.

*Impact:* a `REPEATABLE_READ` transaction that polled `count(*)` to watch other transactions' inserts no longer sees them change.

*Action:* poll with separate transactions, or at `READ_COMMITTED`. See <<isolation,Isolation>>.

====== 26.11.1 - A MongoDB `deleteMany` over a TIMESERIES type no longer accepts a number for the timestamp

*Impact:* a client that deleted time-series samples by a number of milliseconds gets an error instead of a deletion. Nothing is removed by a refused delete.

*Action:* compare the timestamp with a date (a `Date`, a `datetime`, a BSON date): `deleteMany({ts: {$gte: ISODate("2026-10-19T08:00:00Z")}})`. *Impact:* none for a database whose zone is UTC. ====== 26.11.1 - An update of a record the transaction already updated, refused by a constraint or a listener, makes the commit fail

That copy kept the refused values and the commit stored them (issue #10482). The statement still fails with the constraint's error, and `commit()` now throws a `TransactionException` ("Transaction cannot be committed: a statement failed after part of its records were written ..."), like any other statement that fails after writing. A before-update listener that returns `false` to skip the record, which was a silent veto, now makes the commit fail too when the record was already updated by the transaction, since the skipped values would otherwise be committed.

*Impact:* code that caught the error of such an update, or relied on a listener's veto of an already updated record, and went on to commit, now gets a `TransactionException` at `commit()`. A refused update of a record the transaction had not updated yet is unchanged: nothing of it is left. An openCypher statement whose existence-constraint check takes back every record it created, with the edges it connected to them, no longer makes the commit fail.

*Action:* roll the transaction back and retry, or avoid refusing an update after the same record was updated in the transaction. See <<transactions,Transactions>>.

A value no column can store, or a sample a constraint refuses, raises a `ValidationException` naming the column, and the whole batch is refused. *Impact:* application code that fed `appendSamples()` values a constraint refuses now fails at the call. Valid batches behave as before, including text for a numeric column, which is converted. The public constructor of `DatabaseAsyncAppendSamples` that took the boxed arrays is gone, since it built a grid of its own: code that created the task directly must go through `database.async().appendSamples()`.

====== 26.11.1 - SQL `split()` keeps the empty pieces at the end of the list

SQL `split()`, the `split()` function and `text.split()` answer the same list as the openCypher `split()` (issue #10485): `'a,'.split(',')` is `['a', '']` and `','.split(',')` is `['', '']`, where the empty pieces at the end were dropped (`['a']` and `[]`). An empty delimiter splits a string into its characters, a character outside the Basic Multilingual Plane (an emoji) being one, and `replace()` with an empty search puts the replacement between characters and never inside one.

*Impact:* a query that counted the pieces of a text ending with the delimiter, or compared the last one, sees one more piece.

Since 26.12.1 `text.split()` is no longer part of this rule: it is APOC's split around a regular expression (see the entry on the `text.*` functions above), and it drops the empty pieces at the end again unless its `limit` is negative.

*Action:* remove the empty last piece in the query if it is not wanted, for example by trimming the delimiter from the end of the text before splitting it.

====== 26.11.1 - The JSON of a record writes a `DATETIME_MICROS` and a `DATETIME_NANOS` property as text

`record.toJSON()` wrote a `DATETIME_SECOND`, `DATETIME_MICROS` or `DATETIME_NANOS` property as a count of seconds, microseconds or nanoseconds, which `fromJSON()` and the server read as milliseconds (issue #10486). It now writes epoch milliseconds for a `DATETIME_SECOND` property, as for `DATETIME`, and the text with all its digits (for example `"2020-01-02 03:04:05.123456789"`) for `DATETIME_MICROS` and `DATETIME_NANOS`, which milliseconds would truncate. The remote client sends a record as this JSON, so it now stores those properties right on the server.

*Impact:* a reader of `toJSON()` (the change events of a WebSocket subscription carry it) that took those numbers as seconds, microseconds or nanoseconds gets milliseconds, or text, instead.

*Action:* read a number as epoch milliseconds, and parse the text of a `DATETIME_MICROS` or `DATETIME_NANOS` property.

`EXPORT DATABASE` and `IMPORT DATABASE` in the `jsonl` format now round-trip a declared `LIST OF` or `MAP OF` property of any element type (issue #10391). *Action:* none.

====== 26.11.1 - gRPC `BeginTransaction` refuses `SERIALIZABLE`

A gRPC `BeginTransaction` that asks for `SERIALIZABLE` isolation is now refused with `INVALID_ARGUMENT`, as is an isolation value the server does not know, a newer client's enum constant (issue #10386). Before, the server began the transaction at `REPEATABLE_READ` (or, for an unknown value, at `READ_COMMITTED`) and answered success, so a caller that needed write-skew prevention was told its transaction started and got a weaker guarantee. HTTP, SQL, openCypher and PostgreSQL already refused a level the engine cannot provide, and SQL `BEGIN ISOLATION` and openCypher `START TRANSACTION ISOLATION` now say so in the same words as HTTP: `Invalid isolationLevel 'SERIALIZABLE': accepted values are [READ_COMMITTED, REPEATABLE_READ]` (SQL raised the JVM's `No enum constant ...`).

*Impact:* a hand-written gRPC client that sends `SERIALIZABLE` now fails at `BeginTransaction`. The first-party `RemoteGrpcDatabase` never sent it. `READ_UNCOMMITTED`, the proto default, still begins, at the stronger `READ_COMMITTED`, and the response reports it in `effective_isolation`. The server no longer logs a throttled warning for `SERIALIZABLE`, because there is nothing left to warn about.

*Action:* ask for `REPEATABLE_READ`, the strongest level the engine provides. See <<transactions,Transactions>>.

====== 26.11.1 - gRPC sends the records of a traversal, a list or a map as projected records

*Impact:* such a column is now a `list_value` (empty for a vertex with no edges) whose elements are the records, in JSON by default, instead of a string or a list of `link_value`. `soft_limit_bytes` now also counts the records nested inside lists and maps.

*Action:* a client that wants RIDs only sets `projection_encoding` to `PROJECTION_AS_LINK`. See <<grpc-projection-settings,Projected records>>.

====== 26.11.1 - A database an `overwrite` restore replaces refuses writes until the restore ends

While `restore backup ... overwrite` downloads and extracts the backup, the database it replaces stays open for reads and refuses every write, on every protocol, including connections and transactions opened before the restore started (issue #10689). The write is answered as "not available": `57P03` for Postgres, `DatabaseUnavailable` for BOLT, `UNAVAILABLE` for gRPC. A database setting change is refused the same way. The restore first waits for the commits already running. Before, such writes were acknowledged and then lost when the restored copy replaced the database.

*Impact:* an application writing to a database while it is restored now gets an error instead of a success that is silently lost. Reads are unchanged until the swap. When the restore fails, writes are accepted again.

*Action:* none for most installations. Retry the writes after the restore ends.

On an HA cluster the same holds for writes made through the other servers (issues #10965, #10974): while the leader restores a database, a commit on a replica is refused with a retryable error, and the commits the leader had already accepted from replicas are completed before the download starts (at most 10 seconds, otherwise the restore is refused and can be retried). A `restore database` or `restore backup` is refused, retryable, when the server running it is not the leader, or when the leadership moves before the restored copy replaces the database: a new leader may have accepted writes meanwhile, and the restore would destroy them. Requests sent to a follower are forwarded to the leader, as before.

Until the client sends `RESET`, every request is answered `IGNORED`, `HELLO` and `LOGON` included. *Impact:* none for the Neo4j drivers, which never send these messages out of turn. A hand-written client that did must send `RESET` after the error.

====== 26.11.1 - Postgres, Bolt, gRPC, Redis, MongoDB, MCP and Gremlin clients no longer open a database a restore holds or `close database` closed

*Impact:* a connection that names such a database while the restore runs, or after `close database` and before `open database`, is refused instead of opening it. *Action:* none for most installations. Retry the connection once the restore ends, or run `open database` after the cold backup.

====== 26.11.1 - A plugin route that another plugin or the server already holds fails the server start

The routes a plugin declares through `registerAPI(HttpServer, PluginRoutes)` are now one namespace shared by every plugin (issue #10385). Declaring another method on a path a different plugin declared merges into the same entry. Declaring a method a plugin already declared on that path, a path that fills a route the server registers for itself (for example `GET /api/v1/server` or `/api/v1/query/mydb`), or a prefix equal to one of the server's own mounts (`/api/v1`, `/api/v1/ai`, `/ws`), is refused with an `IllegalStateException` naming both parties, and the server does not start. So is an exact path on the path of a prefix another party holds, and a prefix on the path of an exact path another party holds (issue #10532): an exact path is matched before any prefix, so one of the two would answer everything under the path but not the path itself. One plugin may declare both on one path, to handle the root in one handler and everything below it in another. Before, the second registration silently replaced the first plugin's route, which then answered `405` naming the other plugin's method, a plugin could shadow a core route, and a plugin declaring the `/api/v1` prefix replaced the whole core router, with no log line. The same check applies to a plugin still implementing the deprecated `registerAPI(HttpServer, PathHandler)`.

*Impact:* a third-party plugin that relied on replacing another route no longer starts the server. The plugins shipped with ArcadeDB are unaffected.

*Action:* give the route another path, or remove the plugin that also declares it. A route declared `GET` now also answers `HEAD` with the same handler, as the core health routes do, so container healthchecks such as `wget --spider` work against it (issue #10384). Every core `GET` route does the same, and a `405` from a core route names the methods the route answers in an `Allow` header, as a plugin route does (issue #10531).

====== 26.11.1 - A taken schema object name is a conflict, not a server error

Creating, or renaming onto, a name already taken by a type, property, index, constraint, bucket, trigger, view or function now raises `com.arcadedb.exception.AlreadyExistsException`, a `SchemaException` (issue #10153). Before, the SQL statements raised `CommandExecutionException`, and defining a function or a library twice, or renaming or copying a type onto a taken name, raised `IllegalArgumentException`.

*Impact:* over HTTP these answer `409` instead of `500` (or `400` for a rename); over PostgreSQL `42P07`, `42701` or `42710` instead of `XX000` or `42P01`; over Bolt a `Neo.ClientError.Schema.*AlreadyExists` code; over gRPC `ALREADY_EXISTS`. Embedded or remote Java code that caught `IllegalArgumentException` or `CommandExecutionException` for this case no longer catches it.

*Action:* catch `AlreadyExistsException` (or `SchemaException`) where you handle a name that is already taken. Clients that keyed on the old status codes should expect the new ones.

====== 26.11.1 - `REFRESH INCREMENTAL` views track every type their query reads

An `INCREMENTAL` materialized view now refreshes on changes to every type its query names, at any depth (subqueries in `FROM`, `WHERE`, projection, `LET`), and to all their subtypes (issue #10205). Before, only the first `FROM` type was tracked, without its subtypes, and the view went stale while staying `VALID`. `REFRESH INCREMENTAL` is refused for a query that reads a `TRAVERSE`, a `MATCH`, a function, a bucket, an index, `schema:` metadata, record ids or parameters in `FROM`.

*Impact:* existing views have their source list completed from their query on open, so they refresh more often, and `DROP TYPE` of any type they read is refused while the view exists. Creating such a view, or switching one to `INCREMENTAL`, with an untrackable source fails.

====== 26.11.1 - HTTP: committing a session the server does not hold answers `404`, not `204`

*Impact:* a client that treated `204` on commit as "committed" for a stale or foreign session now gets `404`. ====== 26.11.1 - HTTP: plugin routes answer only the method they declare

====== 26.11.1 - SQL `INSERT` into a time series refuses a number for a BOOLEAN or STRING column

====== 26.11.1 - MongoDB: writes on a time-series collection are refused unless they can be applied exactly

A filtered update or delete, and the existence check of an upsert, on a TIMESERIES type matched nothing and reported success. `deleteMany` now deletes the samples when its filter is an AND of conditions the time-series engine applies exactly: `$eq`, `$gt`, `$gte`, `$lt` and `$lte` on the timestamp (whole milliseconds, or a date), and equality on a TAG field with a value of the tag's own kind. An unfiltered `deleteMany` deletes every sample. *Impact:* a MongoDB client that updated, upserted or deleted one document in a time-series collection and got a success that changed nothing now gets an error. *Action:* see <<timeseries-query-languages,Query languages>>.

====== 26.11.1 - Java API: a failed `transaction()` that joined the caller's transaction leaves it open

When the block passed to `database.transaction(...)` joined a transaction the caller had already begun, and threw anything other than a retryable exception, the call rolled back the caller's whole transaction, and the caller's next write failed with "Transaction not begun". `transaction()` now rolls back only the levels it opened itself, embedded and through the remote drivers (HTTP and gRPC) (issues #10135, #10241). *Impact:* code that relied on a failed joined `transaction()` rolling back the outer transaction now finds it still active.

====== 26.11.1 - A UNIQUE key moved off its holder can be given to only one record

When a transaction moved a UNIQUE key away from the record that held it, and then gave the key to two other records, the commit succeeded with only one of the two in the index, a duplicate the index could no longer see. The in-transaction duplicate check now treats a key that was handed over as taken, on UNIQUE and UNIQUE_HASH indexes alike, so the second claim fails with `DuplicatedKeyException` (issues #10265, #10298). Three related defects are fixed with it: inside the transaction, a lookup on a UNIQUE key that one record gave up no longer hides the records still holding it; committing such a transaction on a UNIQUE_HASH index no longer deletes the committed holder's index entry; and a valid replacement whose removals sit in several buckets is no longer refused at commit.

====== 26.11.1 - Remote drivers: deleting a missing or vetoed record throws, and `LIST OF DATE` reads as `LocalDate`

A remote delete that deleted nothing could look like a success. Both drivers now fail the way the embedded engine does for a missing record: a missing record throws `RecordNotFoundException` (HTTP now matches gRPC and embedded), and a vetoed delete throws `RecordVetoedException`, as a vetoed remote `save()` already does. *Impact:* code that deletes a record over HTTP that may already be gone, and relied on the call being silently idempotent, must catch `RecordNotFoundException`. ====== 26.11.1 - A number written into a DATE property is a day count under every `dateImplementation`

Under `arcadedb.dateImplementation=java.util.Date` (also `Calendar` and `LocalDateTime`) a number written into a DATE property was read as epoch milliseconds, while the default `LocalDate` reads days, so the days the remote client sends were stored as 1970-01-01. A number, and a numeric string, written into a DATE property, or into the items of a `LIST OF DATE` or `MAP OF DATE`, is now a day count for every implementation, with the midnight-millis reading kept (a non-zero exact multiple of 86,400,000). The day-to-millis multiplication is overflow-guarded and fails with an `IllegalArgumentException`. A number that is no day count for a `LocalDate`, such as a "now" in millis, is still read as millis (issues #10910, #10996).

*Impact:* a caller that wrote a small millis value (below about 1.07e11 and not a midnight) into a DATE under `java.util.Date`, `Calendar` or `LocalDateTime` now gets that many days, as `LocalDate` always did. A numeric string wins over a configured `dateFormat`.

*Action:* write dates as dates, or as day counts. See <<managing-dates,Managing dates>>.

====== 26.11.1 - An update of a record with a property that cannot be decoded is refused

An update of a record one of whose properties cannot be decoded used to save the record back without that property, because the lenient read logs `Skipping corrupted property` and returns the rest, which turned a possibly recoverable read problem into permanent data loss. The update (`MutableDocument.save()`, SQL `UPDATE`, graph vertex and edge saves, async updates) is now refused with a `SerializationException` naming the record and the property, and the stored bytes are left untouched (issues #10955, #10983). Reads stay lenient. An explicit full overwrite (`fromMap`) is still allowed.

*Impact:* an update of a damaged record now fails instead of silently dropping the damaged property.

*Action:* investigate the record with `CHECK DATABASE`, and restore it from a backup if needed.

====== 26.11.1 - Docker: every image runs as UID 1000, and the volumes changed

The JVM image and both native images (amd64 and arm64) run as `1000:1000`. The amd64 native image ran as root and the arm64 one as UID 65532, so a volume written by one image could not be opened by another (issues #10319, #10331). *Impact:* a volume or bind mount written by an earlier native image is owned by root or 65532, and one written by an earlier custom image by `100:101`, so the new image cannot write to it. ====== 26.11.1 - SQL: on an edge, `out` and `in` read the endpoints

On an edge, SQL reads the endpoints as `@out` and `@in`. The plain names `out` and `in` answered `null` (`SELECT out.id FROM E`, `WHERE in.name = 'x'`, `ORDER BY out`). On an edge with no property of that name they now resolve to the edge's endpoints, like `@out` and `@in`. A property named `out` or `in` on the edge record (even with a `null` value), or declared under that name by the edge's type, still wins. Vertices, documents and projection rows are unchanged (issues #10684, #10806).

*Impact:* `SELECT FROM E WHERE out IS NULL` used to match every edge without an `out` property and now matches none.

*Action:* prefer `@out` and `@in`: `WHERE @out = #rid` can use the index or the adjacency shortcut, while `WHERE out = #rid` answers correctly but through a scan. _Since v26.12.1_ `WHERE out = #rid` takes the adjacency shortcut too, as long as no record or type of the database uses a property named `out` or `in` (issue #10807).

====== 26.11.1 - Number arguments of SQL and Cypher-style functions are no longer truncated or wrapped

`if`, `randomInt` and `vector.sparseCreate` read a numeric argument through a cast to int, which dropped the fraction and wrapped a value past the int range. `if(0.5, a, b)` and a condition of `3000000000` now return `a`, and `-3000000000` returns `b`. `randomInt` and `vector.sparseCreate` refuse a fractional or out-of-range bound, dimension or index with an error naming the function (issues #10699, #10851). The Cypher-style functions (text, collection, aggregation, path, temporal and others) refuse a fractional or out-of-range INTEGER argument with a `CommandSemanticException` naming the function and the argument, and keep a value past the int range as a long where the function can still answer (`left('abc', 3000000000)` returns `'abc'`). The same check covers the SQL `duration`, `date` and `promql` amounts, `ts.timeBucket`, `substring()`, `util.sleep` and `date.*`. A TEXT argument such as `'2.5'` is refused the same way, with `<fn>() requires a whole number <arg>, but received '2.5'`, instead of a raw `NumberFormatException` (issues #10850, #10953, #10954, #10981).

*Impact:* an `if` whose condition is a fraction between -1 and 1, or a number past the int range, can take the other branch. A query that passed `2.5`, or a number past the int range, to one of these functions ran on the truncated or wrapped value and now fails.

*Action:* pass whole numbers.

====== 26.11.1 - HA: a node refuses to start when the root password behind its cluster token was rewritten

With no explicit cluster token, HA derives the token from `arcadedb.ha.clusterName` and the root password at every start. Rewriting the password file (`arcadedb.server.rootPasswordPath`) in place, as rotating a Kubernetes Secret does, or changing the inline `arcadedb.server.rootPassword`, gave each node a new token at its next restart, and during a rolling restart the nodes on the new token and those on the old one refused each other's requests with `401`. A node whose token is derived from the password now records a fingerprint of it in `<raft-storage>.cluster-token-fingerprint` and refuses to start when a later start derives a different token, unless `arcadedb.ha.clusterTokenAllowRotation=true` (default false) (issues #10601, #10826, #10924, #11232). *Impact:* the root password can no longer be rotated with a rolling restart when the token is derived from it. `<raft-storage>.cluster-token-fingerprint` must be writable, otherwise startup fails with a `ConfigurationException`. A new node, or one without persisted Raft storage, has nothing to compare against, so a differing token is still refused per request.

*Action:* either restart every node together with `arcadedb.ha.clusterTokenAllowRotation=true` and then remove the setting, or switch to an explicit `arcadedb.ha.clusterTokenPath`. See <<ha-security,HA security>>.

====== 26.11.1 - openCypher: an explicit write of a lookup key makes the query eager

====== 26.11.1 - A statement that fails inside a transaction is taken back, `UPDATE ... SET` reads the row as it was, and an explicit `NULL` stays `NULL`

A multi-row `INSERT`, `UPDATE`, `DELETE`, `CREATE EDGE`, openCypher or `sqlscript` statement that failed after writing part of its records used to leave them in the caller's transaction, and the commit published half a statement. The engine now takes the statement back on its own, with its records, index entries, edges and counters, and the transaction goes on (issues #10346, #10194, #10379). When it cannot take the statement back exactly (more than `arcadedb.txStatementSavepointMaxEntries` entries, 100,000 by default, a statement that touched a Graph Analytical View, dropped a file or ran Gremlin) the commit is refused with a `TransactionException` that names the reason.

Two SQL write semantics changed with it (issue #10194): every right-hand side of `UPDATE ... SET` reads the row as it was before the statement, so `SET a = b, b = a` swaps the two values, and an explicit `NULL` is stored as `NULL`: a `DEFAULT` fills only a property that is left out of the statement.

*Impact:* code that caught the error of a multi-row statement and relied on the rows written before the error now finds none of them. A `NOTNULL` property with a default refuses an explicit `NULL`. A `SET` list that relied on a later item reading the new value of an earlier one gives a different result.

*Action:* write the dependent assignment out (`SET b = 7, a = 7`), and leave a property out of the `INSERT` to get its default. See <<transactions,Transactions>>.

====== 26.11.1 - String functions count characters, not UTF-16 code units

====== 26.10.2 - Client requests wait in a queue when the server is busy

Every request of a remote client (HTTP, Postgres, BOLT, Redis, gRPC, Gremlin Server, MCP, MongoDB) now goes through a query admission gate: at most twice the number of cores run at once, and a request that arrives when they are all taken, or when the running queries hold more than 80% of the query heap budget, waits in a queue and starts in arrival order (issue #9518). Before, every request started at once, and under a burst of heavy queries the last ones were refused by the heap budget or exhausted the heap.

*Impact:* under load a request can wait before it starts, up to `arcadedb.queryQueueTimeout` (30 seconds by default), and is refused as retryable once that runs out or when `arcadedb.queryQueueMaxSize` requests already wait (HTTP `503`). A MongoDB request is refused at once instead of waiting. A BOLT result stream that is not read to the end keeps its slot until it is.

*Action:* none for most installations. Size the gate with `arcadedb.queryMaxConcurrent`, `arcadedb.queryAdmissionHeapWatermark`, `arcadedb.queryQueueTimeout` and `arcadedb.queryQueueMaxSize` (see <<setting-table,Settings>>), or set `arcadedb.queryMaxConcurrent=0` for the previous behavior.

====== 26.10.2 - Cypher: a path variable over a quantified group is one path, and ignored GQL constructs are refused

`MATCH p = ((m)-[r]->(n)){2}` used to bind `p` to a list with one path per repetition. It now binds one path running through every repetition, as any other path variable does and as Neo4j Cypher 25 does: `valueType(p)` is `PATH NOT NULL` and `length(p)` is 2 (issue #9940). Variables declared inside the group (`m`, `r`, `n`) are still lists.

GQL constructs that the parser accepted and the engine ignored now fail with a `FeatureNotImplemented` error that names the construct:

* the path search prefixes `ANY SHORTEST`, `ALL SHORTEST`, `SHORTEST k`, `SHORTEST k GROUPS`, `ANY` and `ANY k`
* the match mode `REPEATABLE ELEMENTS`
* `x IS DIRECTED`
* `USE` of a graph other than the current database
* a quantified group nested inside another one

An `ORDER BY`, `SKIP`, `OFFSET` or `LIMIT` written after `RETURN` (`RETURN ... LIMIT 2 OFFSET 1`) is now applied after the RETURN's sort, as one page: sort, then skip, then limit.

*Impact:* a query that read such a `p` as a list (`size(p)`, `p[0]`) gets a path instead. A query that used one of the refused constructs fails instead of returning rows the construct did not select.

*Action:* use `length(p)`, `nodes(p)` and `relationships(p)` on the path. Replace a shortest-path prefix with `shortestPath()` or `allShortestPaths()`, and drop `REPEATABLE ELEMENTS`, `IS DIRECTED` and `USE`. See <<cypher-gql-conformance,ISO GQL Coverage Statement>>.

====== 26.10.2 - Cypher `count(*)` of an `OPTIONAL MATCH` with several arms, and of a Cartesian product

A `count(*)` over a star pattern no longer counts an `OPTIONAL MATCH` that reaches the central node from two sides, or holds two patterns, as two independent optional matches: when one side finds nothing the clause contributes one row, not the number of matches of the other side. *Impact:* the counts of those two star shapes change, and now equal the number of rows the same `MATCH` returns.

====== 26.10.2 - A Postgres cancel request stops the statement and keeps the connection

A `CancelRequest` (what JDBC `Statement.cancel()`, pgjdbc's `setQueryTimeout()` and libpq's `PQcancel` send) now stops
the statement the connection is running with SQLSTATE `57014` and leaves the connection open, as PostgreSQL does
(issue #9689). Before, it closed the whole connection, and since every connection had the backend process id `0`, a
cancel could reach a different connection than the one it named.

*Impact:* after a cancel or a query timeout the connection stays usable instead of being closed.

*Action:* a client that relied on a cancel request closing the connection must call `pg_terminate_backend(pid)`
instead. See <<postgres-cancel,Cancelling a statement>>.

====== 26.10.2 - An HTTP client that disconnects terminates its statement

A client that closes its connection while its statement runs (its own timeout, a killed process, `curl --max-time`)
now terminates the statement, and what it wrote is rolled back unless it had already committed, instead of leaving the server working on it until it completes or
reaches `arcadedb.command.timeout` (issue #9689). This applies to plain HTTP/1.x connections, not to TLS or HTTP/2.
Likewise a gRPC client that cancels a call, or whose deadline expires, terminates the server-side work.

*Impact:* a client that sends a write and closes the connection without waiting for the answer can find the write rolled
back.

*Action:* wait for the response of a write before closing the connection. See
<<http-running-queries,List and terminate running queries>>.

====== 26.10.2 - openCypher temporals are stored natively

openCypher used to store `time()`, `localtime()`, zoned `datetime()` and `duration()` values as Strings and guessed the type back from the text, so a String such as `"09:00-17:00"` read back as a time. They are now stored in four new property types, `OFFSET_TIME`, `LOCAL_TIME`, `ZONED_DATETIME` and `DURATION`, and a new database never reinterprets a String (issues #8572, #9462, #9636). A zoned `datetime()` written to a `DATETIME` property is stored as an instant and reads back as the UTC wall clock; before, it kept the local wall clock.

*Impact:* a database written by an earlier version keeps the old reading of undeclared properties until it is migrated, so existing queries keep working after the upgrade. The migration is one-way and converts every String with a temporal shape on an undeclared property, including one meant as text.

*Action:* take a backup, quiesce writers, and run `CALL db.migrateLegacyTemporals() YIELD records, properties` once per database (under HA, on the leader; the user needs `updateDatabaseSettings`). To convert only some properties, declare each with its new type and copy the values through a scratch property instead. See <<cypher-temporal-migration,Migrating Cypher temporals stored as Strings>>.

====== 26.10.2 - Weighted path finders share one edge-weight rule

Every weighted shortest-path finder now reads an edge weight the same way: an edge without the weight property, or with a value that is not a number, weighs 1, and an edge whose weight is negative, NaN or infinite is not walked (issue #9443). Before, `dijkstra()`, `astar()`, `algo.dijkstra` and `algo.astar` treated a missing weight as 0, and several finders walked negative weights. `duanSSSP()` now accepts an options map `{ direction, edgeTypeNames }` as its fourth argument, answers through the same engine as `cchShortestPath()` and honors the command timeout. `bellmanFord()` and `algo.bellmanford` are unchanged.

*Impact:* on a graph where some edges have no weight, `dijkstra()`, `astar()`, `algo.dijkstra` and `algo.astar` return different paths and distances. A graph with negative weights is now routed around those edges. Among paths of equal weight `duanSSSP()` may return a different one. Embedded code: the `MIN` constant of `SQLFunctionHeuristicPathFinderAbstract` is gone.

*Action:* give every routed edge a weight if 0 was intended, and use `bellmanFord()` where negative weights must be walked. A custom subclass reads the rule from `com.arcadedb.graph.EdgeWeight`. See <<dijkstra,`dijkstra()`>> and <<algo-duan-sssp-sql,`duanSSSP()`>>.

====== 26.10.2 - SQL `UPSERT` requires a UNIQUE index

`UPDATE ... UPSERT WHERE` without a sub-query used to accept any index, so an upsert matched through a non-unique index could create duplicates. It now needs an equality on every property of a UNIQUE index, as the sub-query form already did (issues #9339, #9342).

*Impact:* an `UPSERT` served by a non-unique index, by part of a composite key, or by a range, `IN` or `OR` condition fails with an error stating the requirement.

*Action:* create a UNIQUE index on the properties of the `WHERE` condition, or rewrite the condition as equalities on all of its properties. See <<sql-update,`UPDATE`>>.

====== 26.10.2 - SQL `sum()` over an empty or all-NULL group returns NULL

SQL `sum()` now returns NULL for an empty or all-NULL group, like `avg()`, `min()` and `max()`. It used to return 0 (issues #9351, #9384). Cypher `sum()` keeps returning 0, as openCypher requires.

*Impact:* SQL queries that read `sum()` of such a group get NULL.

*Action:* wrap the aggregate where 0 is expected, for example `ifnull(sum(amount), 0)`.

[discrete]
====== 26.10.2 - SQL `k = <list>` no longer expands the list

An index lookup used to expand a list on the right of `=`, so `k = [1, 2]` behaved like `k IN [1, 2]`, while a scan compared the field with the list. Only `IN` and the other multi-value operators expand a list now; `=` and the range operators compare with the list as one value, which matches nothing on a scalar field (issues #9370, #9385).

*Impact:* a query that relied on `=` with a list to match any element returns no rows.

*Action:* use `IN`.

====== 26.10.2 - A statement that hides a write inside a read is refused on the query path

SQL decided whether a statement reads, writes or changes the schema from its top-level node only, so a write placed in a `LET`, a projection, a `FROM` sub-query, a `CASE`, a `RETURN` or a script block ran durably through the read-only paths (issues #9628, #9687). A statement now counts everything nested in it. `PROFILE` takes the classification of the statement it wraps, so `PROFILE INSERT` is a write (issue #9340). `EXPLAIN` stays read-only.

*Impact:* `Database.query()`, `GET` and `POST /api/v1/query` and MCP identities without write permission refuse such statements. A DDL inside `IF`, `FOREACH` or `WHILE` needs `allowSchemaChange` on MCP.

*Action:* send these statements as commands (`Database.command()`, `POST /api/v1/command`).

====== 26.10.2 - SQL `include()` and `exclude()` return a map

`include()` and `exclude()` used to build a record carrying the source record identity, so calling `save()` on a projection overwrote the stored record. They now always return a map with no `@rid`, `@type` or `@cat` unless one of the names asks for it, and they work on edges (issues #9840, #9873). `UPDATE V SET copy = @this.exclude('secret')` now stores an embedded map instead of a link to the record itself.

*Impact:* code that treated the result as a record (saving it, reading its `@rid`, calling `.out()` on it) changes.

*Action:* apply traversals before the projection, and name `@rid` in `include()` when you need it. See <<include,`include()`>>.

====== 26.10.2 - SQL result rows: `values()` follows `keys()`, and a bare `ORDER BY @rid` on a `MATCH` with columns is refused

`values()` on a sub-query row or `LET` variable used to return the record metadata as extra unlabeled values. It now returns one value per key, in the order of `keys()` (issue #9843). A SQL `MATCH` that returns columns, `$paths` or `$patterns` builds rows with no `@rid`, so `ORDER BY @rid` sorted on null and kept the pattern order; it now fails at planning time (issue #9911). The same applies to other bare record attributes such as `@type`.

*Impact:* code that read the extra values of `values()` sees fewer, and a keyset pagination that used a bare `ORDER BY @rid` on such a `MATCH` fails.

*Action:* write `ORDER BY <alias>.@rid`, or return the RID as a column and order by it. See <<sql-match,`MATCH`>>.

====== 26.10.2 - Schema refuses a `REGEXP` no value can match, and constrained properties on `LIGHTWEIGHT` edges

`CREATE PROPERTY`, `ALTER PROPERTY` and `Property.setRegexp()` refuse a pattern that no value of the property type can match, such as `[A-Z]+` on a `LONG` or a `DATE`, which used to be accepted and then refused every write (issues #9853, #9871). A pattern the check cannot decide in time is accepted with a WARNING. A `MANDATORY` or default-valued property can no longer reach a `LIGHTWEIGHT` edge type through a supertype, by `CREATE EDGE TYPE ... EXTENDS ... LIGHTWEIGHT`, `ALTER TYPE ... SUPERTYPE`, `ALTER TYPE ... WITH lightweight = true` or by declaring the property on the supertype (issue #9846).

*Impact:* such DDL fails with a `SchemaException`. A schema that already holds such a pattern or combination still opens.

*Action:* fix the pattern, or remove it with `ALTER PROPERTY ... REGEXP null`. Make the inherited property optional, or keep the edge type record-backed. See <<sql-alter-property,`ALTER PROPERTY`>> and <<lightweight-edges,Lightweight edges>>.

====== 26.10.2 - Cypher `MERGE` matches what `MATCH` matches, and declared properties compare in their declared type

`MERGE` used its own equality and disagreed with `MATCH`: it missed a stored `FLOAT`, creating a duplicate, and matched a temporal against the text of a `STRING` property (issues #9693, #9696). It now uses the comparison `MATCH` applies. On a property declared `STRING`, a stored text also equals a number, boolean or temporal whose written text it is, so `MATCH (n:S) WHERE n.v = 1` finds the node holding the text `+'1'+`; on a property declared `INTEGER`, `LONG`, `FLOAT`, `DOUBLE`, `BOOLEAN`, `DATE` or `DATETIME`, a text equals the value it converts to (issues #9695, #9794). Undeclared properties keep strict Cypher typing.

*Impact:* a repeated `MERGE` no longer duplicates nodes in these cases, and `=`, `<>`, `IN` and joins on declared properties can return more rows than before.

*Action:* none, unless a query relied on the old mismatch. See <<cypher-merge,`MERGE`>>.

====== 26.10.2 - `DROP CONSTRAINT <name>` does not drop named constraints created by older releases

A named Cypher constraint now records what its `CREATE CONSTRAINT` created, and `DROP CONSTRAINT <name>` removes exactly that; before, it did nothing (issues #9646, #9707). Creating a constraint under a name in use and dropping an unknown name now raise an error, unless `IF NOT EXISTS` or `IF EXISTS` is given.

*Impact:* a named constraint created by an earlier version has no such record, so `DROP CONSTRAINT <name>` raises an error for it.

*Action:* drop an old constraint by its index name, or through SQL (`DROP INDEX`, `ALTER PROPERTY ... MANDATORY false`). See <<cypher-drop-constraint,`DROP CONSTRAINT`>>.

====== 26.10.2 - The `+path.*+` procedures answer as `+apoc.path.*+` does

`path.expandconfig` now reads its `uniqueness` option, with the APOC default `RELATIONSHIP_PATH`, and `path.expand` is breadth-first with `RELATIONSHIP_PATH` (issue #10049). Before, the breadth-first walk was always `NODE_GLOBAL` and the depth-first walk and `path.expand` always `NODE_PATH`. `path.subgraphall` returns every relationship between the returned nodes, whatever the `relationshipFilter` (issue #10048). `relationshipFilter` and `labelFilter` read the APOC syntax, and an unknown relationship type or label is refused (issue #10025).

*Impact:* on a graph with cycles or several routes to a node these procedures return more paths, growing quickly with `maxLevel`. A walk too wide for `arcadedb.queryMaxHeapElementsAllowedPerOp` or `arcadedb.queryMaxHeapRAM` fails the query.

*Action:* to keep the old answers add `uniqueness: 'NODE_GLOBAL'` to a breadth-first `path.expandconfig`, `uniqueness: 'NODE_PATH'` to a depth-first one, and replace `path.expand` with the equivalent `path.expandconfig` call with `bfs: false, uniqueness: 'NODE_PATH'`. See <<path-expand-config,`path.expandconfig`>>.

====== 26.10.2 - An ISO duration text is parsed as Neo4j parses it

The Docker images are built on `eclipse-temurin:25-alpine` instead of Java 21, which enables compact object headers, and `ARCADEDB_OPTS_GC` drops the obsolete `-XX:+ZGenerational` (issue #9602). The jars still run on Java 21 for embedded use. Studio and the Swagger UI page are served with a `Content-Security-Policy` that refuses inline script (issue #9681), set by `arcadedb.server.httpContentSecurityPolicy`.

*Impact:* custom images or scripts that set JVM flags removed in Java 25 fail to start. A reverse proxy or extension that injects inline script into Studio is blocked.

*Action:* check custom JVM options against Java 25. To try a custom policy without blocking, set `arcadedb.server.httpContentSecurityPolicyReportOnly=true`. See <<upgrade-docker,Docker / Kubernetes>>.

[discrete]
====== 26.10.2 - New and rebuilt hash indexes use page layout 3, which older servers cannot open

A `NOTUNIQUE_HASH` key whose record ids would take more than a quarter of a page now keeps them in a chain of pages of their own, so adding a record to a key costs the same whatever the key already holds (issue #9228). Before, the cost of an insert grew with the record ids the key already held: 49 pages were written per insert into a key with 20,000 of them. Every hash index created or rebuilt by 26.10.2, `UNIQUE_HASH` included, is written at page layout version 3. Hash indexes created by older versions keep working at their layout and move to version 3 only on `REBUILD INDEX`.

*Impact:* none on upgrade. A server older than 26.10.2 knows layouts 1 and 2 only, and refuses a hash index at layout 3 (see <<downgrade-hash-indexes>>).

*Action:* to get the new layout on an existing `NOTUNIQUE_HASH` index with large keys, run `REBUILD INDEX` on it. See <<index-hash,Hash index>>.

[discrete]
====== 26.10.2 - Cypher paths are sent as one path object on every protocol

Every Cypher path is now one path value, whatever built it: a `MATCH p = ...` pattern, `shortestPath()`, `allShortestPaths()`, a path procedure, or `apoc.path.create`, `apoc.path.slice` and `apoc.path.combine` (issue #9913). Over HTTP (and `Result.toJSON()`), gRPC and PostgreSQL a path returned by a `MATCH` used to be sent as its text form; it is now the object `{"_type": "path", "nodes": [...], "relationships": [...], "length": n}`, with every node and relationship written whole whatever the JSON serializer settings. A Bolt driver receives a native `Path` for the paths of procedures and `shortestPath()` too, and Studio's graph view draws a returned path.

*Impact:* a client that parsed the text form of a `MATCH` path gets an object instead.

*Action:* read the `nodes`, `relationships` and `length` fields of the object, or return `nodes(p)` and `relationships(p)` explicitly. See <<graph-algo-path-value>>.

[discrete]
====== 26.10.2 - `COMMIT RETRY` and `Database.transaction()` do not retry a leader refusal

A `NeedRetryException` now tells whether retrying on the same server can succeed (`isRetryableOnThisNode()`). An HA follower that refuses leader-only work (a schema change, a security mutation) and names the leader answers `false`, so `BEGIN ... COMMIT RETRY <n>` and `Database.transaction(..., retries)` raise its `ServerIsNotTheLeaderException` on the first attempt (issue #9995). Before, they retried it `<n>` times with the retry delay in between, and `COMMIT RETRY ... ELSE` then ran the `ELSE` block. A refusal raised during an election, which names no leader, is still retried.

*Impact:* the caller gets the leader refusal at once. A `COMMIT RETRY ... ELSE { ... } AND CONTINUE` block no longer runs its `ELSE` or hides the error for such a refusal.

*Action:* send leader-only work to the leader the error names. See <<sql-script-commit>>.

[discrete]
====== 26.10.2 - GraphQL introspection reports real types, and Cypher typed constraints keep a property's attributes

* GraphQL introspection of a type with no `.gql` declaration reports `MAP` and untyped `EMBEDDED` as the new `JSON` scalar, `EMBEDDED OF <T>` as an object, `LINK` as `ID`, `DECIMAL` as the new `BigDecimal` scalar and `BINARY` as a list of `Int`; before, they were all `String`. A sub-selection on a `LINK` property now resolves the linked record (issues #8756, #9467, #9468). See <<graphql-introspection-types,GraphQL type mapping>>.
* `CREATE CONSTRAINT ... REQUIRE n.x IS :: <TYPE>` keeps the property's earlier attributes (`MANDATORY`, `READONLY`, `REGEXP`, `MIN`, `MAX`, `DEFAULT`) instead of dropping them, and checks the records already stored: when one fails, the constraint is refused and the old declaration stays (issue #9304). See <<cypher-is-typed-retype>>.

*Action:* regenerate GraphQL client code built from introspection, and expect a typed constraint over existing data that does not fit to be refused.

[discrete]
====== 26.10.2 - Embedded API changes

* `Schema.alterMaterializedView()` refuses a null mode and a negative interval (`IllegalArgumentException`) and an interval on a `MANUAL` or `INCREMENTAL` view (`SchemaException`), which it used to store (issues #8726, #9381). SQL `ALTER MATERIALIZED VIEW` is unaffected.
* `Schema.unregisterFunctionLibrary()` of a stored library is now saved to `schema.json` and replicated (issues #8879, #9423).
* `Iterator.remove()` on the iterators of `Vertex.getEdges()` and `Vertex.getVertices()` deletes the edge through the database, as `edge.delete()` does, and a refused delete reaches the caller with the entry left in place; a second `remove()` throws `IllegalStateException` (issue #9779). Before, an iterator over given edge types only unlinked the walked side, and one over every edge type logged a refusal and unlinked anyway. See <<vertex-edge-iterator-remove>>.
* On an HA follower, `unregisterFunctionLibrary()`, `Property` setters, `Schema.setExtension()`, the schema date settings and type setters such as `LocalEdgeType.setLightweight()` throw `ServerIsNotTheLeaderException` ("Changes to the schema must be executed on the leader server") instead of changing that follower alone (issues #9747, #9765). `Schema.setZoneId()` checks `UPDATE_DATABASE_SETTINGS`.

*Action:* call these methods on the leader, validate materialized view arguments before passing them, and expect `remove()` on an edge iterator to throw when the delete is refused.

[discrete]
====== 26.10.2 - Client error handling: gRPC writes whose answer was lost, streamed error lines, Postgres transaction modes

* The gRPC Java client throws a non-retryable `RemoteException` when an admin write through `RemoteGrpcServer` or a streaming write (`ingestStream`, `ingestBidi`, `timeSeriesWriteStream`, graph batch loads) ends with a bare `UNAVAILABLE`, since the write may have been applied; reads and `validate_only` dry runs stay retryable. A client-side deadline is a `TimeoutException` whose message says the write may already have been applied (issues #8822, #9470).
* In production mode, the `message` of the `error` line of a streamed query is the classified label, like the `error` field the line now carries in every mode; the detail is in the server log (issues #8899, #9475).
* PostgreSQL: `SERIALIZABLE`, `READ ONLY` and `AND CHAIN` in `BEGIN` / `START TRANSACTION` / `COMMIT` / `ROLLBACK` are refused with SQLSTATE `0A000` instead of a syntax error (issues #9631, #9753).

*Action:* do not retry a write the client reports as possibly applied without checking its outcome, and branch on the `error` field or the status instead of the `message` text.

[[upgrade-single-server]]
===== Single-server upgrade

. Download and extract the new ArcadeDB release in a separate directory (do not overwrite the old install).
. Stop the running server (or close every open database via the HTTP `<<http-servercommand,close database>>` command).
. Copy the directories listed in <<upgrade-what-to-copy,What to copy>> from the old install into the new install, preserving the original paths.
. Start the new server.

When the server starts, every database is opened with the new code and any required format migration is applied in place.

[[upgrade-what-to-copy]]
===== What to copy

ArcadeDB's root directory contains a fixed set of folders.
Only a few of them hold user-owned state; the rest are recreated from the release archive on every install.

[%header,cols="20%,15%,65%"]
|===
|Folder |Action |Notes

|`databases/`
|*Copy*
|The actual database data. Every subdirectory is one database. This is the only folder strictly required for an upgrade.

|`config/`
|*Copy selected files*
|The release ships a default `config/` directory. Carry over only the files you have actually modified — listing below.

|`backups/`
|Copy if you want history
|Backup archives produced by manual or automatic backups. The server does not need them to start; copy them only if you want to keep the backup history reachable from the Studio Backup tab and from `RESTORE DATABASE` commands.

|`log/`
|Skip
|Server log files. Safe to start with an empty `log/` directory; the release ships an empty one. Copy only if you want to keep historical logs alongside the new install.

|`raft-storage-<peerId>/` (HA only)
|*Copy*
|Per-node Raft log segments, created at runtime when HA is enabled. This storage is *durable by default* (`arcadedb.ha.raftPersistStorage=true`) and must be preserved so a node can rejoin by replaying its log instead of a full snapshot resync. When `raftPersistStorage` is explicitly `false`, it is ephemeral and can be skipped. See <<upgrade-ha-cluster,HA cluster upgrade>> for details.

|`replication/`
|Skip
|Legacy directory from the pre-Raft replication implementation. Not used by the current HA stack.

|`lib/`, `bin/`
|Use the new release as-is
|Java artifacts and start scripts. Always take them from the new release — do not copy from the old install. The only exception is custom JARs you have dropped into `lib/` yourself; carry those over by hand.
|===

[[upgrade-config-files]]
====== Files to carry over from `config/`

The `config/` directory ships with a small set of defaults.
You only need to copy the files that you have actually changed:

[%header,cols="35%,65%"]
|===
|File |When to copy

|`server-users.jsonl`
|Always, unless you create users only via REST/SQL on every upgrade.
This is where ArcadeDB persists local users and their per-database group assignments.

|`server-groups.json`
|If you have customised the security policy (custom groups, type-level permissions, result-set limits). See <<security-policy,Security Policy>>.

|`backup.json`
|If you have configured the auto-backup scheduler (schedule, retention, target directory). See <<auto-backup,Automatic Backup>>.

|`arcadedb-log.properties`
|If you have tuned `java.util.logging` settings (log levels, rolling file size, etc.).

|`gremlin-server.yaml`, `gremlin-server.groovy`, `gremlin-server.properties`
|Only if you use the embedded Gremlin Server and have edited any of these.
|===

Everything else under `config/` (for example `arcadedb-log-all.properties`) ships unchanged with each release; take the new version.

NOTE: ArcadeDB does *not* read a `config/server-configuration.json` file in normal operation.
Server-wide settings come from JVM system properties, environment variables and the `arcadedb-server.sh` arguments — see <<server,Server Configuration>>.

[[upgrade-ha-cluster]]
===== HA cluster upgrade

An HA cluster (see <<ha-concepts,High Availability>>) is upgraded one node at a time.
The per-node procedure is the same as <<upgrade-single-server,single-server>> above, with the following clarifications.

What to migrate on each node:

* *`databases/`* — copy, exactly as in the single-server case.
* *`config/`* — copy the same files as in the single-server case.
The cluster's identity is derived from `arcadedb.ha.clusterName` and the `root` password (the inter-node token is computed from them at startup), so as long as every node keeps the same cluster name and the same root password, the upgraded cluster reattaches to itself without any extra step.
* *`raft-storage-<peerId>/`* — *copy*.
The local Raft log is durable by default (`arcadedb.ha.raftPersistStorage=true`), so preserve this directory across the upgrade to let the node rejoin by replaying its own log.
Whether or not it is preserved, after the upgraded node rejoins the cluster the leader replays any missing entries via Raft or, if the node has fallen behind the purge boundary, streams a full snapshot over HTTP automatically.
With `raftPersistStorage=false` this directory is ephemeral and can be skipped.
* *`backups/` and `log/`* — same as single-server.

Recommended rolling upgrade flow (zero downtime, requires quorum at all times):

. Pick a non-leader node first.
. Stop the node, install the new release in a separate directory, copy the folders listed above, start the new binary.
. Wait until `GET /api/v1/cluster` reports the node as healthy and caught up (replication lag near zero).
.. The <<studio-cluster,Studio Cluster tab>> shows the same information visually.
. Repeat for every remaining replica.
. Step the leader down with `POST /api/v1/cluster/stepdown` (or simply stop it — Raft will elect a new leader) and upgrade it last.

[NOTE]
====
A node that receives replicated TIMESERIES data for a type it does not have -- or for a type that
exists locally but is not a TIMESERIES one -- refuses the entry, which quarantines that database and triggers an
automatic resync from the leader. Earlier releases logged the problem and carried on, which left the node's copy
of that type permanently behind the leader's with nothing but a log line to say so.

This should not occur during an ordinary rolling upgrade, since the entry that creates a type is always applied
before data for it arrives. It is a safeguard for the case where it does -- for instance a mixed-version window
in which one node's build cannot construct a type another node has. If you see a database quarantined with a
message about a TimeSeries sealed store, the resync will restore it; complete the rollout so every node runs the
same build.
====

For first-time HA bring-up with a pre-existing database (e.g. when you scale a single-node install into a cluster), see <<ha-offline-bootstrap,Offline Cluster Bootstrap>>.

[[upgrade-docker]]
===== Docker / Kubernetes

When you run ArcadeDB from the official container image, the release is replaced atomically by changing the image tag.
The only data that survives across container restarts is what lives on a persistent volume, so:

* Mount `/home/arcadedb/databases` on a persistent volume — this is the equivalent of "copy the `databases/` folder".
* Mount `/home/arcadedb/config` only if you have edited the files listed in <<upgrade-config-files>>; otherwise let the image ship its defaults.
* Set `arcadedb.ha.raftStorageDirectory` to a static path (e.g. `/home/arcadedb/raft-storage`) and mount *that* path on a persistent volume. The default per-node directory is named `raft-storage-<nodeName>` dynamically, which a container runtime or Kubernetes cannot mount as a volume (a wildcard like `/home/arcadedb/raft-storage-*` is created literally, not expanded) — this is exactly what `raftStorageDirectory` is for. The Raft log is durable by default (`arcadedb.ha.raftPersistStorage=true`) so a restarted pod can replay its own log instead of resyncing from peers. With `raftPersistStorage=false`, the log is ephemeral and this mount is unnecessary.
* Mount `/home/arcadedb/backups` if you want to retain backup archives across pod restarts.

For Kubernetes specifics (StatefulSet, headless service, init container for pre-staging a database), see <<kubernetes,Kubernetes>>.

[[downgrade]]
==== Downgrade ArcadeDB

In case you need to downgrade to an older version of ArcadeDB, check the binary compatibility between the versions.
ArcadeDB uses calendar versioning in the format `YY.M.S` (year, month, serial: for example `26.12.1` is the first release of December 2026), with 100% on-disk compatibility for migration of databases up or down between *serial* releases of the same year and month (the `S` in `YY.M.S`).
For downgrades across months the safest path is to export the database with the newer version and re-import it with the older version.
See <<versioning-policy,Versioning, Compatibility and Deprecation Policy>> for the full compatibility rules.

[[downgrade-ha]]
===== Downgrading a node of an HA cluster

A cluster replicates schema changes in a compact format that older builds cannot read.
Those entries stay in the Raft log, so a node that is restarted on an older build replays them and ends up with a schema that no longer matches the rest of the cluster - silently.

*A node of a cluster must not be rolled back to an older build by restarting it on its existing Raft log.*
If you have to go back, rebuild the node instead: stop it, delete its `raft-storage-<peerId>/` directory and its `databases/` folder, and start the older build so it rejoins empty and takes a fresh copy from the leader.

NOTE: This applies only to the Raft log, not to your data. Database files themselves keep the usual serial-release compatibility described above.

[[downgrade-hash-indexes]]
===== Downgrading from 26.10.2 or later with hash indexes

Since v26.10.2 every hash index (`UNIQUE_HASH` or `NOTUNIQUE_HASH`) that is created or rebuilt is written at page layout version 3, which older servers do not know.
A server that predates this layout refuses such an index with:

----
Hash index '<name>' has the page layout version 3, which this server does not support (it knows 1 and 2). It was created by a newer version: open the database with that version, or drop and recreate the index.
----

Hash indexes that 26.10.2 opened but did not rebuild keep their older layout and still open on an older server.
Before going back, drop the hash indexes created or rebuilt by 26.10.2 (the layout version is part of the index file name) and recreate them once the database runs on the older server, or export the database and re-import it.
Do not open a database holding a hash index created or rebuilt at layout 3 with a server that predates the layout check, because it does not verify the layout version: see <<index-hash,Hash index>>.
