[[ext-fns-schema-meta]]
==== Schema & Meta Procedures

===== Meta/Schema Procedures


[[meta-graph]]
===== meta.graph()

Get a virtual graph representing the database schema structure.

*Syntax:* `CALL meta.graph([config]) YIELD nodes, relationships`

*Returns:*

* `nodes` - One virtual node per label that has nodes, carrying that label and the properties `name` and `count`
* `relationships` - One virtual relationship per start label, relationship type and end label that occur together,
with the properties `type`, `out` (relationships of the type leaving a node with the start label), `in` (relationships
of the type reaching a node with the end label) and `count` (all relationships of the type)

The optional `config` map is accepted for APOC compatibility and does not narrow the answer. The call reads every
relationship record once, so its cost grows with the number of relationships.

The relationships of a `LIGHTWEIGHT` edge type are counted too (_since v26.12.1_, earlier versions left them out). They
have no record, so the call walks the nodes you may read once and counts the entries of their outgoing edge lists; this
extra walk is paid only by a database that declares such a type. A relationship leaving a node you may not read is not
counted. See <<lightweight-edges,Lightweight edges>>.

*APOC Compatible:* `apoc.meta.graph`

[source,cypher]
----
CALL meta.graph() YIELD nodes, relationships
RETURN nodes, relationships
----

'''

[[meta-schema]]
===== meta.nodetypeproperties()

Get property information for each node type.

*Syntax:* `CALL meta.nodetypeproperties([config]) YIELD nodeType, nodeLabels, propertyName, propertyTypes, mandatory, propertyObservations, totalObservations`

*Returns:* one row per label set and property found in the data or declared in the schema:

* `nodeType` - The labels in APOC's form, for example ``:`Person` ``
* `nodeLabels` - List of the labels
* `propertyName` - Name of the property, null for a label set whose nodes have no property
* `propertyTypes` - List of the value types found, with APOC's names (`String`, `Long`, `Double`, `Boolean`,
`StringArray`, `LongArray`, `Date`, `DateTime`, `LocalDateTime`, `Duration`, `Point`, ...)
* `mandatory` - Whether the schema declares the property mandatory
* `propertyObservations` - How many of the examined nodes carry the property (0 for a property only declared in the schema)
* `totalObservations` - How many nodes were examined

The nodes are sampled as APOC samples them: every `count / sample`-th node of each label. The optional `config` map
takes `sample` (default 1000, -1 reads every node), `includeLabels` and `excludeLabels` (and APOC's deprecated `labels`
and `excludes`). Other keys are ignored.

*APOC Compatible:* `apoc.meta.nodeTypeProperties`

[source,cypher]
----
CALL meta.nodetypeproperties() YIELD nodeType, propertyName, propertyTypes
RETURN nodeType, propertyName, propertyTypes
----

'''

[[meta-rel-type-properties]]
===== meta.reltypeproperties()

Get property information for each relationship type.

*Syntax:* `CALL meta.reltypeproperties([config]) YIELD relType, sourceNodeLabels, targetNodeLabels, propertyName, propertyTypes, mandatory, propertyObservations, totalObservations`

*Returns:* one row per relationship type, start labels, end labels and property, with the same columns as
`meta.nodetypeproperties()` plus:

* `relType` - The relationship type in APOC's form, for example ``:`KNOWS` ``
* `sourceNodeLabels` - Labels of the start nodes
* `targetNodeLabels` - Labels of the end nodes

The relationships examined are the outgoing ones of the sampled nodes, at most `maxRels` (default 100) per node. The
optional `config` map takes `sample`, `maxRels`, `includeLabels`, `excludeLabels`, `includeRels` and `excludeRels` (and
APOC's deprecated `labels`, `rels` and `excludes`).

*APOC Compatible:* `apoc.meta.relTypeProperties`

[source,cypher]
----
CALL meta.reltypeproperties() YIELD relType, propertyName, propertyTypes
RETURN relType, propertyName, propertyTypes
----

---
===== meta.schema()

Get detailed schema information including all types and properties.

*Syntax:* `CALL meta.schema([config]) YIELD value`

The optional `config` map is accepted for APOC compatibility and does not change the answer.

*Returns:* `value` - Map containing:

* `nodeLabels` - List of vertex types with their properties
* `relationshipTypes` - List of edge types with their properties

*APOC Compatible:* `apoc.meta.schema`

[source,cypher]
----
CALL meta.schema() YIELD value
RETURN value.nodeLabels AS nodeTypes
----

'''

[[meta-stats]]
===== meta.stats()

Get database statistics including counts of nodes and relationships.

*Syntax:* `CALL meta.stats() YIELD labelCount, relTypeCount, propertyKeyCount, nodeCount, relCount, labels, relTypes, relTypesCount, stats`

*Returns:* APOC's columns:

* `labelCount` - Number of node labels that have nodes
* `relTypeCount` - Number of relationship types that have relationships
* `propertyKeyCount` - Number of property keys, the ones the schema declares plus the ones found on a sample of the records
* `nodeCount` - Total number of nodes
* `relCount` - Total number of relationships
* `labels` - Map of label to count
* `relTypes` - Map of relationship pattern to count, with the keys `()-[:T]->()`, `(:L)-[:T]->()` and `()-[:T]->(:L)`
* `relTypesCount` - Map of relationship type to count
* `stats` - All the above in one map

A column `value`, a map with the same counts and `relTypes` by type name, is kept for the queries written before these
columns existed. The call reads every relationship record once, so its cost grows with the number of relationships.

The relationships of a `LIGHTWEIGHT` edge type are counted too (_since v26.12.1_, earlier versions left them out of
`relCount`, `relTypeCount`, `relTypes` and `relTypesCount`). They have no record, so the call walks the nodes you may
read once and counts the entries of their outgoing edge lists; this extra walk is paid only by a database that declares
such a type. A relationship leaving a node you may not read is not counted, and a `LIGHTWEIGHT` relationship has no
property, so it adds nothing to `propertyKeyCount`. See <<lightweight-edges,Lightweight edges>>.

*APOC Compatible:* `apoc.meta.stats`

[source,cypher]
----
CALL meta.stats() YIELD nodeCount, relCount, labels
RETURN nodeCount AS nodes, relCount AS relationships, labels
----

'''

[[merge-relationship]]
===== merge.node()

Create or match a node by labels and properties.

*Syntax:* `CALL merge.node(labels, matchProps, createProps, onMatchProps) YIELD node`

*Parameters:*
[%header,cols="2,2,4"]
|===
| Parameter | Type | Description
| labels | List of String | Labels for the node
| matchProps | Map | Properties to match on
| createProps | Map | Properties to set when the node is newly created (optional)
| onMatchProps | Map | Properties to set when the node already exists (optional)
|===

*Returns:* `node` - The merged node

*APOC Compatible:* `apoc.merge.node`

[source,cypher]
----
CALL merge.node(["Person"], {email: "alice@example.com"}, {name: "Alice", created: date.currentTimestamp()}) YIELD node
RETURN node

// with onMatchProps: bump a visit counter only when the node already existed
CALL merge.node(["Person"], {email: "alice@example.com"}, {name: "Alice"}, {lastSeen: date.currentTimestamp()}) YIELD node
RETURN node
----

---
===== merge.relationship()

Create or match a relationship between two nodes.

*Syntax:* `CALL merge.relationship(startNode, relType, matchProps, createProps, endNode [, onMatchProps]) YIELD rel`

*Parameters:*
[%header,cols="2,2,4"]
|===
| Parameter | Type | Description
| startNode | Node | Starting node
| relType | String | Relationship type name
| matchProps | Map | Properties to match on
| createProps | Map | Properties to set on create
| endNode | Node | Ending node
| onMatchProps | Map | Optional. Properties to set when the relationship already exists. Default `{}`
|===

*Returns:* `rel` - The merged relationship

`createProps` is applied only when the relationship is created, and `onMatchProps` only when an existing one is matched.
Leaving `onMatchProps` out, or passing `{}`, leaves a matched relationship untouched, which is what the five-argument form has
always done. A `LIGHTWEIGHT` edge type has no record to hold properties, so a non-empty `onMatchProps` on one is refused.

*APOC Compatible:* `apoc.merge.relationship`

[source,cypher]
----
MATCH (a:Person {name: "Alice"}), (b:Person {name: "Bob"})
CALL merge.relationship(a, "KNOWS", {}, {since: 2024}, b) YIELD rel
RETURN rel

// Set a property on create, update another one when the relationship is already there:
MATCH (a:Person {name: "Alice"}), (b:Person {name: "Bob"})
CALL merge.relationship(a, "KNOWS", {}, {since: 2024}, b, {confirmed: true}) YIELD rel
RETURN rel

// With batch processing:
UNWIND $batch AS row
MATCH (a), (b) WHERE elementId(a) = row.source AND elementId(b) = row.target
CALL merge.relationship(a, row.relType, {}, row.props, b) YIELD rel
RETURN count(rel)
----

'''
