[[upgrade]]
==== Upgrade ArcadeDB

ArcadeDB automatically upgrades a database to a newer on-disk format when a newer version of ArcadeDB opens it.
The migration is transparent and happens lazily on first open, so the only operator step is to point the new binaries at your existing data.

[[upgrade-breaking-changes]]
===== Breaking changes

This section lists behavior changes that may require action when upgrading.

[discrete]
====== 26.11.1 - A taken schema object name is a conflict, not a server error

Creating, or renaming onto, a name already taken by a type, property, index, constraint, bucket, trigger, view or function now raises `com.arcadedb.exception.AlreadyExistsException`, a `SchemaException` (issue #10153). Before, the SQL statements raised `CommandExecutionException`, and defining a function or a library twice, or renaming or copying a type onto a taken name, raised `IllegalArgumentException`.

*Impact:* over HTTP these answer `409` instead of `500` (or `400` for a rename); over PostgreSQL `42P07`, `42701` or `42710` instead of `XX000` or `42P01`; over Bolt a `Neo.ClientError.Schema.*AlreadyExists` code; over gRPC `ALREADY_EXISTS`. Embedded or remote Java code that caught `IllegalArgumentException` or `CommandExecutionException` for this case no longer catches it.

*Action:* catch `AlreadyExistsException` (or `SchemaException`) where you handle a name that is already taken. Clients that keyed on the old status codes should expect the new ones.

[discrete]
====== 26.10.2 - Client requests wait in a queue when the server is busy

Every request of a remote client (HTTP, Postgres, BOLT, Redis, gRPC, Gremlin Server, MCP, MongoDB) now goes through a query admission gate: at most twice the number of cores run at once, and a request that arrives when they are all taken, or when the running queries hold more than 80% of the query heap budget, waits in a queue and starts in arrival order (issue #9518). Before, every request started at once, and under a burst of heavy queries the last ones were refused by the heap budget or exhausted the heap.

*Impact:* under load a request can wait before it starts, up to `arcadedb.queryQueueTimeout` (30 seconds by default), and is refused as retryable once that runs out or when `arcadedb.queryQueueMaxSize` requests already wait (HTTP `503`). A MongoDB request is refused at once instead of waiting. A BOLT result stream that is not read to the end keeps its slot until it is.

*Action:* none for most installations. Size the gate with `arcadedb.queryMaxConcurrent`, `arcadedb.queryAdmissionHeapWatermark`, `arcadedb.queryQueueTimeout` and `arcadedb.queryQueueMaxSize` (see <<setting-table,Settings>>), or set `arcadedb.queryMaxConcurrent=0` for the previous behavior.

[discrete]
====== 26.10.2 - The Gremlin plugin fails the server start when its port is busy

If the Gremlin port (`gremlin.port`, default `8182`) is already in use, the server now stops with an error. Before, it started without a Gremlin listener and still advertised the port in `GET /api/v1/server` (issue #9319). With `gremlin.port=0` a free port is chosen at startup and advertised.

*Impact:* a server that used to start while another process held the Gremlin port no longer starts.

*Action:* free the port or set `gremlin.port` to a free one.

[discrete]
====== 26.10.2 - A plain `=` / `IN` on a `COLLATE CI` index is case sensitive

The planner used to return every case variant for `WHERE Name = 'JOHN'` when a `COLLATE CI` index served the query, while the same predicate evaluated by a scan was case sensitive (issue #9403). The index no longer changes the answer: a plain `=` or `IN` is case sensitive with or without it.

*Impact:* a query that relied on `Name = 'john'` finding `"John"` through a `COLLATE CI` index now returns fewer rows.

*Action:* write the lookup on `Name.toLowerCase()`, for example `WHERE Name.toLowerCase() = 'john'`, which the index serves. See <<case-insensitive-indexes,Case-insensitive indexes>>.

[discrete]
====== 26.10.2 - Cypher: a path variable over a quantified group is one path, and ignored GQL constructs are refused

`MATCH p = ((m)-[r]->(n)){2}` used to bind `p` to a list with one path per repetition. It now binds one path running through every repetition, as any other path variable does and as Neo4j Cypher 25 does: `valueType(p)` is `PATH NOT NULL` and `length(p)` is 2 (issue #9940). Variables declared inside the group (`m`, `r`, `n`) are still lists.

GQL constructs that the parser accepted and the engine ignored now fail with a `FeatureNotImplemented` error that names the construct:

* the path search prefixes `ANY SHORTEST`, `ALL SHORTEST`, `SHORTEST k`, `SHORTEST k GROUPS`, `ANY` and `ANY k`
* the match mode `REPEATABLE ELEMENTS`
* `x IS DIRECTED`
* `USE` of a graph other than the current database
* a quantified group nested inside another one

An `ORDER BY`, `SKIP`, `OFFSET` or `LIMIT` written after `RETURN` (`RETURN ... LIMIT 2 OFFSET 1`) is now applied after the RETURN's sort, as one page: sort, then skip, then limit.

*Impact:* a query that read such a `p` as a list (`size(p)`, `p[0]`) gets a path instead. A query that used one of the refused constructs fails instead of returning rows the construct did not select.

*Action:* use `length(p)`, `nodes(p)` and `relationships(p)` on the path. Replace a shortest-path prefix with `shortestPath()` or `allShortestPaths()`, and drop `REPEATABLE ELEMENTS`, `IS DIRECTED` and `USE`. See <<cypher-gql-conformance,ISO GQL Coverage Statement>>.

[discrete]
====== 26.10.2 - Cypher `DURATION` arithmetic is exact, and `date * duration` is an error

Durations stored in a property are read back as durations, including short ones such as `P1D`, so `ORDER BY` and comparisons on them now work (issue #9338). Duration arithmetic raises an arithmetic error when the result does not fit, instead of returning a wrong value. A date or time combined with a duration using `*`, `/` or `%` is now a type error, and `duration + date` is accepted.

*Impact:* a query that relied on a stored duration being plain text, or on `date * duration` returning a date, changes.

*Action:* none for normal use. A range index on a duration property still orders by its text form (issue #9348).

[discrete]
====== 26.10.2 - Sparse-vector top-K is split across workers from 50,000 postings

`vector.sparseNeighbors` on an `LSM_SPARSE_VECTOR` index now splits a query across the scoring workers once its terms hold 50,000 postings in total (setting `arcadedb.sparseVectorScoringMinPostingsForPartitioning`, default `50000`, was `200000`). Queries between 50,000 and 200,000 postings used to run on one thread and set the slowest latencies. A query just past the threshold uses two ranges and leaves the other workers free; wider queries use more (issue #9482).

*Impact:* results are the same. Queries in that size range are faster, and use more CPU when the server is otherwise idle.

*Action:* none. On a small or shared server where CPU matters more than latency, raise `arcadedb.sparseVectorScoringMinPostingsForPartitioning` (for example back to `200000`).

[discrete]
====== 26.10.2 - Production mode conceals error text on Bolt, Redis, `/ws` and MCP

In `production` server mode the `/ws` insert session, `/ws` change-event subscriptions, Bolt, Redis and MCP now answer an engine failure with "The request failed. Check the server log for the details" and write the detail to the server log, as HTTP, gRPC, PostgreSQL, MongoDB and Gremlin Server already did (issue #8749). Before, they returned the engine's message as is, including the stored values of a duplicated key.

*Impact:* a client of these protocols that reads the error text in production gets the generic message. Error codes, Neo4j status codes, RESP prefixes and exception class names are unchanged, and so is text the protocol writes about the request itself.

*Action:* branch on the code rather than on the message, and read the detail from the server log. See <<production-mode-errors,Error details in production mode>>.

[discrete]
====== 26.10.2 - `list queries` names the client on every protocol

Every entry of `list queries` and `SHOW TRANSACTIONS` now carries the client that asked for the work: `clientAddress` for MCP tool calls (`stdio` for the stdio transport), `/ws` insert sessions, the Gremlin Server and gRPC, which listed none before, plus a `connectionId` for the Gremlin Server and `/ws` (issue #9962). A client whose address the transport cannot report has no `clientAddress` field, where it used to be listed as `"null"`.

*Impact:* tools that read the listing see the new fields. Plugins that open entries through `RunningQueryRegistry.register(...)` or `open(...)` now pass a `RunningQuery.Client` (`RunningQuery.Client.NONE` when there is no client).

*Action:* none for clients. Plugin code: add the client argument. See <<http-running-queries,`list queries`>>.

[discrete]
====== 26.10.2 - Graph algorithms answer the incoming side of unidirectional edge types

The `algo.*` and `path.*` procedures, the path-finding SQL functions (`dijkstra()`, `astar()`, `bellmanFord()`, `cchShortestPath()`, `duanSSSP()`) and the `node.degree*` / `node.relationship.*` functions now follow the edges of a `UNIDIRECTIONAL` type from their target too, as a Graph Analytical View already did (issue #8629). Before, they saw such an edge from its source only, so for example a walk with direction `IN` or `BOTH` missed it. `refactor.mergeNodes`, `refactor.cloneNodesWithRelationships` and changing a node's labels in Cypher no longer drop the incoming unidirectional edges of the node.

*Impact:* results over unidirectional edge types can change (more paths, higher in-degrees, different scores), and now match the results with a Graph Analytical View.

*Action:* none. See <<sql-create-type,`CREATE TYPE`>> for the heap a walk from the target takes.

[discrete]
====== 26.10.2 - Cypher counts match an undirected self loop once

An undirected relationship pattern such as `(n)-[:KNOWS]-(m)` matches a self loop (an edge from a vertex to itself) once, as the openCypher specification and Neo4j do. The rows of such a pattern always did, but the counts computed without materializing the rows counted it twice: `MATCH (a)-[:KNOWS]-(b) RETURN count(*)`, a `count(*)` grouped by the start node, `OPTIONAL MATCH ... WITH n, count(m)` and the `COUNT { }` subquery, with and without a Graph Analytical View (issues #8750, #9540). The same release corrects the count of a chain with an inequality such as `WHERE a <> c` when the chain has a labelled or multi-hop part before or after the two positions the inequality compares.

*Impact:* those counts can be lower than before on graphs with self loops, or on such chains, and now equal the number of rows the same `MATCH` returns.

*Action:* none.

[discrete]
====== 26.10.2 - Cypher `count(*)` of an `OPTIONAL MATCH` with several arms, and of a Cartesian product

A `count(*)` over a star pattern no longer counts an `OPTIONAL MATCH` that reaches the central node from two sides, or holds two patterns, as two independent optional matches: when one side finds nothing the clause contributes one row, not the number of matches of the other side. A star next to a node pattern that shares no variable with it, `MATCH (a)-[:R]->(b), (a)-[:S]->(c), (t:Tag)`, now multiplies by the `Tag` count, which it used to leave out. Both were answered by the count push-down without building the rows (issue #9596).

`count(*)` over parts of a `MATCH` that share no variable is now the product of the parts' counts and builds no row, so a count whose result does not fit a 64-bit integer raises an error instead of running until the command timeout.

*Impact:* the counts of those two star shapes change, and now equal the number of rows the same `MATCH` returns.

*Action:* none.

[discrete]
====== 26.10.2 - A Postgres cancel request stops the statement and keeps the connection

A `CancelRequest` (what JDBC `Statement.cancel()`, pgjdbc's `setQueryTimeout()` and libpq's `PQcancel` send) now stops
the statement the connection is running with SQLSTATE `57014` and leaves the connection open, as PostgreSQL does
(issue #9689). Before, it closed the whole connection, and since every connection had the backend process id `0`, a
cancel could reach a different connection than the one it named.

*Impact:* after a cancel or a query timeout the connection stays usable instead of being closed.

*Action:* a client that relied on a cancel request closing the connection must call `pg_terminate_backend(pid)`
instead. See <<postgres-cancel,Cancelling a statement>>.

[discrete]
====== 26.10.2 - An HTTP client that disconnects terminates its statement

A client that closes its connection while its statement runs (its own timeout, a killed process, `curl --max-time`)
now terminates the statement, and what it wrote is rolled back unless it had already committed, instead of leaving the server working on it until it completes or
reaches `arcadedb.command.timeout` (issue #9689). This applies to plain HTTP/1.x connections, not to TLS or HTTP/2.
Likewise a gRPC client that cancels a call, or whose deadline expires, terminates the server-side work.

*Impact:* a client that sends a write and closes the connection without waiting for the answer can find the write rolled
back.

*Action:* wait for the response of a write before closing the connection. See
<<http-running-queries,List and terminate running queries>>.

[discrete]
====== 26.10.2 - openCypher temporals are stored natively

openCypher used to store `time()`, `localtime()`, zoned `datetime()` and `duration()` values as Strings and guessed the type back from the text, so a String such as `"09:00-17:00"` read back as a time. They are now stored in four new property types, `OFFSET_TIME`, `LOCAL_TIME`, `ZONED_DATETIME` and `DURATION`, and a new database never reinterprets a String (issues #8572, #9462, #9636). A zoned `datetime()` written to a `DATETIME` property is stored as an instant and reads back as the UTC wall clock; before, it kept the local wall clock.

*Impact:* a database written by 26.10.1 or earlier keeps the old reading of undeclared properties until it is migrated, so existing queries keep working after the upgrade. The migration is one-way and converts every String with a temporal shape on an undeclared property, including one meant as text.

*Action:* take a backup, quiesce writers, and run `CALL db.migrateLegacyTemporals() YIELD records, properties` once per database (under HA, on the leader; the user needs `updateDatabaseSettings`). To convert only some properties, declare each with its new type and copy the values through a scratch property instead. See <<cypher-temporal-migration,Migrating Cypher temporals stored as Strings>>.

[discrete]
====== 26.10.2 - Weighted path finders share one edge-weight rule

Every weighted shortest-path finder now reads an edge weight the same way: an edge without the weight property, or with a value that is not a number, weighs 1, and an edge whose weight is negative, NaN or infinite is not walked (issue #9443). Before, `dijkstra()`, `astar()`, `algo.dijkstra` and `algo.astar` treated a missing weight as 0, and several finders walked negative weights. `duanSSSP()` now accepts an options map `{ direction, edgeTypeNames }` as its fourth argument, answers through the same engine as `cchShortestPath()` and honors the command timeout. `bellmanFord()` and `algo.bellmanford` are unchanged.

*Impact:* on a graph where some edges have no weight, `dijkstra()`, `astar()`, `algo.dijkstra` and `algo.astar` return different paths and distances. A graph with negative weights is now routed around those edges. Among paths of equal weight `duanSSSP()` may return a different one. Embedded code: the `MIN` constant of `SQLFunctionHeuristicPathFinderAbstract` is gone.

*Action:* give every routed edge a weight if 0 was intended, and use `bellmanFord()` where negative weights must be walked. A custom subclass reads the rule from `com.arcadedb.graph.EdgeWeight`. See <<dijkstra,`dijkstra()`>> and <<algo-duan-sssp-sql,`duanSSSP()`>>.

[discrete]
====== 26.10.2 - SQL `UPSERT` requires a UNIQUE index

`UPDATE ... UPSERT WHERE` without a sub-query used to accept any index, so an upsert matched through a non-unique index could create duplicates. It now needs an equality on every property of a UNIQUE index, as the sub-query form already did (issues #9339, #9342).

*Impact:* an `UPSERT` served by a non-unique index, by part of a composite key, or by a range, `IN` or `OR` condition fails with an error stating the requirement.

*Action:* create a UNIQUE index on the properties of the `WHERE` condition, or rewrite the condition as equalities on all of its properties. See <<sql-update,`UPDATE`>>.

[discrete]
====== 26.10.2 - SQL `sum()` over an empty or all-NULL group returns NULL

SQL `sum()` now returns NULL for an empty or all-NULL group, like `avg()`, `min()` and `max()`. It used to return 0 (issues #9351, #9384). Cypher `sum()` keeps returning 0, as openCypher requires.

*Impact:* SQL queries that read `sum()` of such a group get NULL.

*Action:* wrap the aggregate where 0 is expected, for example `ifnull(sum(amount), 0)`.

[discrete]
====== 26.10.2 - SQL `k = <list>` no longer expands the list

An index lookup used to expand a list on the right of `=`, so `k = [1, 2]` behaved like `k IN [1, 2]`, while a scan compared the field with the list. Only `IN` and the other multi-value operators expand a list now; `=` and the range operators compare with the list as one value, which matches nothing on a scalar field (issues #9370, #9385).

*Impact:* a query that relied on `=` with a list to match any element returns no rows.

*Action:* use `IN`.

[discrete]
====== 26.10.2 - A statement that hides a write inside a read is refused on the query path

SQL decided whether a statement reads, writes or changes the schema from its top-level node only, so a write placed in a `LET`, a projection, a `FROM` sub-query, a `CASE`, a `RETURN` or a script block ran durably through the read-only paths (issues #9628, #9687). A statement now counts everything nested in it. `PROFILE` takes the classification of the statement it wraps, so `PROFILE INSERT` is a write (issue #9340). `EXPLAIN` stays read-only.

*Impact:* `Database.query()`, `GET` and `POST /api/v1/query` and MCP identities without write permission refuse such statements. A DDL inside `IF`, `FOREACH` or `WHILE` needs `allowSchemaChange` on MCP.

*Action:* send these statements as commands (`Database.command()`, `POST /api/v1/command`).

[discrete]
====== 26.10.2 - SQL `include()` and `exclude()` return a map

`include()` and `exclude()` used to build a record carrying the source record identity, so calling `save()` on a projection overwrote the stored record. They now always return a map with no `@rid`, `@type` or `@cat` unless one of the names asks for it, and they work on edges (issues #9840, #9873). `UPDATE V SET copy = @this.exclude('secret')` now stores an embedded map instead of a link to the record itself.

*Impact:* code that treated the result as a record (saving it, reading its `@rid`, calling `.out()` on it) changes.

*Action:* apply traversals before the projection, and name `@rid` in `include()` when you need it. See <<include,`include()`>>.

[discrete]
====== 26.10.2 - SQL result rows: `values()` follows `keys()`, and a bare `ORDER BY @rid` on a `MATCH` with columns is refused

`values()` on a sub-query row or `LET` variable used to return the record metadata as extra unlabeled values. It now returns one value per key, in the order of `keys()` (issue #9843). A SQL `MATCH` that returns columns, `$paths` or `$patterns` builds rows with no `@rid`, so `ORDER BY @rid` sorted on null and kept the pattern order; it now fails at planning time (issue #9911). The same applies to other bare record attributes such as `@type`.

*Impact:* code that read the extra values of `values()` sees fewer, and a keyset pagination that used a bare `ORDER BY @rid` on such a `MATCH` fails.

*Action:* write `ORDER BY <alias>.@rid`, or return the RID as a column and order by it. See <<sql-match,`MATCH`>>.

[discrete]
====== 26.10.2 - Schema refuses a `REGEXP` no value can match, and constrained properties on `LIGHTWEIGHT` edges

`CREATE PROPERTY`, `ALTER PROPERTY` and `Property.setRegexp()` refuse a pattern that no value of the property type can match, such as `[A-Z]+` on a `LONG` or a `DATE`, which used to be accepted and then refused every write (issues #9853, #9871). A pattern the check cannot decide in time is accepted with a WARNING. A `MANDATORY` or default-valued property can no longer reach a `LIGHTWEIGHT` edge type through a supertype, by `CREATE EDGE TYPE ... EXTENDS ... LIGHTWEIGHT`, `ALTER TYPE ... SUPERTYPE`, `ALTER TYPE ... WITH lightweight = true` or by declaring the property on the supertype (issue #9846).

*Impact:* such DDL fails with a `SchemaException`. A schema that already holds such a pattern or combination still opens.

*Action:* fix the pattern, or remove it with `ALTER PROPERTY ... REGEXP null`. Make the inherited property optional, or keep the edge type record-backed. See <<sql-alter-property,`ALTER PROPERTY`>> and <<lightweight-edges,Lightweight edges>>.

[discrete]
====== 26.10.2 - Cypher `MERGE` matches what `MATCH` matches, and declared properties compare in their declared type

`MERGE` used its own equality and disagreed with `MATCH`: it missed a stored `FLOAT`, creating a duplicate, and matched a temporal against the text of a `STRING` property (issues #9693, #9696). It now uses the comparison `MATCH` applies. On a property declared `STRING`, a stored text also equals a number, boolean or temporal whose written text it is, so `MATCH (n:S) WHERE n.v = 1` finds the node holding the text `+'1'+`; on a property declared `INTEGER`, `LONG`, `FLOAT`, `DOUBLE`, `BOOLEAN`, `DATE` or `DATETIME`, a text equals the value it converts to (issues #9695, #9794). Undeclared properties keep strict Cypher typing.

*Impact:* a repeated `MERGE` no longer duplicates nodes in these cases, and `=`, `<>`, `IN` and joins on declared properties can return more rows than before.

*Action:* none, unless a query relied on the old mismatch. See <<cypher-merge,`MERGE`>>.

[discrete]
====== 26.10.2 - `DROP CONSTRAINT <name>` does not drop named constraints created by older releases

A named Cypher constraint now records what its `CREATE CONSTRAINT` created, and `DROP CONSTRAINT <name>` removes exactly that; before, it did nothing (issues #9646, #9707). Creating a constraint under a name in use and dropping an unknown name now raise an error, unless `IF NOT EXISTS` or `IF EXISTS` is given.

*Impact:* a named constraint created by 26.10.1 or earlier has no such record, so `DROP CONSTRAINT <name>` raises an error for it.

*Action:* drop an old constraint by its index name, or through SQL (`DROP INDEX`, `ALTER PROPERTY ... MANDATORY false`). See <<cypher-drop-constraint,`DROP CONSTRAINT`>>.

[discrete]
====== 26.10.2 - The `path.*` procedures answer as `apoc.path.*` does

`path.expandconfig` now reads its `uniqueness` option, with the APOC default `RELATIONSHIP_PATH`, and `path.expand` is breadth-first with `RELATIONSHIP_PATH` (issue #10049). Before, the breadth-first walk was always `NODE_GLOBAL` and the depth-first walk and `path.expand` always `NODE_PATH`. `path.subgraphall` returns every relationship between the returned nodes, whatever the `relationshipFilter` (issue #10048). `relationshipFilter` and `labelFilter` read the APOC syntax, and an unknown relationship type or label is refused (issue #10025).

*Impact:* on a graph with cycles or several routes to a node these procedures return more paths, growing quickly with `maxLevel`. A walk too wide for `arcadedb.queryMaxHeapElementsAllowedPerOp` or `arcadedb.queryMaxHeapRAM` fails the query.

*Action:* to keep the old answers add `uniqueness: 'NODE_GLOBAL'` to a breadth-first `path.expandconfig`, `uniqueness: 'NODE_PATH'` to a depth-first one, and replace `path.expand` with the equivalent `path.expandconfig` call with `bfs: false, uniqueness: 'NODE_PATH'`. See <<path-expand-config,`path.expandconfig`>>.

[discrete]
====== 26.10.2 - An ISO duration text is parsed as Neo4j parses it

`duration('<text>')`, a `DURATION` property set from text and a gRPC value tagged `duration` now follow the Neo4j grammar (issue #10055). Refused: a text with no component (`P`, `PT`, `P1YT`), a malformed number (`P.5Y`, `PT1.S`) and a fraction on any component but the last one (`P1.5Y2M`). Newly accepted: a sign before the `P` or on a component, and a decimal comma.

*Impact:* writes and queries that used such texts fail instead of storing a zero or truncated duration.

*Action:* correct the duration texts. See <<duration,`DURATION`>>.

[discrete]
====== 26.10.2 - Time-series writes refuse what they used to store silently

* A line protocol, gRPC or remote write with an empty tag value (`cpu,host= value=1`) is refused with HTTP `400` or `INVALID_ARGUMENT`, as InfluxDB does. Leave the tag out instead (issues #8647, #9364).
* A sample carrying a tag, field, property or label its type does not declare in that role is dropped and reported as a partial write (HTTP `400` with `undeclaredKeys`, or gRPC `undeclared_keys`). SQL `INSERT` fails, and Prometheus remote write drops the series (issues #8646, #9365, #9366, #9384). A sample that omits a declared key is still accepted. A Prometheus label with an empty value is an absent label.
* A column codec that cannot encode the column type is refused at `CREATE`; types already persisted keep loading (issues #9310, #9384).
* A line protocol line cut right after a tag or field `,` separator is refused (issues #9323, #9392).

*Impact:* producers that send extra tags (Telegraf, for example), empty tag values or a misspelled key see refusals where they used to succeed.

*Action:* fix the producers, or set the database setting `arcadedb.timeSeriesUndeclaredKeys=ignore` for schema-less producers. See <<timeseries-undeclared-keys,Undeclared keys>>.

[discrete]
====== 26.10.2 - Unbounded time-series reads stream

`SELECT FROM <timeseries type>` without `LIMIT`, and the gRPC time-series stream without a row limit, now stream rows instead of loading the whole range first (issues #9420, #9421).

*Impact:* a retention pass that runs during such a read gives a shorter answer, since the removed rows are skipped. A downsampling pass that runs during it fails the read with a retryable error (HTTP `503`, gRPC retry category), possibly after some rows were sent.

*Action:* retry a read that fails this way, and expect a client to have received partial rows before the error.

[discrete]
====== 26.10.2 - PromQL refuses what Prometheus refuses

The PromQL engine now answers HTTP `400` `bad_data` on `/prom/api/v1/query` and `/query_range`, and an error in SQL `promql()`, for expressions it used to answer with NaN, an empty result or an unchanged value (issues #9723, #9743, #9788, #9883, #9922, #9924): a comparison between two scalars without `bool` (`1 > 0`), `and`, `or` and `unless` with a scalar operand, a range vector or a string as an operator operand, a function or aggregation argument of the wrong type or count (`sum(m[5m])`, `abs(-1)`), and a range query over a range vector or a string. `bool` right after an operator is now the comparison modifier, so a metric named `bool` cannot be the right operand.

*Impact:* dashboards and alert rules that used these expressions get an error instead of a value.

*Action:* rewrite them as Prometheus requires, for example `1 > bool 0`. See <<timeseries-promql-refused,Refused PromQL expressions>>.

[discrete]
====== 26.10.2 - Time-series filters, Prometheus endpoints and `ts.movingAvg` change results

* The PromQL label matchers `=`, `!=`, `=~` and `!~` read a typed tag the same way on `/query`, remote read and `/series`, so `=` and `!=` select complementary sets, and `=~"007"` selects a `LONG` tag holding 7 (issues #9833, #9880).
* The JSON tag filter of `POST /ts/query`, `GET /ts/latest`, the Grafana query and the gRPC `TimeSeriesQuery` and `TimeSeriesLatest` calls reads a `DATE` or `DATETIME` value in the database time zone instead of the JVM one (issues #9879, #9929). Embedded API: `TimeSeriesGateway.andTag()` and `buildTagFilter()` now take the `Database` as an argument.
* Prometheus remote write and read answer `415` for a `proto=` content type they do not implement, so a remote-write 2.0 sender falls back to 1.0 instead of losing the batch, and `400` instead of `204` for a non-empty body with no remote-write 1.0 field (issues #9624, #9755).
* `ts.movingAvg()` keeps one element per row: a null sample keeps its slot instead of being dropped, which shifted every later average into an earlier row (issue #9958).

*Impact:* some matcher and tag filter results change, a misconfigured remote-write sender now gets an error, and `ts.movingAvg()` results line up with their rows.

*Action:* recompile embedded code that calls `andTag()` or `buildTagFilter()`; otherwise none.

[discrete]
====== 26.10.2 - `GraphBatch.withLightEdges(true)` needs a `LIGHTWEIGHT` edge type

====== 26.10.2 - HA rolling upgrade: type renames and database settings wait for every node

`ALTER TYPE ... NAME` and `ALTER DATABASE` / `set database setting` now replicate to every node; before, they changed the node that ran them only (issues #9762, #9763). While any peer runs an older build or cannot be reached, a rename is refused up front with HTTP `409`, and a database setting change with HTTP `409` / gRPC `FAILED_PRECONDITION`; nothing changes (issues #9891, #9904, #9919). ====== 26.10.2 - A follower's write refusal is a redirect on every protocol

A write sent to an HA follower is refused with the leader address. Bolt, MongoDB and Redis reported it as a retryable conflict, so drivers retried against the same follower. A refusal that names the leader is now a redirect (issues #9845, #9868, #9869, #9930, #9931): Bolt `Neo.ClientError.Cluster.NotALeader` (was `DeadlockDetected`), MongoDB `10107 NotWritablePrimary` (was `112 WriteConflict`), Redis `READONLY` (was `TRYAGAIN`), the `/ws` insert endpoint code `NOT_LEADER` (was `DB_ERROR`) with a `leaderAddress` field, and the gRPC streaming inserts `InsertError.code = NOT_LEADER` (was `DB_ERROR` or `COMMIT_FAILED`) with `leader_address`. *Impact:* a `bolt://` (not `neo4j://`) or plain MongoDB client no longer retries a leader refusal, and clients that matched the old codes miss the new ones.

*Action:* send writes to the leader or use a routing driver, and handle the new codes. See <<websocket-insert-session,`/ws` insert session>>.

====== 26.10.2 - New and rebuilt hash indexes use page layout 3, which 26.10.1 cannot open

A `NOTUNIQUE_HASH` key whose record ids would take more than a quarter of a page now keeps them in a chain of pages of their own, so adding a record to a key costs the same whatever the key already holds (issue #9228). Before, the cost of an insert grew with the record ids the key already held: 49 pages were written per insert into a key with 20,000 of them. Every hash index created or rebuilt by 26.10.2, `UNIQUE_HASH` included, is written at page layout version 3. Hash indexes created by older versions keep working at their layout and move to version 3 only on `REBUILD INDEX`.

*Impact:* none on upgrade. A 26.10.1 server knows layouts 1 and 2 only, and refuses a hash index at layout 3 (see <<downgrade-hash-indexes>>).

*Action:* to get the new layout on an existing `NOTUNIQUE_HASH` index with large keys, run `REBUILD INDEX` on it. See <<index-hash,Hash index>>.

====== 26.10.2 - Cypher paths are sent as one path object on every protocol

Every Cypher path is now one path value, whatever built it: a `MATCH p = ...` pattern, `shortestPath()`, `allShortestPaths()`, a path procedure, or `apoc.path.create`, `apoc.path.slice` and `apoc.path.combine` (issue #9913). Over HTTP (and `Result.toJSON()`), gRPC and PostgreSQL a path returned by a `MATCH` used to be sent as its text form; it is now the object `{"_type": "path", "nodes": [...], "relationships": [...], "length": n}`, with every node and relationship written whole whatever the JSON serializer settings. A Bolt driver receives a native `Path` for the paths of procedures and `shortestPath()` too, and Studio's graph view draws a returned path.

*Impact:* a client that parsed the text form of a `MATCH` path gets an object instead.

*Action:* read the `nodes`, `relationships` and `length` fields of the object, or return `nodes(p)` and `relationships(p)` explicitly. See <<graph-algo-path-value>>.

====== 26.10.2 - `COMMIT RETRY` and `Database.transaction()` do not retry a leader refusal

A `NeedRetryException` now tells whether retrying on the same server can succeed (`isRetryableOnThisNode()`). An HA follower that refuses leader-only work (a schema change, a security mutation) and names the leader answers `false`, so `BEGIN ... COMMIT RETRY <n>` and `Database.transaction(..., retries)` raise its `ServerIsNotTheLeaderException` on the first attempt (issue #9995). Before, they retried it `<n>` times with the retry delay in between, and `COMMIT RETRY ... ELSE` then ran the `ELSE` block. A refusal raised during an election, which names no leader, is still retried.

*Impact:* the caller gets the leader refusal at once. A `COMMIT RETRY ... ELSE { ... } AND CONTINUE` block no longer runs its `ELSE` or hides the error for such a refusal.

*Action:* send leader-only work to the leader the error names. See <<sql-script-commit>>.

====== 26.10.2 - Embedded API changes

* `Schema.alterMaterializedView()` refuses a null mode and a negative interval (`IllegalArgumentException`) and an interval on a `MANUAL` or `INCREMENTAL` view (`SchemaException`), which it used to store (issues #8726, #9381). SQL `ALTER MATERIALIZED VIEW` is unaffected.

*Action:* call these methods on the leader, validate materialized view arguments before passing them, and expect `remove()` on an edge iterator to throw when the delete is refused.

====== 26.10.2 - Client error handling: gRPC writes whose answer was lost, streamed error lines, Postgres transaction modes

* The gRPC Java client throws a non-retryable `RemoteException` when an admin write through `RemoteGrpcServer` or a streaming write (`ingestStream`, `ingestBidi`, `timeSeriesWriteStream`, graph batch loads) ends with a bare `UNAVAILABLE`, since the write may have been applied; reads and `validate_only` dry runs stay retryable. A client-side deadline is a `TimeoutException` whose message says the write may already have been applied (issues #8822, #9470).
* In production mode, the `message` of the `error` line of a streamed query is the classified label, like the `error` field the line now carries in every mode; the detail is in the server log (issues #8899, #9475).
* PostgreSQL: `SERIALIZABLE`, `READ ONLY` and `AND CHAIN` in `BEGIN` / `START TRANSACTION` / `COMMIT` / `ROLLBACK` are refused with SQLSTATE `0A000` instead of a syntax error (issues #9631, #9753).

====== 26.10.1 — Sparse-vector top-K scores a window of documents at a time

The remote `ArcadeGraph` client used to connect to Gremlin Server on the fixed port `8182`. It now uses the port the server advertises (`GET /api/v1/server?mode=cluster`, `ports.gremlin`), and falls back to `8182` when the server advertises none (issue #8578).

====== 26.10.1 — Negative zero equals zero, and a few query results change

`-0.0` is now equal to `0.0` everywhere (SQL and Cypher, `=`, `IN`, ordering, indexed or not), as IEEE 754 and openCypher define it.

*Action:* a HASH index over a `FLOAT` or `DOUBLE` property that already stores `-0.0`, or an LSM index that stored both `-0.0` and `0.0`, should be rebuilt once after upgrading:

[source,sql]
----
REBUILD INDEX `Measure[value]`
----

Other results that change:

* `vector.neighbors`, `vector.sparseNeighbors` and `db.index.vector.queryNodes` on a parent type spec (`Parent[prop]`) now also search the records of its sub-types. Use the sub-type name in the spec to search only that sub-type.
* A `FLOAT` property is equal to the `DOUBLE` bound that narrows to it, so `<`, `<=`, `>` and `>=` agree with `=` and with an index (`v = 16777217.0` finds `16777216f`, and `v < 16777217.0` no longer does).
* An integer bound above 2^53 on a `DOUBLE` property, or above 2^24 on a `FLOAT` property, is answered by a scan instead of the index, so the result is exact.

====== 26.10.1 — HASH indexes on a DECIMAL property need one `REBUILD INDEX` after upgrading

A `DECIMAL` keeps the scale it was written with, so `5` and `5.00` are the same number stored two different ways. The `LSM_TREE` index family already treated them as one key; the `HASH` family did not, because it settles key identity on the serialized bytes and the two spell out differently. A `UNIQUE_HASH` index on a `DECIMAL` property therefore accepted both as separate rows, and a lookup for one spelling could not find a row stored under the other. Fixed in 26.10.1 (issue #7767).

*Impact:* any `HASH`/`UNIQUE_HASH`/`NOTUNIQUE_HASH` index on a `DECIMAL` property created before 26.10.1. `LSM_TREE`/`UNIQUE`/`NOTUNIQUE` indexes are unaffected.

*Action:* run `REBUILD INDEX` once, after upgrading, on every HASH index over a `DECIMAL` property:

[source,sql]
----
REBUILD INDEX `Invoice[amount]`
----

Until it is rebuilt, the index file still holds the keys in their original form and lookups stay unreliable. If duplicates slipped in while a `UNIQUE_HASH` constraint was not being enforced, the rebuild reports them as a duplicated key — correct the data, then rebuild again.

----

====== 26.10.1 - Writes that used to store NULL or a coerced value now fail

A value that the declared property type cannot take is refused with an error naming the property, instead of being stored silently as `NULL` or coerced (issues #8090, #9110). This covers:

* an unparsable datetime string written to a `DATETIME`/`DATE` property (the SQL timestamp form `2024-02-29 13:45:10.123456`, which PostgreSQL clients send, is now parsed instead of being stored as `NULL`);
* a number that overflows a `LONG`, `FLOAT` or `DOUBLE` property, an empty string written to a number, a fraction written to a `BOOLEAN`, and wrong-typed values written to `DECIMAL`, `DATETIME`, `BINARY` or `LINK` properties;
* a typed property set from a bare sub-query, for example `UPDATE Order SET id = (SELECT max(id) FROM Order)`, which used to store `NULL` and now fails with `Cannot convert type ArrayList to INTEGER`.

Schemaless properties are unaffected.

*Action:* fix the statements that now fail. For a sub-query, extract the scalar, for example `SET id = (SELECT max(id) AS m FROM Order)[0].m`.

|`ha.divergedFollowerRecoveryDurationMs`|shared `ha.staleFollowerRecoveryDurationMs` (60000)|separate window, default 20000. A deployment that raised the old setting to delay the reformat of a diverged follower must raise this one.
|`ha.grpcMaxConnectionIdleMs`|unbounded|300000: an idle inbound Raft gRPC connection is closed with a GOAWAY and reopened on the next call. `0` restores the old behavior.
|`ha.jvmPauseCloseThresholdMs`|Ratis closed the Raft division after a 60 s JVM pause|`0`: the division is not closed; a long pause still steps a leader down and the health monitor decides on recovery. Set `60000` to restore the old behavior.
|===

See <<upgrade-ha-cluster,HA cluster upgrade>> for the rolling-upgrade procedure.

[discrete]
====== 26.9.1 — Sparse-vector indexes need one `REBUILD INDEX` after upgrading

A partial compaction of an `LSM_SPARSE_VECTOR` index could give the merged segment a position ahead of a segment it had not merged. When that skipped segment held the tombstone for a document an older merged segment still had a live posting for, the delete was overruled and the document reappeared in `vector.sparseNeighbors` results — permanently, because the next full compaction then discarded the tombstone as the loser. The same inversion could restore a stale weight after an update. Fixed in 26.9.1 (issue #6379).

*Impact:* `LSM_SPARSE_VECTOR` indexes on databases created before 26.9.1 that have seen deletes or updates. Upgrading corrects the ordering for every new merge, but a segment already written under the old rule cannot be repaired automatically — the record of where it should have sat is gone.

*How to tell:* the server reports it once per affected index, when the index is opened:

[source]
----
Sparse-vector index 'Doc[tokens,weights]' holds 3 segment(s) whose precedence predates the
recency-epoch fix (issue #6379); a document deleted before those segments were merged may still
be returned by queries. Run 'REBUILD INDEX Doc[tokens,weights]' once to rewrite them in the
correct order.
----

The flag behind that message is stored in the segment and inherited by any later merge, so ordinary write traffic compacting the affected segments away does not silence it. Nothing else distinguishes an affected index: queries succeed and the data looks intact.

*Action:* run once per sparse-vector index, after upgrading:

[source,sql]
----
REBUILD INDEX `Doc[tokens,weights]`
----

This collapses the existing segments into a single correctly ordered segment. Indexes that have only ever been appended to are unaffected, as are databases created on 26.9.1 or later. See <<sparse-vector-search,Sparse Vector Search>>.

*HA rolling upgrade:* the corrected ordering is recorded in the segment file, but reading it correctly requires the fix. During a staged rollout, a node still on the older build that receives a segment merged by an upgraded leader falls back to ordering by segment id and can still return a deleted document, until it is upgraded too. Upgrade every node before running the `REBUILD INDEX` above, and treat sparse-vector query results from a mixed-version cluster as provisional.

[[upgrade-single-server]]
===== Single-server upgrade

. Download and extract the new ArcadeDB release in a separate directory (do not overwrite the old install).
. Stop the running server (or close every open database via the HTTP `<<http-servercommand,close database>>` command).
. Copy the directories listed in <<upgrade-what-to-copy,What to copy>> from the old install into the new install, preserving the original paths.
. Start the new server.

When the server starts, every database is opened with the new code and any required format migration is applied in place.

[[upgrade-what-to-copy]]
===== What to copy

ArcadeDB's root directory contains a fixed set of folders.
Only a few of them hold user-owned state; the rest are recreated from the release archive on every install.

[%header,cols="20%,15%,65%"]
|===
|Folder |Action |Notes

|`databases/`
|*Copy*
|The actual database data. Every subdirectory is one database. This is the only folder strictly required for an upgrade.

|`config/`
|*Copy selected files*
|The release ships a default `config/` directory. Carry over only the files you have actually modified — listing below.

|`backups/`
|Copy if you want history
|Backup archives produced by manual or automatic backups. The server does not need them to start; copy them only if you want to keep the backup history reachable from the Studio Backup tab and from `RESTORE DATABASE` commands.

|`log/`
|Skip
|Server log files. Safe to start with an empty `log/` directory; the release ships an empty one. Copy only if you want to keep historical logs alongside the new install.

|`raft-storage-<peerId>/` (HA only)
|*Copy*
|Per-node Raft log segments, created at runtime when HA is enabled. This storage is *durable by default* (`arcadedb.ha.raftPersistStorage=true`) and must be preserved so a node can rejoin by replaying its log instead of a full snapshot resync. When `raftPersistStorage` is explicitly `false`, it is ephemeral and can be skipped. See <<upgrade-ha-cluster,HA cluster upgrade>> for details.

|`replication/`
|Skip
|Legacy directory from the pre-Raft replication implementation. Not used by the current HA stack.

|`lib/`, `bin/`
|Use the new release as-is
|Java artifacts and start scripts. Always take them from the new release — do not copy from the old install. The only exception is custom JARs you have dropped into `lib/` yourself; carry those over by hand.
|===

[[upgrade-config-files]]
====== Files to carry over from `config/`

The `config/` directory ships with a small set of defaults.
You only need to copy the files that you have actually changed:

[%header,cols="35%,65%"]
|===
|File |When to copy

|`server-users.jsonl`
|Always, unless you create users only via REST/SQL on every upgrade.
This is where ArcadeDB persists local users and their per-database group assignments.

|`server-groups.json`
|If you have customised the security policy (custom groups, type-level permissions, result-set limits). See <<security-policy,Security Policy>>.

|`backup.json`
|If you have configured the auto-backup scheduler (schedule, retention, target directory). See <<auto-backup,Automatic Backup>>.

|`arcadedb-log.properties`
|If you have tuned `java.util.logging` settings (log levels, rolling file size, etc.).

|`gremlin-server.yaml`, `gremlin-server.groovy`, `gremlin-server.properties`
|Only if you use the embedded Gremlin Server and have edited any of these.
|===

Everything else under `config/` (`arcadedb-log-all.properties`, `arcadedb-statefulset.yaml`, …) ships unchanged with each release; take the new version.

NOTE: ArcadeDB does *not* read a `config/server-configuration.json` file in normal operation.
Server-wide settings come from JVM system properties, environment variables and the `arcadedb-server.sh` arguments — see <<server,Server Configuration>>.

[[upgrade-ha-cluster]]
===== HA cluster upgrade

An HA cluster (see <<ha-concepts,High Availability>>) is upgraded one node at a time.
The per-node procedure is the same as <<upgrade-single-server,single-server>> above, with the following clarifications.

What to migrate on each node:

* *`databases/`* — copy, exactly as in the single-server case.
* *`config/`* — copy the same files as in the single-server case.
The cluster's identity is derived from `arcadedb.ha.clusterName` and the `root` password (the inter-node token is computed from them at startup), so as long as every node keeps the same cluster name and the same root password, the upgraded cluster reattaches to itself without any extra step.
* *`raft-storage-<peerId>/`* — *copy*.
The local Raft log is durable by default (`arcadedb.ha.raftPersistStorage=true`), so preserve this directory across the upgrade to let the node rejoin by replaying its own log.
Whether or not it is preserved, after the upgraded node rejoins the cluster the leader replays any missing entries via Raft or, if the node has fallen behind the purge boundary, streams a full snapshot over HTTP automatically.
With `raftPersistStorage=false` this directory is ephemeral and can be skipped.
* *`backups/` and `log/`* — same as single-server.

Recommended rolling upgrade flow (zero downtime, requires quorum at all times):

. Pick a non-leader node first.
. Stop the node, install the new release in a separate directory, copy the folders listed above, start the new binary.
. Wait until `GET /api/v1/cluster` reports the node as healthy and caught up (replication lag near zero).
.. The <<studio-cluster,Studio Cluster tab>> shows the same information visually.
. Repeat for every remaining replica.
. Step the leader down with `POST /api/v1/cluster/stepdown` (or simply stop it — Raft will elect a new leader) and upgrade it last.

[NOTE]
====
From 26.10.1, a node that receives replicated TIMESERIES data for a type it does not have -- or for a type that
exists locally but is not a TIMESERIES one -- refuses the entry, which quarantines that database and triggers an
automatic resync from the leader. Earlier releases logged the problem and carried on, which left the node's copy
of that type permanently behind the leader's with nothing but a log line to say so.

This should not occur during an ordinary rolling upgrade, since the entry that creates a type is always applied
before data for it arrives. It is a safeguard for the case where it does -- for instance a mixed-version window
in which one node's build cannot construct a type another node has. If you see a database quarantined with a
message about a TimeSeries sealed store, the resync will restore it; complete the rollout so every node runs the
same build.
====

For first-time HA bring-up with a pre-existing database (e.g. when you scale a single-node install into a cluster), see <<ha-offline-bootstrap,Offline Cluster Bootstrap>>.

[[upgrade-docker]]
===== Docker / Kubernetes

When you run ArcadeDB from the official container image, the release is replaced atomically by changing the image tag.
The only data that survives across container restarts is what lives on a persistent volume, so:

* Mount `/home/arcadedb/databases` on a persistent volume — this is the equivalent of "copy the `databases/` folder".
* Mount `/home/arcadedb/config` only if you have edited the files listed in <<upgrade-config-files>>; otherwise let the image ship its defaults.
* Set `arcadedb.ha.raftStorageDirectory` to a static path (e.g. `/home/arcadedb/raft-storage`) and mount *that* path on a persistent volume. The default per-node directory is named `raft-storage-<nodeName>` dynamically, which a container runtime or Kubernetes cannot mount as a volume (a wildcard like `/home/arcadedb/raft-storage-*` is created literally, not expanded) — this is exactly what `raftStorageDirectory` is for. The Raft log is durable by default (`arcadedb.ha.raftPersistStorage=true`) so a restarted pod can replay its own log instead of resyncing from peers. With `raftPersistStorage=false`, the log is ephemeral and this mount is unnecessary.
* Mount `/home/arcadedb/backups` if you want to retain backup archives across pod restarts.

For Kubernetes specifics (StatefulSet, headless service, init container for pre-staging a database), see <<kubernetes,Kubernetes>>.

[[downgrade]]
==== Downgrade ArcadeDB

In case you need to downgrade to an older version of ArcadeDB, check the binary compatibility between the versions.
ArcadeDB uses calendar versioning in the format `YY.M.S` (year, month, serial: for example `26.10.1` is the first release of October 2026), with 100% on-disk compatibility for migration of databases up or down between *serial* releases of the same year and month (the `S` in `YY.M.S`).
For downgrades across months the safest path is to export the database with the newer version and re-import it with the older version.
See <<versioning-policy,Versioning, Compatibility and Deprecation Policy>> for the full compatibility rules.

[[downgrade-ha]]
===== Downgrading a node of an HA cluster

A cluster running v26.10.1 or later replicates schema changes in a compact format that earlier builds cannot read.
Those entries stay in the Raft log, so a node that is restarted on an older build replays them and ends up with a schema that no longer matches the rest of the cluster - silently.

*A node of a cluster that has run v26.10.1 or later must not be rolled back below it by restarting it on its existing Raft log.*
If you have to go back that far, rebuild the node instead: stop it, delete its `raft-storage-<peerId>/` directory and its `databases/` folder, and start the older build so it rejoins empty and takes a fresh copy from the leader.

NOTE: This applies only to the Raft log, not to your data. Database files themselves keep the usual serial-release compatibility described above.

[[downgrade-hash-indexes]]
===== Downgrading from 26.10.2 to 26.10.1 with hash indexes

Since v26.10.2 every hash index (`UNIQUE_HASH` or `NOTUNIQUE_HASH`) that is created or rebuilt is written at page layout version 3, which 26.10.1 does not know.
A 26.10.1 server refuses such an index with:

----
Hash index '<name>' has the page layout version 3, which this server does not support (it knows 1 and 2). It was created by a newer version: open the database with that version, or drop and recreate the index.
----

Hash indexes that 26.10.2 opened but did not rebuild keep their older layout and still open on 26.10.1.
Before going back, drop the hash indexes created or rebuilt by 26.10.2 (the layout version is part of the index file name) and recreate them once the database runs on 26.10.1, or export the database and re-import it.
Do not open a database holding a hash index created or rebuilt by 26.10.1 or later with a server older than 26.10.1, which does not check the layout version: see <<index-hash,Hash index>>.
