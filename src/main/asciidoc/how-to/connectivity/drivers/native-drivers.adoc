ArcadeDB publishes six native drivers, an HTTP one and a gRPC one for each of Python,
JavaScript/TypeScript and Go, from the
https://github.com/ArcadeData/arcadedb-drivers[arcadedb-drivers] repository. Every one of them is
generated from a shared contract -- an OpenAPI specification for the HTTP drivers, a Protobuf
`.proto` for the gRPC drivers -- and each driver's build regenerates from that contract and fails
if the checked-in code and a fresh regeneration disagree.

That matters to you, not just to the people who build the drivers: a generated client cannot
silently disagree with the server about the wire format. When ArcadeDB adds a field, the driver
gets it from the contract rather than from someone remembering to hand-write it.

===== HTTP or gRPC?

[cols="1,3", options="header"]
|===
| Choose | When

| HTTP
| General application traffic, browsers, serverless functions, and anywhere you want the smallest
dependency footprint. This is the right default.

| gRPC
| Throughput-sensitive server-to-server work: large result sets you want to stream rather than
page, and bulk inserts.
|===

There is no browser gRPC driver, and there cannot be one until the server changes. ArcadeDB's
`GrpcServerPlugin` is plain grpc-java over HTTP/2, with no gRPC-Web handler and no Connect
protocol in front of it. A browser cannot speak raw HTTP/2 gRPC framing at all, so no client
library in any language can reach this server from a browser. Use an HTTP driver there.

===== The result envelope, and why `truncated` matters

The HTTP drivers' `query` and `command` do not return bare rows. They return the whole response
envelope: `result`, `limit`, `returned`, and `truncated`.

`truncated` is true when the server's serializer hit its row cap while the query still had rows
left to write. `result` is then a partial answer, not a short-but-complete one -- and the two are
indistinguishable by shape. A caller that reads `result` and ignores `truncated` will silently
work off half an answer.

Always check `truncated` before treating `result` as the whole result set. When it is true,
re-query with a narrower filter or a higher `limit`. Raising `limit` is not always the fix: a
result whose true size exceeds the server's hard ceiling
(`+arcadedb.server.httpQueryMaxResultRows+`) is refused outright with HTTP 413 rather than
truncated, so past that ceiling a narrower filter is the only way forward.

===== Versions and server compatibility

All six drivers are released together, at one version, and each release is generated against one
ArcadeDB server release's contract:

[cols="1,1,3", options="header"]
|===
| Driver version | ArcadeDB server | Packages

| 0.4.0
| 26.11.1
| All six

| 0.3.0
| 26.10.2
| All six: `arcadedb-driver` and `arcadedb-driver-grpc` (PyPI), `@arcadedb/driver` and
`@arcadedb/driver-grpc` (npm), `github.com/ArcadeData/arcadedb-drivers/go/arcadedb` and
`.../go/arcadedbgrpc` (Go modules)

| 0.2.0
| 26.10.1
| All six

| 0.1.0
| 26.9.1
| PyPI and npm only
|===

Pointing a driver at a server on a materially different release may work for the endpoints both
versions share, but is not tested or supported. Install commands in these pages are deliberately
unpinned; the registries carry the current version. The Go modules had no 0.1.0 release: their
first published version is 0.2.0. Each release's changes are listed in the
https://github.com/ArcadeData/arcadedb-drivers/releases[arcadedb-drivers release notes].

===== Upgrading to 0.4.0

0.4.0 is generated against ArcadeDB 26.11.1. It adds a transaction isolation level to
`transaction()` in all six drivers (`READ_COMMITTED` or `REPEATABLE_READ`), and a row limit to
`command` in the Python, TypeScript and Go HTTP drivers, with the same meaning as on `query`.
The isolation level relies on a field that the 26.11.1 contract introduced, so older servers are not
tested. Three changes can affect existing code:

* *TypeScript: `limit` moved from `QueryOptions` to `CommandOptions`.* `QueryOptions` is still
  exported, as an alias of `CommandOptions`, so existing imports keep compiling.
* *Go HTTP: `WithLimit` now returns the exported `LimitOption`,* which is both a `QueryOption` and
  a `CommandOption`. Only code that holds the function itself as a `func(int) QueryOption` breaks.
* *Go gRPC: `Transaction` takes trailing `opts ...TransactionOption`.* Callers compile unchanged.

On a 26.11.1 server, wrong Basic credentials answer 401 instead of 403, and committing a terminated
transaction answers 404 instead of a silent 204. The driver READMEs describe both, and keep the
old behaviour documented for earlier servers.

===== Upgrading to 0.3.0

0.3.0 adds server administration, login sessions and API tokens, listing and terminating running
work, query tags, and a duplex insert session to the three HTTP drivers; each language's page
below shows them. Three changes can affect existing code:

* *gRPC insert streams no longer copy the database into `InsertOptions.database`.* All three gRPC
  drivers send `database` on the first chunk only, as the `.proto` specifies. Every supported
  server (26.9.1 and later) reads it there. A server older than 26.9.1 reads only
  `options.database`, so against it a stream now reports its rows as received, inserts nothing,
  and raises no error. If you must use such a server, set `options.database` yourself.
* *A stream's in-band error carries the server's own status.* An error event in the middle of an
  HTTP query or command stream used to surface with status 200. It now carries the event's
  `status` (500, 503, 409 and so on), and falls back to 200 only when the event has none. Retry
  logic keyed on the status now sees the real one.
* *Go: the option types are split.* `QueryOption` is now a sealed interface, joined by
  `CommandOption` and `TransactionOption`. Existing calls compile unchanged; only code that
  implemented `QueryOption` itself, or passed a `[]QueryOption` to `Command`, needs updating.
