[[java-api-remote]]
=== Java API (Remote)

ArcadeDB comes with a convenient Java library to work with a remote database.

[[remote-server]]
==== RemoteServer Class
The RemoteServer class is used to manage remote server connections and databases.

The server administration calls (databases, users, groups and API tokens) prefer the cluster leader and wait out an election in progress. If the server becomes unreachable, they switch to another server of the cluster only when `arcadedb.network.sameServerErrorRetries` is greater than 0 (the default is 0). A write whose answer was lost is never sent again, because the server may already have applied it. `createApiToken` refuses to send the token over plain HTTP to a non-loopback host, whichever server the request is sent to, unless `setAllowInsecureApiTokenTransport(true)` is set.

When a server becomes unreachable, `RemoteServer` and `RemoteDatabase` refresh the cluster configuration by asking every known replica in turn, then the old leader, then the address the client was created with, and the retry goes to the server that answered. If no server can give the configuration, for example during an election, the client keeps the leader and the replica list it had and spends the remaining retries (`arcadedb.ha.errorRetries`) on that list, so a read can still reach a follower. The error is raised when those retries run out. _(Since v26.12.1.)_

`RemoteDatabase.begin()` fails over the same way. When the server it is sent to cannot be reached and the request provably never got there, it refreshes the cluster configuration and starts the transaction on another live server, trying each known server once within the same `arcadedb.ha.errorRetries` budget. The commands, the commit and the rollback of that transaction then go to the server that began it. The `FIXED` connection strategy keeps to its one server. A commit is never sent to another server this way, since a lost answer may mean it was applied. Before, `begin()` kept failing with `NeedRetryException` ("the server could not be reached") until another request moved the client to a live server. _(Since v26.12.1.)_

`RemoteDatabase.begin()` fails over the same way when the server it is connected to cannot be reached: since no transaction exists yet, the begin is sent to another server of the cluster, trying every known server before it tries one again, within the same `arcadedb.ha.errorRetries` budget. It is retried only when the request provably never reached a server. The rest of the transaction (commands, commit and rollback) then goes to the server that began it. With the `FIXED` connection strategy the begin keeps to its server, as every other request does. Before, a `begin()` kept failing with "the server could not be reached" until some other request moved the client to a live server. _(Since v26.12.1.)_

_(Since v26.10.2.)_ `acceptDivergedDatabase(databaseName)` and `acceptStaleSnapshot()` are the operator overrides for a
node of a replicated cluster that has no peer left to resync from. Both are root only and accept the node's local copy
as the truth without a resync, so the entries that were skipped are not replayed. `acceptDivergedDatabase` lifts the
quarantine, and its read floor, standing on one database, through `+POST /api/v1/cluster/accept-diverged/{database}+`.
It is allowed on a node that is the only voter of its cluster, or when every voter holds the same database quarantined,
since no node then has a copy to resync from. It returns `result`, `database`, `localServer` and `appliedIndex`, plus
`divergenceCause` and `readFloor` when they stood. `acceptStaleSnapshot` lifts the node-wide stale-snapshot read floor,
through `POST /api/v1/cluster/accept-stale-snapshot`, on a sole voter only, and returns `result`, `localServer`,
`readFloor`, `snapshotIndex` and `appliedIndex`. The server answers `404` when nothing stands to be lifted (for
`acceptDivergedDatabase`, when the database carries no quarantine and no read floor) and `409` where a resync from a
peer is still the way out; `acceptStaleSnapshot` also answers `409` while a snapshot download is running. The gRPC
client `RemoteGrpcServer` has the same two methods, returning the `AcceptDivergedDatabaseResponse` and
`AcceptStaleSnapshotResponse` messages and raising its not-found and failed-precondition errors for the same cases (see
<<grpc-api,gRPC API>>). When to use them is described in <<ha-accept-diverged,Lifting a quarantine without a resync>>
and <<ha-accept-stale-snapshot,Lifting the stale-snapshot read floor>>.

_(Since v26.10.2.)_ A create refused because the name is already taken raises
`com.arcadedb.remote.RemoteAlreadyExistsException`: a user (`createUser`), an API token (`createApiToken`) or a
database (`create`). The server answers these with `409 Conflict`, and the gRPC server with `ALREADY_EXISTS`;
`RemoteGrpcServer` raises the same exception from `createUser`, `createApiToken` and `createDatabase`, where it used to
report a duplicated key (or, for `createDatabase`, a plain `RuntimeException`). It extends `RemoteException`, so code
that caught `RemoteException` for these cases keeps working, and a provisioning tool can catch it to treat "already
there" as success. Restoring a backup into a database name that is taken still answers `400`.

[[remote-exception-types]]
_(Since v26.11.1.)_ A failing statement raises the same exception remotely as embedded: a syntax error is a
`CommandSQLParsingException`, an unknown function or a missing bucket a `CommandExecutionException`, an `INSERT` sent
through `query()` a `QueryNotIdempotentException`, an unknown query language an `IllegalArgumentException`, and so on for
every ArcadeDB exception that carries only its message, over HTTP and gRPC alike. Its message is the server's own
sentence. A missing query parameter arrives as the `CommandSemanticException` that `CommandParameterMissingException`
extends, since the latter is built from the parameter names rather than from a message. `RemoteException` itself now extends `ArcadeDBException`, so a `catch (ArcadeDBException e)` written against the
database interfaces catches the same failures whether the database is embedded or remote, including a failure whose type
the client cannot rebuild (a class of a newer server, or of a plugin). In 26.10.2 and earlier these failures reached the
caller as a `RemoteException` that was not an `ArcadeDBException`, with a message of the form
`Error on executing remote operation ... (cause:<class> detail:<message>)`.

_(Since v26.11.1.)_ `getType()` answers the record's type on a mutable remote record too (`newDocument()`,
`newVertex()`, `modify()`), as it does on a record read from the server, instead of throwing
`UnsupportedOperationException`. `toMap()` and `toJSON()` of a remote edge include `@in` and `@out`, as an embedded edge
does.

_(Since v26.12.1, issue #12190.)_ The record factories of `RemoteDatabase` (and of `RemoteGrpcDatabase`, which inherits
them) follow the embedded API. `newEmbeddedDocument()` works on a remote document, vertex or edge, also nested, in a list
or in a map: the embedded document is built on the client and sent with its owner on `save()`. Only a document type can
be embedded. `newDocument()` on a vertex or edge type, and `newVertex()` on a type that is not a vertex type, throw
`IllegalArgumentException`. `newRecord()` of a remote type builds a document on a document type and a vertex on a vertex
type, and throws `UnsupportedOperationException` on an edge type: create an edge from its source vertex with `newEdge()`.
Before, `newEmbeddedDocument()` threw a `NullPointerException`, `newDocument()` on a vertex type saved a vertex,
`newVertex()` on a document type threw a `ClassCastException` and `newRecord()` on an edge type was accepted. Code that
created vertices with `newDocument()` has to use `newVertex()`.

[[remote-database]]
==== RemoteDatabase Class
The RemoteDatabase class is used to work with a remote database instance.

Add the following dependencies in your Maven pom.xml file under the tag `<dependencies>`:

[source,xml, subs="+attributes"]
----
<dependency>
    <groupId>com.arcadedb</groupId>
    <artifactId>arcadedb-engine</artifactId>
    <version>{revnumber}</version>
</dependency>
<dependency>
    <groupId>com.arcadedb</groupId>
    <artifactId>arcadedb-network</artifactId>
    <version>{revnumber}</version>
</dependency>
----

==== 10-Minute Tutorial

===== Connect to a remote database
There are 2 main classes that handle the connection to the remote database by translating the Java API into http-calls:

- `<<remote-server,RemoteServer>>`, to create new database on a remote server
- `<<remote-database,RemoteDatabase>>`, to work with a remote database instance

We start by creating a RemoteServer:

[source,java]
----
RemoteServer server = new RemoteServer("localhost", 2480, "root", "playwithdata");
----

Next, let's create a RemoteDatabase instance pointing to the database "mydb" on ArcadeDB Server located on "localhost", port 2480 -- the HTTP port, which is what `RemoteDatabase` speaks. User and passwords are respectively "root" and "playwithdata":

[source,java]
----
RemoteDatabase database = new RemoteDatabase("localhost", 2480, "mydb", "root", "playwithdata");
----

NOTE: The `RemoteDatabase` is not thread-safe. It holds a backend session. If a thread closes a transaction, it also closes the session, so that any request performed by a concurrent thread using the same RemoteDatabase instance leads to unexpected behavior. To avoid concurrency problems you should not hold RemoteDatabase instances as fields on the heap, but rather create a new instance in method scope as a variable on the stack.

[[remote-vertex]]
==== RemoteImmutableVertex and RemoteMutableVertex

Vertices retrieved through `RemoteDatabase` are instances of `RemoteImmutableVertex` (or `RemoteMutableVertex` after calling `modify()`).
These classes expose graph-traversal methods that translate directly into SQL queries over HTTP -- there is no per-vertex round trip.

===== Traversal methods

[cols="1,3"]
|===
|Method|Description

|`getVertices(direction, edgeTypes...)`
|Returns all neighbor vertices, transparently paginating in batches of `DEFAULT_PAGE_SIZE` (2,000) records per HTTP call. The vertices come in the order of their edges, once per edge, and a vertex deleted since its edge was read is left out.

|`getVerticesPaged(direction, pageSize, edgeTypes...)`
|Same as above but with an explicit page size. Use to tune round-trip vs. payload trade-off for supernodes. A page size of zero or less throws `IllegalArgumentException`.

|`getVertices(direction, limit, skip, edgeTypes...)`
|Returns a single page of up to `limit` neighbor vertices starting at offset `skip`. Useful for implementing your own pagination.

|`getEdges(direction, edgeTypes...)`
|Returns all connected edges in RID order, transparently paginating with `DEFAULT_PAGE_SIZE` per HTTP call. `BOTH` returns the outgoing edges, then the incoming ones, so a self-loop comes twice, as in the embedded API.

|`getEdgesPaged(direction, pageSize, edgeTypes...)`
|Same as above but with an explicit page size.

|`getEdges(direction, limit, skip, edgeTypes...)`
|Returns a single page of up to `limit` edges starting at offset `skip`.

|`countEdges(direction, edgeTypes...)`
|Returns the number of connected edges (single HTTP call, no result materialization).
|===

`DEFAULT_PAGE_SIZE = 2_000` is the batch size used by `getVertices()` / `getEdges()`. Values up to 20,000 are safe against the server's default result limit.

===== Example

[source,java]
----
RemoteDatabase db = new RemoteDatabase("localhost", 2480, "mydb", "root", "playwithdata");

// standard traversal -- paginates automatically, no cast needed
Vertex hub = db.lookupByRID(new RID(db, "#1:0"), true);
for (Vertex neighbor : hub.getVertices(Vertex.DIRECTION.OUT, "Knows")) {
    System.out.println(neighbor.getString("name"));
}

// supernode -- explicit page size requires cast to the concrete remote type
RemoteImmutableVertex hubRemote = (RemoteImmutableVertex) hub;
for (Vertex neighbor : hubRemote.getVerticesPaged(Vertex.DIRECTION.OUT, 5_000, "Knows")) {
    System.out.println(neighbor.getString("name"));
}
----

NOTE: Each page of `getEdges()`, `getVertices()`, `getEdgesPaged()` and `getVerticesPaged()` resumes after the RID of the last edge of the previous page, so deleting the edges or the vertices while iterating (`for (Edge e : hub.getEdges(OUT)) e.delete();`), or another client deleting edges already read, does not make the iteration skip live ones.
A lightweight edge has no RID of its own: deleting, while iterating, an already read lightweight edge of the same type between the same two vertices as a live one can still hide the live one.
The server still reads the whole edge list of the vertex on every page, so for supernodes with millions of edges prefer a larger page size, or a SQL query with a server-side `WHERE` filter to narrow results before fetching them.

The database, which name you have given as the third parameter in the constructor is not automatically created nor is it checked whether it exists. Before you use the `RemoteDatabase` make sure that the database exists, or, if it doesn't, create it:

[source,java]
----
if (!server.exists("mydb"))
    server.create();
----

For a list of all databases hosted by the server use:

[source,java]
----
List<String> databases = server.databases();
assert(databases.contains("mydb"));
----

Now that we have the database created we may create the schema (but we may also work without):

[source,java]
----
String schema =
"""
    create vertex type Customer if not exists;
    create property Customer.name if not exists string;
    create property Customer.surname if not exists string;
    create index if not exists on Customer (name, surname) unique;
""";
database.command("sqlscript", schema);
----

As language we have used `sqlscript`, which has the advantage that all the statements in the script are executed within one single transaction. Of course you can also send these requests line by line with `sql` as language. If you go line by line it is important to enclose the requests in a common transaction:

[source,java]
----
database.begin();
database.command("sql", "create vertex type Customer if not exists");
database.command("sql", "create property Customer.name if not exists string");
database.command("sql", "create property Customer.surname if not exists string");
database.command("sql", "create index if not exists on Customer (name, surname) unique");
database.commit();
----

Or:

[source, java]
----
database.transaction(() -> {
    ...
});
----

The `transaction` method encloses the lambda function with a `begin` - `commit`, or a `rollback` in case of any exception.

If the transaction fails because another client modified the same records, it is rolled back and the lambda is executed again, up to `arcadedb.txRetries` times (3 by default). There is one exception: when `transaction(lambda, true)` is called from inside a transaction you opened yourself, the error is thrown to you instead of being retried, because re-executing the lambda inside your still open transaction would leave the effects of the failed attempt behind. In that case catch the exception and retry the whole unit of work.

The same happens when the server refuses the transaction before running it: the `503` a node answers while it installs a snapshot, a leader change, or a `begin` whose connection could not be established. Each retry waits first, with the exponential backoff the embedded `transaction()` uses (`arcadedb.txRetryDelayBase` doubling up to `arcadedb.txRetryDelay`), and when the refusal carries a `Retry-After` header the retry waits at least that long, up to `arcadedb.network.retryAfterMaxWait` (30 seconds by default). A duplicated key is retried only once, since failing twice means the duplicate is genuine. A commit the server answered with an error also releases the server-side session right away instead of leaving it to the session timeout.

A commit whose connection drops after the request was sent is different: the server may already have applied it. Over gRPC such a commit (status `UNAVAILABLE` with no error from the server) raises a `TransactionException` and is *not* retried, so the work is never applied twice. Read the data back to find out whether the commit landed.

_(Since v26.10.2.)_ The gRPC client draws the same line for the other writes whose answer can be lost. A bare
`UNAVAILABLE` (no error class from the server, and not a failure to connect) on an admin write of `RemoteGrpcServer`
(creating or dropping a database, a user or a token, and the other server writes) or on a streaming write of
`RemoteGrpcDatabase` (`ingestStream`, `ingestBidi`, `timeSeriesWriteStream`, graph batch loads) raises a
non-retryable `RemoteException` whose message says the server may already have applied the request. A streaming write
commits as it goes, so any part of it, from none to all, may be durable. Reads, and `validate_only` dry runs, stay
retryable. A client-side deadline that expires before the server answers raises a `TimeoutException` whose message says
that the write may already have been applied. Before, these failures were reported as retryable, so a caller that
retried could apply a write twice.

A statement stopped on the server (by the <<http-running-queries,`terminate query`>> server command, Cypher
`TERMINATE TRANSACTIONS` or Studio) raises `com.arcadedb.exception.QueryTerminatedException`, over HTTP and over gRPC
alike. It is not retried by `transaction()`: somebody asked for the work to stop. _(Since v26.10.2.)_

_(Since v26.12.1, issue #12193.)_ The index methods of the schema API answer the index over a `RemoteDatabase` as they do
embedded. `createTypeIndex()` and `getOrCreateTypeIndex()`, of the `Schema` and of a type, return the index they created
or found, and `getIndexByProperties()`, `getPolymorphicIndexByProperties()`, `getIndexesByProperties()` and
`getAllIndexes()` of a type find an existing index, so a setup such as
`if (type.getIndexByProperties("email") == null) type.createTypeIndex(...)` creates the index once. The returned index
describes it (name, type, properties, index type, unique, null strategy, key types) and `drop()` drops it. The client
holds none of its entries, so `get()`, `range()`, `countEntries()`, `put()`, `setNullStrategy()` and the other methods
reading or changing them throw `UnsupportedOperationException`: run a query instead, the server picks the index, and set
the null strategy when creating the index (<<sql-create-index,`CREATE INDEX ... NULL_STRATEGY`>>). Each lookup asks the
server and is not cached, so it sees an index another client created or dropped. Before, the lookups answered `null` or an
empty list for an existing index, `getIndexesByProperties(String...)` and `getAllIndexes()` threw
`UnsupportedOperationException`, and the creation methods returned `null`.

Now that the schema is in place, we will insert some data:

[source, java]
----
database.command("sql", "insert into Customer(name, surname) values(?, ?)", "Jay", "Miner");
database.command("sql",
        "update Customer set lastcall = :lastcall where name = :name and surname = :surname",
        Map.of("lastcall", Date.from(Instant.now()), "name", "Jay", "surname", "Miner"));
----

The first command creates a new vertex of type 'Customer'. The second command updates this vertex by adding a new value for the property 'lastcall'. The first command uses unnamed parameters where the values are mapped by their order in the parameter list. Whereas the second command uses named parameters, which are mapped by the parameter names.

_(Since v26.12.1.)_ A parameter, and a value set on a record that `save()` sends, keeps its Java type as the embedded API
does, also for a property the schema does not declare: a `RID` (or a saved record) is stored as a link, a `BigDecimal` as
a DECIMAL with its scale (`SELECT :a + :b` with `0.1` and `0.2` answers `0.3`), a `byte[]` as BINARY, a `LocalDate` as a
DATE, `java.util.Date`, `LocalDateTime` and `Instant` as a DATETIME and a `ZonedDateTime` as a ZONED_DATETIME. The client
sends them as <<vector-http-typed-markers,typed parameter markers>>, which a server older than 26.12.1 does not decode, so
upgrade the server first. Before, these values reached the server as plain JSON: a `RID` was stored as a string, a record
as an embedded copy, a `BigDecimal` as a double, a `byte[]` as a list and the dates as numbers. A record read back from
the server holds an undeclared link as a `RID`, and a list or map of links as a list or map of `RID`s, as a projection of
the same property does _(since v26.12.1, issue #12195; before, the record answered the rid text `"#1:0"`)_. The same
holds for the links in a property declared as a bare `LIST` or `MAP`, without `OF LINK`, and a `NaN` or infinite number
in such a collection reads back as a `Double` _(since v26.12.1, issue #12598)_. Every link the client reads, in a record
property, in the items of a list or map, or in a projection column, is bound to the remote database, so
`((Identifiable) doc.get("friend")).asDocument()`, `asVertex()` and `getRecord()` load the linked record from the server
on any thread _(since v26.12.1, issue #12603; before, they failed with `DatabaseOperationException` on a thread with no
embedded database open, and `database.lookupByRID(rid, true)` was the way to load the record)_. An undeclared date,
decimal or binary property still reads back as a string, a double or a list, so `modify()` and
`save()` write such an untouched property back with that type (issue #12599).

We can now query some customer data from our database:

[source, java]
----
ResultSet resultSet = database.query("sql", "select from Customer where name = :name",
        Map.of("name", "Jay"));
Map<String, Object> customer = resultSet.stream().findFirst().map(Result::toMap).orElse(Map.of());
----

The query returns a `ResultSet`, which holds an array of objects of type `Result`, which can be read as Map:

[source,javascript]
----
{name=Jay, @cat=d, @rid=#1:0, lastcall=1675961747290, surname=Miner, @type=Customer}
----

[[java-api-remote-streaming]]
===== Streaming results

`query()` and `command()` wait until the server has serialized the whole result, and keep it in
memory. For a large result use `queryStream()` or `commandStream()` instead: they ask the server for the
<<http-streaming-results,NDJSON encoding>> and return a `ResultSet` that reads each row off the connection as it
arrives, so neither the server nor the client holds more than one row at a time.

[source,java]
----
try (ResultSet resultSet = database.queryStream("sql", "select from Customer where surname = ?", "Miner")) {
  while (resultSet.hasNext()) {
    Result customer = resultSet.next();
    ...
  }
}
----

* The `ResultSet` keeps an HTTP connection open until it is read to the end or closed, so open it in a
try-with-resources. It can be read only once.
* `hasNext()` returns `false` only after the server sent the `stats` trailer. A failure on the server raises the
exception the buffered call would have raised, and a stream that ends without its trailer (a dropped connection)
raises a `RemoteException`: a short result is never returned silently.
* Without `setMaxResultRows()` the stream returns every row, up to the server's hard ceiling
`arcadedb.server.httpQueryMaxResultRows` (1,000,000 rows by default). A result above the ceiling raises an exception
after the rows that fit, instead of ending short. The server's default cap for buffered responses
(`arcadedb.server.httpQueryDefaultLimit`, 20,000 rows) does not apply to a stream _(since v26.12.1, issue #12185;
before, the stream stopped at that cap)_. Call `setMaxResultRows()` to cap the stream yourself: when the cap drops
rows, the client logs a warning and `hasNext()` returns `false`.
* `commandStream()` takes read-only statements only. The server refuses a statement that writes, because its rows would
reach the client before it committed. Use `command()` for writes.
* The response has no `explain` or write statistics. Use `query()` or `command()` when you need them.

`iterateType()` and `iterateBucket()` return every record of the type or bucket, as on the embedded API, whatever
`setMaxResultRows()` is set to _(since v26.12.1, issue #12185; before, they stopped at the server's default cap of
20,000 rows while `countType()` reported the full count)_. They read the records in one buffered response, so a type or
bucket larger than `arcadedb.server.httpQueryMaxResultRows` is refused with an exception rather than returned in part.
